## GAP-031① 是正 (2026-08-04) — 「分岐」の実装 (メッセージ時点で新スレッドへ)

> 監査スクリプト: `apps/web/.audit-e01-branch.mjs`（再実行可能・実操作+DB 突合・3 連続 ALL PASS）。
> pytest: `test_chat.py::TestBranchThread` 2 件 / vitest: uc08 に 3 件追加。

- **POST /chat/messages/{message_id}/branch**: 分岐点までの履歴 (表示順 =
  created_at, id の位置で切る) を新スレッド「分岐: 〈元題名〉」へコピー。
  コピー行は parent_message_id で直前コピーへ連鎖し、**先頭コピーの parent は
  分岐元メッセージ ID** (元スレッドへの系譜ポインタ — 既存の未使用列
  parent_message_id を実データ化)。元スレッドは不変。audit `chat_thread.branch`。
  R-T08: 他 WS user は 404 (pytest)
- **UI**: persisted assistant のアクション行に「分岐」(モック msg-action-row
  準拠)。クリック → 実 POST → 分岐先スレッドへ遷移 (履歴ロードで分岐点までを
  表示)。失敗は inline error、onBranched 未注入なら非描画 (Rule 10)

### 監査が検出した実バグ (2 件 — 分岐実装で顕在化)

1. **タプル比較の境界取り漏れ**: 同一トランザクションで入る user/assistant は
   created_at が同値 (default now() = transaction timestamp) になり、
   (created_at, id) タプル比較の境界が UUID 次第で崩れる → コピーが 1 件に。
   境界を「表示順の位置」で切る方式に修正
2. **スレッド表示順そのものの曖昧さ**: 同値 created_at は分岐に限らず
   (created_at, id) 順の表示を UUID 順に委ねていた → SSE の _insert_message を
   `clock_timestamp()` 明示に修正 (以後の user/assistant は必ず単調増加)。
   コピー行も +i マイクロ秒で順序固定

- **承認ゲート (SSE agentic ループ)**: `APPROVAL_REQUIRED_TOOLS` のツール要求は
  実行せず approval_inbox (type='tool_execution'、migration `t-d-99zf`) に

  tool_result で返す。audit `chat_tool.approval_requested`
- **POST /chat/tool-approvals/{id}/execute**（承認して実行）: pending を検証して
  初めて execute_atelier_tool を実行 → 実 knowledge 生成 → inbox approved +
  resolution_note に結果 → スレッドへ tool メッセージ記録 → audit
  `chat_tool.executed`。二重実行 409 / 他人の承認は RLS 不可視 404 (R-T08)
- **POST /chat/tool-approvals/{id}/reject**（差戻）: rejected + スレッドへ
  system メッセージ「差し戻されました」。**実行はされない** (監査で knowledge
  0 件を突合)
- **UI**: pending をスレッドロード/stream 完了後に取得し、モック .approval-card
  準拠の承認カード (承認して実行 / 差戻 / Inbox で確認 = /approvals 実リンク)。
  実行後は tool メッセージ実描画 + カード消滅。pending 無しは非描画 (Rule 10)
- 登録側 (LLM ループ→pending) は実 LLM が必要なため pytest + コード配線で担保、
  承認/実行/差戻側は実 UI E2E (シードは request_tool_approval と同形)
