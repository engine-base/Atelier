## GAP-014 是正 (2026-08-04) — 法令・運用バックエンド (必須) の実装

> 監査スクリプト: `apps/web/.audit-o01-legal.mjs`（再実行可能・実ジョブ実行+DB 突合+実描画・3 連続 ALL PASS）。
> pytest: `tests/routes/test_platform_jobs.py`（7 件）/ vitest: uc25 に 2 件追加。

モックの「法令・運用バックエンド (必須)」節はプラットフォームジョブの実体と
可視化 API が無く未描画だった。**ジョブの実体から**実装して是正:

- **purge-deleted-accounts** (毎日 0:00 JST / cron `0 15 * * *` UTC):
  T-A-05 退会 (soft-delete + 30 日猶予) が「ハード削除は worker job が処理する」
  と規定しながら worker 不在だったパイプ断絶の解消。退会 30 日経過ユーザーの
  所有 workspace (cascade) → external_uploads (FK restrict) → auth.users
  (public.users へ cascade、comments 等は set null 匿名化) を物理削除。
  猶予中 (30 日未満) と現役は絶対に触らない (pytest + 実操作監査で実証)。
  削除実行は audit `platform.account.purged` に記録 (法定監査証跡は保持)。
- **integrity-check** (毎日 5:00 JST / cron `0 20 * * *` UTC): SQL のみの
  整合性チェック 5 種 — dangling 依存 / AC 不在参照 / モック不在参照 /
  工程-プロジェクト不一致 / 工程担当の越境 (R-T08 系)。検知時は workspace
  owner の承認待ち (approval_inbox type=integrity_alert、pending 中は重複
  通知しない) へ通知。migration `t-d-99ze` (enum + target_type=project)。
- **可視化 API**: GET /cron-platform-jobs (read-only) — 定義 + 実 cron 式 +
  次回時刻 (対応 cron 部分集合のみ計算、非対応は null で偽装しない) +
  最終実行 (cron_run_history 実データ)。
- **UI**: S-O01 に「法令・運用バックエンド 必須」節 (モック group 3a 準拠) —
  ジョブ名/説明/無効化不可・コスト無料・SQL のみタグ/スケジュール/cron 式/
  次回/最終実行。API 未到達時は節ごと非描画 (偽の稼働状況を出さない)。
- 実行経路は Inngest cron (handler + record_run) と単独実行
  `python -m src.services.platform_jobs {purge|integrity}` の 2 つ (どちらも
  同一本体 + cron_run_history 記録)。
