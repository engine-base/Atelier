# ADR-019: ドメイン語彙の二層方針 (DDD は上位層に、実装層は機械検証で統制)

- **Status**: Accepted
- **Date**: 2026-08-16
- **Decider**: 経営者 (チャット合意) + 実装 AI
- **Category**: architecture / process

## 文脈

Atelier は AI 主体で実装されるプロダクトである。開発手法のすり合わせの中で
「DDD (ドメイン駆動設計) をどこまで採用するか」を決める必要があった。

DDD の価値の大半は「大人数の人間チームが共通のメンタルモデルを維持する」ことに
あるが、AI 開発では前提が変わる:

- AI はコードベース全体を短時間で読めるため、共通言語をコード語彙に埋め込む
  伝達コストの削減効果が小さい。AI にとっての共通理解の源は仕様書
  (tickets.json の 3-tier AC / gap-tracker) である。
- フル DDD の重装備 (集約・リポジトリ層・値オブジェクトの儀式的階層) は
  間接参照を増やし、「1 変更で触るファイルが増える = AI の逸脱・バグ機会が増える」
  ため AI 実装ではむしろ有害に働く。
- AI に効くのは散文の設計思想ではなく **機械検証できる制約**
  (型 / スキーマ / テスト / CI ゲート) — 「読んで察する」より「違反したら即死する」。

## 決定

**ドメイン語彙は上位層 (人間が読む層) に置き、実装層は機械検証制約で統制する。**

1. **上位層 = 業務の言葉 (DDD-lite)**
   - 画面 ID (S-E01 等)・tickets.json の受入条件・gap-tracker・openapi の
     summary・コミットメッセージは業務語彙で書く。
   - コードの命名も業務語彙に寄せる (`approve_deliverable` であって
     `update_status_3` ではない — LLM は名前から意図を推論するため事故が減る)。
   - モジュール境界は業務単位 (services/billing, services/meetings, …)。
     `files_changed_predicted` によるタスク境界は「境界づけられたコンテキスト」の
     機械版として機能する。
2. **実装層 = 機械検証制約**
   - 型 (pyright strict / tsc)・スキーマ (openapi 凍結 + 型自動生成)・
     テスト (coverage ≥ 80%)・CI 13 ゲート・RLS 越境試験で統制する。
   - フル DDD の儀式的階層 (集約ルート経由の強制、リポジトリ抽象、
     値オブジェクトの全面採用) は **採用しない**。
3. 本方針は今後の全機能追加に適用する。逸脱 (例: 新しい抽象層の導入) は
   ADR の追記を先行させる。

## 検討した代替案

- **フル DDD 移行**: 現行規模では書き直しコストが利益を上回る。AI 実装との
  相性も悪い (上記)。棄却。
- **命名も含め完全自由 (No-DDD)**: LLM の意図推論を助ける業務語彙の利点まで
  捨てることになる。棄却。

## 影響

- 既存構造は本方針に概ね適合済みのため、コード変更は不要 (本 ADR は現状の
  暗黙合意の明文化)。
- 新機能のレビュー観点に「業務語彙の命名か」「機械検証制約でガードされているか」
  を含める。
