# 増やすときの手順書（machine を増やす / DB の壁を越える）

> **これは「混んでから読む」ものではなく、「混む前に読んでおく」ものです。**
> 実際に必要になったとき、判断ではなく **手順の実行** だけで済むようにしてあります。
>
> 今どこまで余裕があるかは **運営画面 S-T01 の「増やせる余地 (machine 数)」** に
> 常に出ています。推測しないでください。

## いま何が上限か（2026-08-21 時点・実測）

| 上限 | 値 | 決めているもの |
|---|---|---|
| 同時チャット | 1 台 1000 / 2 台 **2000** | アプリの設定（GAP-202 実測） |
| machine 数 | **2 台** | `fly.toml` の `max_machines_running` |
| **DB 接続** | **60**（30 × 2 台） | **ここが 3 台目の壁** |

機械は 1 台 **月 $2.02**（使わない間は自動停止で $0）。**しかし DB はそうではありません。**
全部の機械が同じ Supabase を共有しているので、**接続の方が先に頭打ちになります。**

---

## 段階 1 — 2 台のまま、まだ余裕があるとき

やることはありません。S-T01 の

- 「同時チャット (SSE)」の **順番待ち人数 / 断った回数**
- 「増やせる余地 (machine 数)」

を見て、**順番待ちが日常的に出るようになったら**段階 2 へ。

## 段階 2 — machine を増やす（DB 接続の予算内で）

**所要 5 分。** ただし S-T01 が示す台数まで。既定（直結・1 台 30 接続・予算 60）
では **2 台が上限**なので、この段階は「予算を先に上げた場合」にだけ使えます。

```bash
# 1) fly.toml を編集
#      max_machines_running = 2  →  増やしたい台数
# 2) デプロイ
fly deploy
```

**確認**: S-T01 の「増やせる余地」が `予算超過` になっていないこと。
なっていたら **段階 3 を先にやります**（超えたまま動かすと、負荷がかかった
ときに初めて接続エラーで落ちます）。

## 段階 3 — DB の壁を越える（Supavisor 経由へ切り替える）

3 台目以降に必要。**コード変更は不要です**（GAP-205 で用意済み）。

### やること

1. **Supabase のダッシュボードで確認する**（ここだけは実物を見ないと分かりません）
   - 現在のプランと compute サイズ
   - **直結の接続上限**と、**Supavisor (transaction mode) の接続上限**
   - Supavisor の接続文字列（`...pooler.supabase.com:6543/...`）
2. **環境変数を 3 つ設定する**

   | 変数 | 値 | 意味 |
   |---|---|---|
   | `ATELIER_DB_URL` | Supavisor の接続文字列 | 本体をまとめ役経由にする |
   | `ATELIER_DB_LISTEN_URL` | **直結**の接続文字列 | **押し出し通知だけは直結が必須**（後述） |
   | `ATELIER_DB_POOLER_CONNECTION_BUDGET` | ダッシュボードで確認した上限 | 「何台まで」の計算に使う |

   必要なら `ATELIER_DB_POOLER_MODE=1` で明示もできます（通常は自動判定）。

3. `fly.toml` の `max_machines_running` を増やして `fly deploy`

### なぜ `ATELIER_DB_LISTEN_URL` が要るのか

GAP-202 で入れた「呼び鈴」（`LISTEN/NOTIFY`）は、**Supavisor の transaction mode
では届きません**。接続が毎回別のものに割り当てられるため、待ち受けが維持できない
からです。そのため **待ち受け専用の 1 本だけ直結**を使います。

設定し忘れても落ちません。**押し出しが使えないと自動で判断して、従来のポーリング
（0.25 秒ごと）へ戻ります**。ただし遅くなり、待機人数ぶんの DB 負荷が戻るので、
S-T01 の「チャットの押し出し通知」行が **警告** になります。
**そこを見れば設定漏れに気づけます。**

### 切り替えると自動で変わること

- `ATELIER_DB_URL` に `pooler.supabase.com` か `:6543` が含まれていれば、
  **アプリが自動で pooler モードと判断**します（設定の付け忘れ対策）。
- pooler モードでは **prepared statement を自動で無効化**します。
  transaction mode では毎回別の接続に割り当てられ、前回作った文が
  見つからずに落ちるためです。直結では無効にしません（遅くなるだけなので）。

### 未検証であることの明示

**Supavisor 本体の挙動は実 Supabase でしか検証できません。** ここで検証済みなのは
「prepared statement を無効にした状態で SQL が通ること」までです
（`apps/api/tests/test_scaling_headroom.py` が実 Postgres に対して確認）。

切り替えたら、まず **S-T01 の全行が緑であること**と、**チャットが 1 往復通ること**を
確認してください。

## 段階 4 — それでも足りないとき

| 手 | 効果 | 状態 |
|---|---|---|
| Supabase の compute を上げる | 接続上限・処理能力が上がる | 未実施（費用はダッシュボードで確認） |
| 同時チャットの上限を 1000 から上げる | 実測では 5000 でも配達 p95 77ms | **uvicorn / Fly プロキシ側が未実測**。上げる前にそこを測る |
| 待機中のポーリングを 3 クエリ → 1 に | 保険の再確認が 1/3 に | 未実施 |

## 費用の考え方（正直に）

- **machine**: 1 台 月 $2.02。使わない間は自動停止で $0。**線形に増やせます**
- **Supabase**: 台数とは無関係。**組織単位の月額**で、プランを上げると段階的に増えます。
  **「$2.02 ずつ」ではありません**
- **同時 2000 人までは Fly 側 月 $4 で足ります。** その先は Supabase 側の
  プラン判断が入ります（金額は**ダッシュボードで確認してください** — ここに
  推測の数字は書きません）
