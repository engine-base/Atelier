## 1. エラー監視 — 自前 (実装済 / GAP-182)

外部の監視 SaaS は使わない（経営者判断 2026-08-19）。スタックトレース・URL・
ユーザー ID を外部に出さず、追加費用もかからない。

| 何が | どこに記録されるか | どこで見るか |
|---|---|---|
| API の未捕捉例外 (500) | `public.error_log` (source=`api`) | 運営メニュー > 監査ログ > **エラーログ** |
| 画面 (Next.js) のクラッシュ | 同上 (source=`web`) — `POST /client-errors` 経由 | 同上 |
| バッチ (cron) の失敗 | `public.cron_run_history` | 自動スケジュール画面 > 実行履歴 |

- 秘匿値 (Bearer / API キー / JWT / DB URL / password=… ) は保存前にマスクされる。
- テナントからは読めない (RLS で policy を一切与えていない)。運営 admin のみ。
- 同種は `fingerprint` でまとまり、直近 24h の件数が一覧に出る。
- 運営ヘルスチェック (`GET /admin/health`) に「エラー監視 (自前 / 外部送信なし)」行があり、
  直近 24 時間の件数を返す。

保持期間: 30 日（`purge_old_errors`）。

## 2. 実行経路の可視化 (実装済)

`GET /admin/health` が「誰の費用で何が動いているか」を実データで返す。

| 行 | 何を見ているか |
|---|---|
| AI 実行経路 / 費用の出どころ | relay (本人サブスク) / agent_sdk / API 課金 のどれか (GAP-178) |
| 意味検索 (埋め込み) の経路 | ローカル / Voyage / 利用不可 + 準備状況 (GAP-180) |
| 議事録の文字起こし経路 | ローカル faster-whisper / OpenAI API (GAP-181) |
| ディスパッチャ / Bridge | 接続 Bridge 数・実行中・キュー待ち |
| エラー監視 | 直近 24h のエラー件数 (GAP-182) |

起動時にも `atelier.llm_route` / `atelier.embedding_route` / `atelier.stt_route` の
3 行がログに出る (警告があれば warning レベル)。

## 3. エラー発生時の通知 — メール / Slack (実装済 / GAP-194)

記録するだけでは誰も気づけない。`error-alerts` cron (15 分ごと) が
「新種のエラー」と「増えているエラー」を運営へ送る。

| 仕掛け | 効果 |
|---|---|
| fingerprint 単位の冷却 (既定 60 分) | 同じ不具合で何百通も来ない |
| 前回通知以降の増分だけを伝える | 「また 300 件」ではなく「新たに 12 件」 |
| 1 回の実行で最大 5 件 | 一斉障害でもメール爆撃にならない (残りは次回) |
| warning は既定で送らない | ノイズを増やさない |
| `AlertDeliveryFailed` は通知対象外 | 通知の失敗が次の通知を呼ぶ無限ループを作らない |

**送信先が未設定なら「送ったふり」をしない**。`skipped` として記録し、
`last_notified_at` を進めないので、設定した瞬間に 1 通目がちゃんと届く。
配送失敗も同じ (次回再試行)。Resend の dry-run も成功に数えない。

| 環境変数 | 意味 |
|---|---|
| `ATELIER_ALERT_EMAIL_TO` | 通知先メール (カンマ区切り) |
| `ATELIER_ALERT_SLACK_WEBHOOK_URL` | Slack Incoming Webhook |
| `ATELIER_ALERT_COOLDOWN_MINUTES` | 再通知までの冷却 (既定 60) |
| `ATELIER_ALERT_NOTIFY_WARNINGS` | warning も送るか (既定 false) |
| `ATELIER_ALERT_MAX_PER_RUN` | 1 回の最大送信数 (既定 5) |
| `ATELIER_ALERT_DASHBOARD_URL` | 本文に載せる運営画面 URL |

**通知は最大 15 分遅れる**。`user-schedules` と同じ 15 分間隔に載せてあるため
Fly.io の起床回数 (= 課金) は増えない。即時通知にすると常時起動が必要になり
月額が上がるので、安いほうを選んでいる。画面 (S-T05) にもその旨を表示する。

状態は運営メニュー > 監査ログ > **エラー通知** で確認できる
(通知先が未設定なら赤字で「どこにも通知できていません」と出る)。

## 4. 外形監視 (uptime) — 実装済 / GAP-195

上の 2 つは **サーバーが生きている前提**でしか動かない。Fly.io が完全に落ちたら
自分ではログを書けないので、運営インフラの**外側**から見る目を用意した。

- **どこで動くか**: GitHub Actions (`.github/workflows/uptime.yml`)、15 分ごと
- **費用**: このリポジトリは public なので Actions は無料 (分数無制限)。監視 SaaS の契約なし
- **記録先**: **API を経由せず直接 Supabase** (`public.uptime_checks`)。
  API が落ちているときに API 経由では記録できないため
- **見る場所**: 運営メニュー > 監査ログ > **外形監視**（24h 稼働率 / 停止開始時刻 / 応答時間）

| 状況 | 通知 |
|---|---|
| 稼働中の初回観測 | しない |
| 落ちた / 復旧した | する |
| 落ちたまま | **しない**（6 時間ごとにリマインドのみ） |
| 通知が届かなかった | `notified=false` のまま記録 → 次の判定で黙らない |

1 回のタイムアウトで「落ちた」と決めつけない (3 回試行して全部失敗したときだけ)。

必要な設定 (未設定なら workflow が exit 1 で赤くなる):

| 設定 | 種別 | 例 |
|---|---|---|
| `PROD_DATABASE_URL` | Secret | deploy.yml と共用 |
| `ATELIER_UPTIME_TARGETS` | Variable | `api=https://atelier-api-eb.fly.dev/health,web=https://atelier-web-coral.vercel.app` |
| `ATELIER_ALERT_SLACK_WEBHOOK_URL` / `ATELIER_ALERT_EMAIL_TO` | Secret | GAP-194 と共用 |

GitHub 側の制約 (隠さずに書く): `schedule` は混雑時に遅れる / リポジトリが 60 日
非活性だと自動停止する / Supabase まで落ちた場合はここにも記録が残らない
(その場合は workflow 自体が失敗し、通知は DB を使わない経路で飛ぶ)。
画面は観測が 0 件のとき「異常なし」に見せず「監視が動いていない可能性があります」と出す。

## 6. 容量の実測値 (GAP-197 / GAP-198)

「何人まで同時に使えるか」は推測ではなく、運営画面 (S-T01 プラットフォーム健全性)
の数字で見る。関係する 2 行:

| 行 | 何を見ているか |
|---|---|
| DB 接続プール | 使用中 / 1 台あたり上限 30 · 全台合計 60 / 予算 60 |
| 同時チャット (SSE) | 接続中 / 1 台あたり上限 22 · **混雑でお断りした回数** |

**SSE は張っている間ずっと DB 接続を 1 本掴む**ので、同時チャットの上限は
Fly の `soft_limit` ではなく DB プールで決まる (実測で確認済み)。予備 8 本は
普通の画面操作 (一覧・保存) が詰まらないように残してある。

| | 1 台 | 2 台 (max_machines_running=2) |
|---|---|---|
| 同時チャット | 22 人 | **44 人** |

上限に当たると **黙って遅くなるのではなく** 503 +「ただいま混み合っています」を
その場で返す (実測 0 ms)。断った回数は上の表の行に出るので、
**増やすべきタイミングは数字で分かる**。

44 人を超えて必要になったら Supabase の **Supavisor (transaction pooler)** へ
切り替える。asyncpg では `statement_cache_size=0` が要るため実 Supabase での
検証が前提で、**今は入れていない**。

## 8. 運用コスト (GAP-183 — 実際の料金表で確認)

Fly.io は「マシンが起動している秒数 × VM サイズ」でのみ課金される
(リクエスト数・ユーザー数では増えない)。shared-cpu-1x を 24 時間 365 日動かした場合:

| VM | 月額 |
|---|---|
| 256MB (現行) | $2.02 |
| 512MB | $3.32 |
| 1GB | $5.92 |
| 2GB | $11.11 |

停止中は rootfs ストレージのみ ($0.15/GB/月)。帯域はアジア太平洋の egress $0.04/GB。

自動実行の見張りは **利用者の PC (Bridge) が主**なので運営負担は 0 円。
クラウド側の滑り止め cron は 15 分間隔で、稼働率 約 1/3 = 月 $0.7 程度。
毎分にすると実質 24 時間起動になり $2.02/月 (固定) になる。

## 9. 日々の確認手順

通知 (GAP-194) と外形監視 (GAP-195) が入ったので、**平常時は見に行かなくてよい**。
異常があれば届く。それでも手で見るときは:

1. 運営メニュー > 監査ログ > **エラー通知** — 通知先が設定されているか (赤字が出ていないか)
2. 同 > **外形監視** — 24h 稼働率と最終確認時刻 (観測が止まっていないか)
3. 同 > **エラーログ** を「24 時間」で開き、`kind` と `24h` 列を見る (同じものが増えていないか)
4. `./scripts/check-monitoring.sh` で主要エンドポイントが 200 を返すことを確認
