# テスト・ラダー（L1〜L5）— 「いつ・誰が・どの粒度で」テストを作り、流すかの正本

> 2026-09-02 に本番実走で 5 件の穴（保存先バケット未作成 / AI の無言終了 / Bridge 終了後 90 秒の
> 誤表示 / モード切替の無視 / 退会後もセッション有効）が見つかった。5 件とも **正本に観点が無く、
> 実装が全部終わってから「全体」を対象にテストを書いたため細部が抜けた** のが共通原因。
> このファイルは、その構造を変えるための **全スキル共通の規約**。task-decomposition /
> acceptance-criteria / test-verification / distributed-dev / jit-task-execution / human-grade-qa /
> e2e-journey-walkthrough / architecture-design / feature-decomposition / sprint-planning /
> release-planning が参照する。**ここと矛盾する記述は、ここが勝つ。**

## 1. 原則（3 行）

1. **テストはタスク分解の時点で作る。** 実装が終わってから書かない。1 タスク = その場で観点を出し切る。
2. **粒度は 5 段（L1〜L5）。** 小さい単位で細かく、大きい単位で流れと回帰を見る。どの段も正本（Excel）に載る。
3. **流すのは「揃った瞬間」。** タスク単位は実装者が merge 前に、流れは最後のタスクが merge 前に、Wave / リリース / 全体は締めで。

## 2. 5 段の定義

| 段 | 単位（比喩） | 何を見るか | 正本の置き場 | 作る時点 | 流す時点 / 誰が |
|---|---|---|---|---|---|
| **L1 タスク** | 1 日 | そのタスクが触った画面・API・データの **全要素・全分岐・全エラー・全境界** | `screens/*.md`（画面）/ `sweeps`・技術行（API/DB）/ `ai-runtime-matrix.md`（AI） | task-decomposition（タスクカードと同時） | **実装した本人が merge 前に**、staging で全行 |
| **L2 流れ** | 1 週 | 複数タスクをまたぐ 1 本の業務の流れ（ジャーニー）が最後まで成立するか | `journeys/`（plan.json + README） | task-decomposition（機能の流れごとに、`runnable_after` = 依存タスク ID 群） | **揃えた最後のタスクが merge 前に**（`qa-ladder.py runnable` が自動で示す） |
| **L3 Wave** | 1 か月 | その Wave の L1+L2 を全部 + 前 Wave 以前の回帰（diff） | 同上（Wave タグで抽出） | sprint-planning（Wave 編成時に対象 ID を確定） | Wave 締めで、Wave 責任者 |
| **L4 リリース** | 四半期 | 正本 full（画面別・ジャーニー・RLS・AI 実動・負荷）+ 本番スモーク | 同上 + `prod-smoke.md` | release-planning | リリース前に、リリース責任者。本番はスモークのみ |
| **L5 製品全体** | 1 年 / 大改修 | 全正本の full + 正本自体の鮮度監査（画面取りこぼし・古い期待結果） | 全部 | human-grade-qa test-plan の全面改訂 | 年次 / 大改修前 |

- **L1 は「タスクを見て書く」から細かくなる。** 全体を見て書くと細部が抜ける（2026-09-02 の 5 件）。
- **L2 は「流れを見て書く」から抜けが減る。** 画面 1 枚では出ない（切替の瞬間・組み合わせ・別ロールへの波及）。
- **L3〜L5 は回帰。** 新しく作るのではなく、既にある L1/L2 を締めごとに流し直す。

## 3. 正本の形（Excel で見たときに今のまま整理されていること）

- 画面別 / 技術 / AI の行は **既存の 9 列**に **2 列を足した 11 列**で書く（9 列の旧行も読める）:
  `| ID | 画面 | テスト観点 | テスト項目 | 前提条件 | 操作手順 | 期待結果 | 結果 | 備考 | タスク | 実行条件 |`
  - **タスク** = その行を担当するタスク ID（`T-A-12`）。複数なら `,` 区切り。L1 行は必須。
  - **実行条件** = `L1` / `L2:after=T-A-12,T-U-05` / `L3:wave=W3` / `L4` / `L5`。空欄は L1 扱い。
- ジャーニー（`journeys/plan.json`）は各行に `depends_on`（行の順序）とは別に **`runnable_after`**（タスク ID 群）を持つ。
- Excel は `build_xlsx.py` で **画面ごとのタブ + 「実行計画」タブ（段 × タスク × 実行可否）** に再生成する。手で足さない（鉄則3）。
- tickets.json 側は各タスクに `qa_rows: {"l1": [行 ID…], "l2_flows": [J-xx…]}` を持ち、`qa-ladder.py validate` が **両方向の整合**を機械検査する（片方にしか無い ID は fail）。

## 4. 各段で必ず入れる観点（抜けた 5 類型を構造で潰す）

人間の注意ではなく **観点の列挙で** 潰す。L1 の行を書くとき、以下 G-11〜G-15 を **タスクごとに「該当 / N/A + 理由」** で必ず判定する（空欄禁止）。既存の G-01〜G-10（lessons-learned L-003）に追加。

| ID | 類型 | 2026-09-02 の実例 | L1 で書く行の形 |
|---|---|---|---|
| **G-11** | **外部リソースの実在** | Storage バケットが本番に 1 つも無く、添付・成果物・議事録の保存が全部 502 | 「この機能が触る外部リソース（バケット / キュー / 秘密 / DNS / 外部 API 設定）が **対象環境に存在する**ことを、プロビジョニングコード（migration / IaC）と実環境の両方で確認」。環境ごとに 1 行 |
| **G-12** | **切り替わりの瞬間** | Bridge 終了後 90 秒「接続中」のまま。その間の送信は 3 分無応答 | 状態 A→B の **直後**（0 秒・鮮度窓の内側・期限切れの直前）に操作した行。「B になってしばらく後」だけでは不十分 |
| **G-13** | **機能の組み合わせ** | 実行中の追い足し（後から入った機能）× モード切替（既存機能）で切替が捨てられた | このタスクの機能 × **同時に起きうる既存機能**（実行中・切替・中断・再開・別ロールの操作）を直積で列挙し、1 セル 1 行 |
| **G-14** | **口座状態の波及** | 退会後も発行済み JWT と Bridge トークンが有効 | 退会 / 停止 / 権限変更 / パスワード変更 / 招待取消 の **後に、既存のセッション・トークン・接続・共有リンク・Webhook が全部無効**になる行 |
| **G-15** | **信号なし終了** | CLI が完了信号（result）を出さず exit 0 → 空応答が「完了」 | 外部プロセス / 外部 API / ジョブが **完了信号を出さずに終わる・空を返す・途中で切れる** ケースを成功にしない行。「exit 0 = 成功」を疑う |

加えて全 L1 行の **基本の直積**（既存規約の再掲・省略禁止）: 正常 × 異常（UI/API/データ/復旧の 4 層）× 境界値 × 権限（ロール × 操作）× 状態（0 件 / 大量 / 重複 / 初回 / 2 回目）× 中断・再開。

## 5. 実行環境（staging）

- **L1〜L3 のブラウザ通し・ジャーニー・AI 実動は staging で流す。** ローカルのスタブ環境は単体・契約テストまで。
- **本番は L4 のスモーク（prod-smoke）だけ。** 本番のデータを触る通しはしない。
- staging の **構成は technology-agnostic に決め打ちしない**。`architecture-design` が **本番と同じ migration / deploy / プロビジョニングコードで作れる**ことを条件に決め、`selected-stack.json` の `environments.staging` と ADR に確定させる。**未確定のプロジェクトでは、この決定自体を最初のタスクとして起票する。**
- staging に無いもの（有料の外部プロバイダ等）は **BLOCKED（理由つき）** で残す。fake green にしない。

## 6. 「完了」の定義（機械ゲート）

| 段 | 完了と言える条件 | ゲート |
|---|---|---|
| L1 | そのタスクの `qa_rows.l1` 全行が PASS または理由つき BLOCKED、証拠あり | `qa-ladder.py gate T-x-y`（jit-task-execution STEP 4.5 / PR 前に必須） |
| L2 | `runnable_after` が全て merge 済みの流れが、全行 PASS | 同上（揃えたタスクの gate に自動で含まれる） |
| L3〜L5 | 対象 ID 全行 PASS + `completion_gate.sh` STATUS: 完了 | `qa-coverage.py` / `completion_gate.sh` |

完了系の語（完了 / 完璧 / 一周した / done / 100%）は **ゲートの出力を貼ってから**しか書けない（human-grade-qa 鉄則0.5 と同じ）。

## 7. 既存プロジェクトへの適用（後追い）

- 既に正本がある場合、`qa-ladder.py suggest` が **画面 ID（screen_ids）で行とタスクを機械的に突合**して `タスク` 列の候補を出す。候補は人が確認してから正本に書く（勝手に確定しない）。
- 突合できない行（技術行・横断行）は `T-I-*`（Integration）へ寄せるか、L3 以上として扱う。
- 適用の進み具合は `qa-coverage.py` の「段別」集計に出る（タスク列が空の L1 行数 = 未適用）。

## 8. スキルごとの責務（要約。詳細は各 SKILL.md の「テスト・ラダー」節）

| スキル | 責務 |
|---|---|
| feature-decomposition | 機能ごとに **流れ（ジャーニー候補 J-xx）** を列挙し、機能 ↔ 流れの対応を出す |
| task-decomposition | 各タスクに `qa_rows.l1` を **タスクカードと同時に**書く。G-11〜G-15 を判定。L2 の `runnable_after` を確定 |
| acceptance-criteria | AC の観点に G-11〜G-15 を必須追加（G1〜G4 と同格） |
| architecture-design | staging の定義（本番同一の migration/deploy/プロビジョニング）と **外部リソースのコード化**を Foundation gate に入れる |
| test-verification | 3-tier AC ↔ L1〜L5 の対応、staging 前提の E2E 設計、`qa-ladder.py validate` を CI に |
| distributed-dev | CLAUDE.md（実装パッケージ）に **そのタスクの L1 行と解禁される L2** を逐語で埋める |
| jit-task-execution | STEP 4.5 で L1 全行 + 解禁 L2 を staging で流し、結果を正本に書き戻してから push。gate 未通過で PR 禁止 |
| sprint-planning | Wave 編成時に L3 対象 ID を確定 |
| release-planning | L4（full + 本番スモーク）をリリース手順に固定 |
| human-grade-qa | 段の概念・11 列・実行計画タブ・G-11〜G-15・staging を規約に組み込む。L3〜L5 の実行者 |
| e2e-journey-walkthrough | ジャーニーは L2。`runnable_after` を分母にし、揃った流れから順に流す |
