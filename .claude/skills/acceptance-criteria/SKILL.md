## 🪜 テスト・ラダー（L1〜L5）— このスキルの責務（2026-09-02 追加・必須・省略不可）

> 規約の正本: `.claude/rules/common/test-ladder.md`（ここと矛盾したら規約が勝つ）。
> 由来: 2026-09-02、本番実走で 5 件（保存先バケット未作成 / AI の無言終了 / Bridge 終了後 90 秒の誤表示 /
> モード切替の無視 / 退会後もセッション有効）が出た。5 件とも正本に観点が無く、**実装が全部終わってから
> 「全体」を対象にテストを書いたため細部が抜けた**のが共通原因。テストは **タスク分解の時点で・タスク単位で**
> 作り（L1）、流れ（L2）は揃った瞬間に、Wave / リリース / 全体（L3〜L5）は締めで流す。

### 🔒 恒久ガードレール G5：G-11〜G-15 を AC の必須観点にする（G1〜G4 と同格・省略不可）

UI / API / 状態遷移 / 外部連携を持つ **すべての機能**の AC に、次の 5 観点を **「該当 → AC を書く」か「N/A + 理由」** で必ず置く。空欄は不完全 = 差し戻し。

| ID | 観点 | 悪い例（抜ける） | 良い例（AC として書く） |
|---|---|---|---|
| G-11 | 外部リソースの実在 | 「ファイルを保存できる」 | 「保存先のバケット/キュー/秘密が **対象環境に実在**し、無ければ起動時または最初の利用時に**明示的に失敗**する。プロビジョニングはコード（migration/IaC）で再現できる」 |
| G-12 | 切り替わりの瞬間 | 「Bridge を止めると未接続と表示される」 | 「Bridge を止めた **直後（0 秒）** に接続表示が未接続になり、その間に送った操作は待たされず案内が出る」 |
| G-13 | 機能の組み合わせ | 「実行中に指示を追加できる」「モードを切り替えられる」（別々） | 「実行中に **別のモードで**追加した指示は、今の実行に混ぜず、実行後に**そのモードで**流れる」 |
| G-14 | 口座状態の波及 | 「退会後はサインインできない」 | 「退会の直後、**発行済みの JWT・Bridge トークン・共有リンク・Webhook が全部無効**になり、復活すると再び有効になる」 |
| G-15 | 信号なし終了 | 「実行が終わると結果が出る」 | 「外部プロセス/API が**完了信号を返さずに終わった・空を返した・途中で切れた**場合は失敗として扱い、原因の生メッセージを利用者に出す（exit 0 を成功と決めつけない）」 |

### 段（L1 / L2）を AC に付ける

- 1 タスクで閉じる AC = **L1**。複数タスク・複数ロールをまたぐ AC = **L2**（ジャーニー行になる。`runnable_after` に揃うべきタスクを書く）。
- AC は task-decomposition の `qa_rows` と 1:1 で正本の行になる。**AC に書いたのに正本に無い観点は、存在しないのと同じ**。

## 🔒 恒久ガードレール G1：状態遷移 × 副作用マトリクス（必須・省略不可）

状態遷移を持つ機能（申込/休会/解約/再開/退会/プラン変更/オプション増減/同梱サービス操作など）の AC は
**リストではなくマトリクス**で書く。これを満たさない AC は不完全＝差し戻し対象。

- **行** = その機能の全アクション/遷移（cancel / pause / resume / revert / change / add / remove …）を **1つ残らず**。
- **列** = 各アクションが触れる全副作用サーフェス：
  `DB状態 / 外部課金(サブスク 作成・停止・再開・解約) / 関連サブスク(オプション・同梱サービス) / 入室可否 / UI表示 / 通知 / 返金有無`。
- **全セルを EARS で明示**。該当しないセルは「N/A＋理由」を書く（空欄禁止）。
- **対称性ルール（最重要）**：ある副作用（例「課金を止める／再開する」）を1つの遷移に書いたら、
  **同じリソースの全遷移について同じ副作用の有無を必ず解決**する。
  「cancel は課金停止を書いたが pause/resume の課金が未記載」は **即 FAIL**。
- 外部プロバイダ（決済/本人確認/施錠）への副作用は **「DBがこう変わる」ではなく「プロバイダ側がこうなる」** で書く
  （例：Stripe サブスクが paused / canceled / active になる）。

> 由来：ドリコスの解約だけ課金停止が AC に書かれ、休会/再開の課金制御が漏れて実装・QA を素通りした事故。


## 🔒 恒久ガードレール G4：AC は「描画」ではなく「動作」で書く（必須・省略不可）

**「画面が表示される」「モック構造に一致する」で合格を出せる AC は不完全＝差し戻し対象。**

> 由来: ScoliVio で全チケットに監査記録あり・ユニットテスト200本超が緑・CI全green・
> 12画面のビジュアルパス完了の状態で、実機QAにより**製品バグ30件**（ユーザーが確実に詰むもの7件・
> セキュリティ2件）が出た。原因は実装者の注意不足ではなく **AC が「描画されたか」で合格を出せた**こと。
> AC を変えない限り同じ漏れは必ず再発する。

UI/画面/機能の AC には、以下を**必ず**含める（含まれない AC は不完全）:

| # | 必須AC観点 | 悪い例（描画止まり） | 良い例（動作を検証できる） |
|---|---|---|---|
| 1 | **操作の結果** | 「保存ボタンが表示される」 | 「保存を押すと**DBに反映され、別GETで再取得した一覧に現れる**」 |
| 2 | **到達性** | 「メニューに項目がある」 | 「メニュー項目の href が**実在ルートで、押すと200で表示される**」 |
| 3 | **API結線** | 「一覧APIが200を返す」 | 「related_apis の各エンドポイントが**UIのどの操作から呼ばれるか**が特定できる」 |
| 4 | **値の実在** | 「信頼度列が表示される」 | 「信頼度列に**実データの値が入る**（`—`のまま固定でない）」 |
| 5 | **メッセージの到達** | 「エラー時にメッセージを出す」 | 「未入力で送信すると**その文言が実際に画面に出る**（上流のネイティブ検証に奪われない）」 |
| 6 | **防御の層数** | 「不正値は保存できない」 | 「不正値は **UI/API/DB の3層で拒否**される（各層で個別に検証）」 |
| 7 | **共通要素の影響** | 「タブレットで崩れない」 | 「共通ヘッダを含む**全画面**で `scrollWidth - clientWidth <= 1`」 |
| 8 | **仕様states対応** | （記載なし） | 「仕様の states / transitions が**実装のどこに対応するか**を1対1で示せる」 |

### 「ユニットテストが緑」は上記の代替にならない（構造的理由）
テストランナー（jsdom等）は **(a) ブラウザ標準のフォームバリデーション (b) UI/チャートライブラリの
ポインタイベント (c) mousemove由来のホバー・アクティブ状態 (d) 実レイアウト幅 (e) 実DB制約**
を再現しない。よって**実機で死ぬ実装がユニットテストでは原理的に緑になる**。
実際に「JSで実装した必須検証が `required` 属性に submit を奪われ一度も到達しない」
「チャートの点クリックが発火せず死にボタン」がこれで通過した。

→ AC の Tier3（回帰）には **「実ブラウザで当該操作を実行し結果を確認」** を必ず1行入れる。

### 検証手段まで AC に書く
各 AC に「**どうやって確認するか**」を添える（確認できない AC は書き直す）:
- 実ブラウザで押す / DB照会で突合 / 別GETで再取得 / 上流を故意に壊す / 数値測定（`scrollWidth`等）

類型と検出手段の全体像: [rules/common/lessons-learned.md](../../.claude/rules/common/lessons-learned.md) L-003（G-01〜G-10）

## 🧠 全スキル共通：思考品質基準（必ず守ること）

---

### 1. 出力前の必須内部チェック（ユーザーには見せない）

出力を生成する前に、以下を内部で確認する：

- ユーザーの業界・ドメインに固有の法律・規制・制度を参照したか
- 仮説は「売上を上げたい」のような汎用ゴールではなく、そのドメイン・業務フローに固有の仮説になっているか
- 質問は「はい/いいえ」で終わらず、具体例や選択肢を含む設計になっているか
- 曖昧な発言（複数の解釈が可能な表現）に対して複数の解釈を提示したか
- ステークホルダー全員の視点（承認者・反対する人・実際の利用者）を漏らしていないか

---

### 2. 仮説の品質基準

【仮説】ラベルを使う際は以下の形式に従う：

❌ 悪い仮説：「動作するはず」「うまくいくはず」（検証不能な表現）

✅ 良い仮説の構造：
- テスト可能な具体的な条件を示す
- 入力・操作・期待結果を明確に分ける
- 境界値・異常系を網羅している

---

### 3. 質問設計の基準

質問1つに対して、必要に応じてサブ質問（a, b, c）を設ける。
単一の質問だけでは曖昧さが残る場合は必ずサブ質問に分解する。

---

### 4. ドメインスキャン（出力前に内部実行）

ユーザーの業界・プロジェクト種別を判定し、該当する規制・制度を確認する。
ACに法的要件（個人情報・認証・決済等）が関わる場合は明示する。

---

### 5. 曖昧な発言の複数解釈処理

ユーザーの発言に複数の解釈が可能な場合、解釈を並べて確認する。

---

### 6. ステークホルダーの網羅

「誰が使うか」だけでなく、承認者・反対者・運用者の視点も常に確認する。

---

### 7. 質問保留・打ち合わせ優先ルール（全スキル共通）

クライアントから「質問は打ち合わせで」「後で回答します」などの発言があった場合、即座に質問の送信を停止し、現時点の情報を整理して出力する。

---

### 8. 出力フォーマット厳守（最優先ルール）

**スキルモードで動作している場合、出力の冒頭に会話的な前置きを絶対に含めない。**

各STEPの出力は、テンプレートの最初のMarkdown要素（`#`、`##`、`-`、`|` 等）から直接始める。

❌ **禁止（冒頭に付けない）：** 「ありがとうございます」「了解です」「承知しました」「情報を整理します」などの会話的前置き

✅ **正しい出力：** テンプレートの `##` や `|` から直接開始する

**理由：** スキルの出力は `outputMarkdown` としてDBに保存され、プロジェクト管理ドキュメントとして表示される。

# 受け入れ基準定義スキル

要件・ユーザーストーリーを受け取り、Given/When/Then形式（Gherkin）で受け入れ基準（Acceptance Criteria）を定義する。正常系・異常系・境界値を網羅し、テスト可能で具体的なACを生成する。

**このスキルが解決する問題：**
- 「動作すること」「正しく表示されること」という曖昧な受け入れ基準
- 異常系・境界値が見落とされ、後からバグとして発覚する
- 開発者とQAがACの解釈を共有できておらず、手戻りが発生する

## Gherkin記法のルール

### 基本構造
```gherkin
Given [前提条件: システムの状態・ユーザーの状況]
When  [操作: ユーザーが何をするか]
Then  [期待結果: システムがどう振る舞うか]
And   [追加条件（Given/When/Thenの補足）]
But   [例外条件]
```

### 品質基準
- **具体的な値を使う**：「入力する」ではなく「11文字のメールアドレスを入力する」
- **テスト可能な結果を書く**：「エラーになる」ではなく「「メールアドレスの形式が正しくありません」というエラーメッセージが表示される」
- **1つのACに1つの振る舞い**：複数の振る舞いを1つのACに詰め込まない
- **技術実装を含めない**：「データベースに保存される」ではなく「登録完了画面が表示される」

### 網羅すべきシナリオ
1. **正常系**：ユーザーが期待通りの操作をした場合
2. **異常系**：無効な入力・操作をした場合
3. **境界値**：最大文字数・最小値・上限件数など
4. **権限**：ログイン済み/未ログイン・権限レベル別の動作
5. **状態**：初回/2回目・データあり/なし・有効/無効状態
6. **中断・再開**：多ステップ・状態遷移機能で途中離脱・二重送信・期限切れが起きた場合（横断A）
7. **異常系（4レイヤー）**：UI / API / データ / 復旧 の各層で失敗が起きた場合（横断B）

---

## 🔁 横断的に必須とする2カテゴリ

ACを定義する際、以下の2カテゴリを**横断的関心事**として必ず点検する。機能の種類に応じて、漏れなくACに織り込むこと。

### 横断A: 中断・再開耐性（多ステップ／状態遷移機能で必須）

複数ステップ・状態遷移を伴う機能（登録ウィザード・決済・予約・申請フロー等）では、以下を**必ずAC化する**：

- **中断点** — どのステップで離脱・中断しうるか
- **中断時の状態** — 入力途中データが保持されるか
- **再開導線** — どこから再開できるか
- **冪等性** — 二重送信・重複操作で重複レコード・二重課金・不整合が起きないか
- **未完状態の期限** — 未完了のまま放置された状態がいつ・どう破棄/リセットされるか

→ テンプレートの `### 中断・再開` セクションを使用する。

### 横断B: 異常系・エラー（4レイヤー・全機能で必須）

**すべての機能**で、異常系を以下の4レイヤーに分けてそれぞれ最低1件のACを置く：

- **UI** — 分かりやすいメッセージ／リトライ導線／状態の出し分け
- **API** — 4xx（入力・権限：400/401/403/409 等）／5xx（サーバ：500 等）の応答
- **データ** — 処理失敗時のロールバック／整合性の担保（中途半端な状態を残さない）
- **復旧** — 失敗→停止→復活の流れ、外部依存ダウン時の挙動（データ消失・多重実行を防ぐ）

→ テンプレートの `### 異常系（UI / API / データ / 復旧 の4レイヤー）` セクションを使用する。

## STEP 1: 要件・ユーザーストーリーの確認

**このSTEPでやること：**
入力された要件・ユーザーストーリーを整理し、AC定義に必要な情報を確認する。

**確認項目：**
1. **ユーザーストーリー** — 「〇〇として、〜〜したい。なぜなら〜〜だから」の形式で整理
2. **主要アクター** — 誰がこの機能を使うか（権限レベルも含む）
3. **前提条件** — この機能が動作する前提（ログイン状態・データの存在等）
4. **主要フロー** — 正常系の主なステップ
5. **代替フロー** — 異常系・例外が起きた場合の動作
6. **範囲外（スコープ外）** — この機能でカバーしないこと

**出力形式：**

```
## 要件確認

### ユーザーストーリー
「[アクター]として、[機能]を使いたい。なぜなら[目的]だから。」

### 主要アクター
- プライマリ: [メインで使うユーザー・役割]
- セカンダリ: [補助的に関わるユーザー・システム]

### 前提条件
- [前提1]
- [前提2]

### 主要フロー（正常系）
1. [ステップ1]
2. [ステップ2]
...

### 想定される異常・例外ケース
- [ケース1: 無効な入力]
- [ケース2: 権限エラー]
- [ケース3: 境界値]

### スコープ外
- [この機能でカバーしないこと]

### 不明点・確認が必要な事項
- [不明点1]
- [不明点2]
```

📦 **STEP 1 確認**

要件の整理を確認してください。

- ユーザーストーリーの解釈に誤りはありませんか？
- 想定される異常・例外ケースに見落としはありますか？
- 問題なければ「STEP 2へ」とお知らせください

**※ STEP 2には進まない。ユーザーの確認を待つ。**

## STEP 2: AC（受け入れ基準）の定義

**このSTEPでやること：**
STEP 1の確認内容をもとに、Gherkin形式でACを定義する。

**AC定義のプロセス：**
1. 正常系ACを先に定義（主要フローを網羅）
2. 異常系ACを定義（エラー・バリデーション）
3. 境界値ACを定義（上限・下限・境界）
4. 権限・状態別ACを定義（必要に応じて）
5. **中断・再開ACを定義**（横断A・多ステップ／状態遷移機能では必須。中断点／中断時状態／再開導線／冪等性／未完状態の期限）
6. **異常系（4レイヤー）ACを定義**（横断B・全機能で必須。UI／API／データ／復旧 にそれぞれ最低1件）
7. 各ACにAC番号（AC-001, AC-002...）を付番

**出力形式：**

```
## 受け入れ基準一覧 — [フィーチャー名]

### 正常系

#### AC-001: [AC タイトル]
**概要:** [このACで検証する振る舞いを1文で]

\`\`\`gherkin
Given [前提条件]
When  [ユーザーの操作]
Then  [期待結果]
\`\`\`

---

### 異常系

#### AC-00N: [AC タイトル]
**概要:** [このACで検証する振る舞いを1文で]

\`\`\`gherkin
Given [前提条件]
When  [無効な操作・入力]
Then  [エラーメッセージや動作]
\`\`\`

---

### 境界値

#### AC-00N: [AC タイトル]
\`\`\`gherkin
Given [境界条件の前提]
When  [境界値での操作]
Then  [期待する振る舞い]
\`\`\`

---

### 中断・再開（多ステップ／状態遷移機能のみ）

#### AC-00N: 途中離脱からの再開
\`\`\`gherkin
Given [入力途中で離脱・中断した状態]
When  [再度アクセスする]
Then  [中断点から再開でき、入力済みデータが保持される]
\`\`\`

#### AC-00N: 二重送信での冪等性
\`\`\`gherkin
Given [送信直前の状態]
When  [同一操作を二重に送信する]
```
