## 🔒 恒久ガードレール G3：外部副作用は「実プロバイダ」で検証（モックPASS禁止・必須カテゴリ）

決済(Stripe)/本人確認(eKYC)/施錠(KEYVOX) など外部プロバイダに副作用を出す操作は、**モックでは PASS にしない**。
テスト計画に以下を必須カテゴリとして追加する。

- **Real-Integration Side-Effect（実副作用検証）**：テストモードの **実キー**で実行
  （例 `USE_REAL_STRIPE=1` + sk_test、本人確認は Identity テスト）。
  検証対象は **ローカルDBの行ではなくプロバイダ側の状態そのもの**：
  サブスクが本当に paused/canceled/active になったか、課金が発生/停止したかを実APIで照会して assert。
  プロバイダを実行できないセルは **FAIL/BLOCKED。絶対に PASS にしない**。
- **Provider 制約の境界**：実APIの制約を実値で踏む（例 billing anchor が「作成+1課金間隔」超で拒否される 等）。机上 OK にしない。
- **Webhook 取りこぼし/復旧（中断・再開の外部版）**：イベントを「配信→意図的に落とす」を再現し、
  reconcile/再取得で **最終的にDBがプロバイダ結果へ収束**し、申込中などで固まらないことを検証。
- 状態遷移を持つ機能は **G1 のマトリクス全セル**を実機で1つずつ潰す（cancel だけでなく pause/resume/revert も）。

> 由来：QA がモック Stripe で走り「休会で課金が止まったか」「anchor 制約」を構造的に踏めず、
> 決済失敗・課金継続を本番直前まで検知できなかった事故。


# human-grade-qa

「Claude がユーザのフリをして全機能を触る QA スキル」。実 UI を操作し、データ層まで貫通検証する。

## なぜこのスキルか

実装フェーズで書く単体テスト・契約テストは「コードの仕様適合」を見るが、ユーザが実際に触ると
壊れるパターン（state batching、認証ヘッダ、TZ ズレ、空データ時の UI、上限値、権限不一致）は
**実機を触らないと出てこない**。このスキルは

- ヒトの行動を再現する Chrome 操作（生 DOM・実 cookie・実 token）
- 操作の前後で **DB / API / ストレージ** の整合をチェック
- **正常系だけでなく** 異常系・バリデーション・境界値・権限分岐を網羅
- 全結果を Markdown ログに残し、失敗の再現手順を発行

を 1 セッションで完遂する。

## 鉄則0 — 仕様書なきQAは無効（実行モードの最上位ゲート・絶対）

**full / diff / feature / regression の各実行モードは、テスト仕様書の正本を先に作らないと始めてはいけない。**
過去、「実機検証は走らせたが、正本 `.qa/test-specs/screens/*.md` と 2系統Excel を作らずに『テスト完了』と報告」した
事故が起きた（鉄則3/4 に書いてあっても、フローの手前にゲートが無く飛ばせた）。構造的に潰す:

1. **実行(STEP 3)より前に、必ず STEP 0 で正本を作る。** 対象画面ぶんの `screens/*.md`（9列・ID 3桁）を書き、
   `build_xlsx.py` で **2系統xlsx（クライアント版/エンジニア版）を生成** してからでないと実機操作に進まない。
2. **正本と2系統xlsxが存在しない状態で「テスト完了/PASS/報告」してはならない。** diff/feature の小さなスコープでも
   例外にしない（対象画面が1枚でも `screens/*.md` は1枚作る）。「検証は十分やった」は理由にならない —
   成果物（正本＋xlsx）が無ければ QA は無効。
3. **report 前の必須自己質問（1つでも No なら report 禁止・run は未完(BLOCK)）:**
   - ① 対象の全画面ぶん `.qa/test-specs/screens/*.md` が存在するか？
   - ② `build_xlsx.py` で `.qa/テスト仕様書_クライアント版.xlsx` と `_エンジニア版.xlsx` を **実際に生成** したか？
   - ③ 全TC件数を「クライアント可視 ＋ 技術専用 ＝ 全数」で **件数照合** したか？

4. **仕様書ゲート（機械強制・STEP 3 の直前・blocking）。** ①〜③は散文の自己質問なので飛ばせる。
   結果側には `completion_gate.sh` があるのに仕様側には無く、**粗い仕様のまま実機に入れる穴**が
   空いていた（姉妹スキル e2e-journey-walkthrough で、77画面/140操作のプロジェクトに 38 行の
   計画を書いて実行に入る事故が実際に起きた）。実機に入る前に必ず:

   ```bash
   # 表面積を機械導出 (画面 × 操作 / エンティティ / API ルート)
   python3 <skills>/e2e-journey-walkthrough/scripts/derive_surface.py <repo> \
       -o .qa/e2e-journey/surface.json
   # 仕様書が表面積に対して十分かを検査 (exit 2 なら実機に入ってはならない)
   bash "$SKILL_DIR/scripts/spec_gate.sh" .qa/test-specs .qa/e2e-journey/surface.json
   ```

   `spec_gate.sh` が見るもの: ① 画面ごとの正本の有無 ② **TC 件数がその画面の操作数+5 以上か**
   （鉄則2-8「件数は表面積から導出、目標バンドを先に置かない」の機械化）③ 2系統 xlsx の生成
   ④ 期待結果が実装描写になっていないか（鉄則5 / G-09）⑤ 到達性・空状態・権限・レスポンシブの
   観点が入っているか。**STATUS: 仕様書OK が出るまで実機操作に進んではならない。**

> 実装スキル(jit-task-execution 等)や /code-review から呼ばれた時、他モードへ流用された時も、この鉄則0は最優先で効く。

## 鉄則0.5 — 「完了」の語は completion_gate.sh を通してからしか出せない（機械強制・絶対）

過去、エージェントが本 SKILL の「過大報告禁止（鉄則1-4）」を **読んでいてなお**、散文の自己質問を
すり抜けて「完璧／完了／全て完了」と報告し、実際は **結果列が全部空＝全 TC 未実施（planned=2397/2397）**
だった事故が反復した。散文の歯止め（「自己質問せよ」）は回避できてしまう。だから **機械的な強制ゲート** にする。

### 手順（総括の直前・例外なし）
「完了／完璧／終わった／done／perfect／全て完了／100%／もう大丈夫」等を **1 語でも書く前に**、必ず:

```bash
bash "$SKILL_DIR/scripts/completion_gate.sh" .qa/test-specs   # または state.json のある run-dir
```

- スクリプトが結果列 / state.json を機械集計し `PASS n / BLOCKED m / FAIL f / 未(planned) k / 全 N` と
  `STATUS: 完了` または `STATUS: 未完了（残 k）` を出力する（planned>0 か failed>0 で exit 2）。
- **その出力を報告にそのまま貼る。** そして:
  - `STATUS: 完了`（planned=0 かつ failed=0）でない限り、上記の **完了系の語を報告に出力してはならない**。
  - `STATUS: 未完了` のときは総括を必ず **【未完了（残 k 件）】** と書き、内訳 `PASS n/BLOCKED m/未 k/全 N` を併記する。
  - 「コアは完了」「主要部分は完璧」等の **部分肯定も、同じ文に《全体は未完了・残 k》を併記** しなければ禁止。

### 禁止語（planned>0 の間は出力禁止）
`完了` `完璧` `全部終わった` `全て完了` `やり切った(完了の意味)` `done` `complete` `perfect` `100%` `もう大丈夫`。
これらを STATUS=完了 の裏付けなしに書いた時点で **鉄則違反（捏造報告）** とみなす。

### 結果列の機械判定（曖昧さを残さない）
- 結果列に `PASS`/`完了`/`FIXED` を含む行だけが **passed**。`BLOCKED` は blocked、`FAIL/NG` は failed、
  **空・`未実施`・`要ブラウザ実操作`・`—` は planned（未実行）**。ゲートが機械でこう数える。人間の印象は無効。

### コード監査は PASS の証拠にならない（最重要の落とし穴）
- 「コードを読んで、そのボタンの onClick が実在ルート/実在 API に配線されている」と確認しても、
  それは **結果列を PASS にする根拠にはならない**。それは「配線されている」であって「実際に動いた」ではない。
- 結果列を PASS にできるのは、**実際にその要素を操作し**、証拠（**スクショ / DB 照会 / network**）を残した TC だけ
  （鉄則1）。配線監査だけの TC は **planned のまま**。ゲートがそれを planned と数え、完了主張を弾く。

### 全ボタン実操作の数値追跡（鉄則2 の機械化）
- 各画面の **全ボタン・全リンク・全フォーム・全 select・全トグルを 1 つずつ実際に操作**し、各々を TC 化して
  結果列を埋める。1 つでも未操作の要素が残る画面は、その画面の該当 TC が planned のまま＝ゲートが未完と判定する。
- 「配線監査で DEAD=0 を確認した」は **到達確認と同じ**で、実操作 PASS ではない。実操作して初めて結果列 PASS。

> 自己質問（完了ゲート実行の直前）: 「completion_gate.sh を **実際に走らせて出力を見たか**。STATUS は 完了 か。
> 完了でないのに完了系の語を書こうとしていないか。結果列 PASS はすべて **実操作＋証拠** に裏打ちされているか
> （配線監査だけで PASS にした行は無いか）。」 1 つでも怪しければ **完了と書かず【未完了（残 k）】**。

## 鉄則 — 証拠なき PASS は捏造（最優先・絶対）

このスキルが過去に最悪の事故を起こした原因は **「実機を触っていないのに passed と書いた」** こと。
コードを読んで「動くはず」と思っただけで `passed` にするのは **テスト結果の捏造** であり、
未実装・偽データと同格の最悪の不具合とみなす。これを構造的に防ぐため:

1. **PASS には証拠を必ず添える。** ある TC を `passed` にできるのは、その操作を **実際に実行し**、
   次のいずれかを `evidence` に記録したときだけ:
   - `screenshots`（実機スクリーンショットのパス）
   - `db_checks`（実行した SQL とその結果）
   - `network`（叩いた API のレスポンス / HAR）

   証拠ゼロの `passed` は **スキーマ違反**（`templates/state.schema.json` が拒否）。
2. **「PASS と書く前」の自己質問（毎 TC）:** 「この操作を本当に実行したか？ その証拠はどこにあるか？」
   答えられないなら status は `passed` ではなく `planned`（未実施）。
3. **レポート前に自己監査を必ず通す:** `scripts/audit_evidence.sh <run-dir>` を実行。
   未証明 PASS が 1 件でもあれば run 全体の判定を **BLOCK（信頼不可）** に落とす。
4. **「完了／できた／テスト完璧」は 100% 検証済みのときだけ言う（★過大報告の禁止・絶対）。**
   1 件でも `planned`（未実施）が残る状態で「テスト完了」「機能テスト完了」「完璧に検証した」等と
   **総括してはならない**。ユーザーが «やってないのにできたと言うな» と怒る最大の原因。
   - 報告は必ず **実測の内訳**で書く: `PASS n / BLOCKED m / 未(planned) k / 全 N`。
   - 未が 1 件でもあれば全体ステータスは **「未完了（残 k 件）」**。「コアは完了」等の部分肯定も、
     必ず «全体は未完了・残 k» を同じ文に併記する。
   - `BLOCKED` は «理由と解除条件» を必ず明記（実Stripe/実eKYC/管理web/本番write許可 等）。理由なき BLOCKED 禁止。
   - **目標は planned=0**（全 TC を PASS か 理由付き BLOCKED にする）。planned を残したまま «完了» で締めない。
   - 自己質問（総括の直前）: 「planned は 0 か？ 0 でないのに «完了/できた» と書いていないか？ 実測 n/N を出したか？」
5. **不確実なら FAIL/未実施に倒す。** 「たぶん大丈夫」を `passed` にしない。確証が無いものは
   実行して証拠を取るか、`planned` のまま残す（嘘の合格より正直な未完のほうが遥かに良い）。


## 鉄則2 — 「全画面 × 全要素」を触らずに完了と言うな（★今回の大量漏れの直接原因）

実案件で「主要数画面だけ深く触り、 残りは『ページが開くか(到達確認)』だけで済ませ、 残りは自動テストで
担保と称して **完了/バグ0件** と報告 → 直後にユーザが触って 死にボタン・作成しても反映されない・本番状態で詰む
等を大量発見」という最悪の事故を起こした。 «一部を見て全体を語る» のは捏造PASSと同罪。 構造的に防ぐ:

1. **網羅は「画面」ではなく「インタラクティブ要素」単位。** 各画面の **全ボタン・全リンク・全フォーム送信・
   全タブ・全トグル・全 select** を 1 つずつ **実際に操作**する。 «開いた» は «テストした» ではない。
   到達確認(描画される)だけで passed にしない。 未操作の要素が1つでも残れば、 その画面は `planned`。
2. **一般化の禁止（最重要）。** 「ある作成フォームが通ったから、 同型の他フォームもOK」と推測して
   未実行のまま passed にしてはいけない（実際: 問題作成は通ったが宿題はUUID手入力で失敗＝別物だった）。
   **作成/編集/削除フローは画面ごとに個別に最後まで実行**する。 «representative（代表確認）» は禁止語。
3. **「実装済み/PASS」の定義（これを満たさなければ未実装扱い）。** 画面が描画される・API が 200・自動テスト緑
   «だけ» では実装済みではない。 次の **全部** を満たして初めて実装済み:
   (a) モックにある全要素が存在する (b) ナビ/リンク/ボタンから **UIで到達できる** (c) 全操作要素が
   **実際に動く**（押すと何かが起きる） (d) 作成/更新が **別GET再取得で UI に反映** され DB にも在る。
4. **死にボタン検査を必ず行う。** 各ボタン/リンクについて (i) onClick/href/type=submit 等の **ハンドラがあるか**、
   (ii) それが叩く **API メソッド(POST/PUT/DELETE)が実在するか** を確認。 «ボタンはあるが何も起きない»
   «GETだけで作成APIが無い» を検出する（実際: コース新規/編集/削除・時間帯編集・分析「分析実行」が死にボタンだった）。
5. **「作成→保存」で合格にせず「画面に出るか」まで見る。** create→**別GET/一覧/詳細/生徒側**で表示確認→DB突合
   の貫通で初めて PASS（実際: 問題作成がDB保存されても管理一覧にも生徒側にも出なかった）。
6. **実際の対象環境の状態で検証する。** ローカルの seed 入りDBで通っても **本番(実デプロイ先)の実状態**で
   詰むことがある。 «0/空»（時間帯0件で授業作成不能）・«重複/全半角ゆれ»（第1期生が2つ）・«任意入力の未設定»
   （締切null で予約が必ず失敗）等、 実データ状態とエッジを必ず含める（→ coverage-matrix セクション I・H）。
7. **UI 断線を疑う。** バックエンド(API/サービス)が在るのに **UIから到達/呼び出しできない** デッドコード化を探す
   （実際: コース→動画/小テストのリンク無し、 視聴しても進捗POSTを呼ばない、 結果画面が常に0/0/0%、 自習記録
   フォーム無し、 解説リンク404）。 «全 page ルートを列挙→各々へUIから到達→全操作要素を実クリック→
   主要書込を最後まで→結果がUIに出る» を full モードで必ず実走（coverage-matrix セクション I）。
8. **件数は「表面積から導出」する。 上限も目標値も置かない（★件数を抑えるのは網羅の放棄）。** 1画面のTC数は
   «全インタラクティブ要素 × 全状態 × 全入力境界 × 全エラー経路 × 全ロール × 全データ状態(0/大量/重複)» を
   洗い出した **結果として決まる**。 «各画面30〜40件» のような **目標バンドを先に置くと、 単純画面は水増しされ、
   複雑画面は枠に押し込まれて過小テスト＝漏れる**。 件数は入力ではなく出力。 静的ページは10件未満、 フィルタ＋
   一括操作＋CSV＋ページングを持つ一覧は60〜80件超になって当然。 «数字に合わせて足す/削る» を禁止する。

> 自己質問（report 前）: 「**全画面の全ボタンを1つずつ押したか？** 押していない要素はどれか。 作成系は
> 各画面で個別に最後まで通し、 結果が画面に出るのを見たか。 本番の実状態(0/空/重複)でも確認したか。」
> 1つでも No があれば **完了/PASS と言わない**。 «数画面だけ» で報告するのは鉄則1違反と同じ捏造。

## 鉄則3 — テスト仕様書は「単一の正本」、変更は黙って混ぜず明示改訂（★ドリフト事故の直接原因）

QA 途中でバグ修正や機能追加を重ねるうち、 **仕様書を最初に一度作って終わりにし、 アプリの変化に
合わせて作り直さなかった**ため、 新機能用の別仕様ファイルを途中で継ぎ足す形になり、 «仕様書が途中で
変わった/増えた» とユーザを混乱させた。 一部を見て全体を語るのと同じく、 **正本が複数化・部分化する**のは
事故である。 「100%・漏れなしの仕様を先に出してそれを進める」ものを、 場当たりに足すと信頼を失う。 構造的に防ぐ:

1. **正本は1つ（Single Source of Truth）。** プロジェクトのテスト仕様は **1つの権威ある集合**（マトリクス1冊）に
   集約する。 «主要機能ぶんの仕様» と «新機能ぶんの仕様» が別々の正本として並立する状態を作らない。 部分仕様を
   黙って増やさない。 提出物・参照先・ファイル名は常に1つに収束させる。
2. **マトリクスはソースから決定論的に再生成する（完成物の手書きパッチ禁止）。** 画面別 spec（`screens/*.md`）＋
   実行結果（`results/`）→ ビルドスクリプトで xlsx/CSV を生成、 という **再現可能なパイプライン**にする。 完成 xlsx を
   直接いじらない＝ いつでも同じ結果に再生成でき、 一部が壊れても **ソースから100%復元**できる。
3. **アプリが途中で変わったら、 仕様も «完全な超集合» に作り直す。** 修正/追加のたびに、 その変更を
   **全観点（表示・操作・バリデーション・エラー・境界・セキュリティ・レスポンシブ）で TC 化**し、 既存ぶんと
   統合した **完全版を1冊**出す。 古い正本に新機能を «あとから足す» のではなく、 毎回 **全体を整合させて再生成**する。
4. **変更は黙って混ぜない＝ バージョン＋変更履歴で明示する。** TC 総数が増減したら、 必ず **版（日付/連番）を更新し、
   何を・なぜ 足した/変えたかを changelog に1行残す**。 ユーザから見て «いつのまにか増えた/変わった» を起こさない。
   途中追加は事故ではなく **意図した改訂**として見える化する（report 時にも «前回比 +N件・理由» を1行添える）。
5. **網羅は着手前に確定し、 総数で追跡する。** test-plan 段階で **100%（全画面・全ルート・全動作・全バリデーション・
   全エラー・全セキュリティ）を列挙**し、 総 TC 数を固定。 以後の増分は 4 の改訂として扱う。 «途中で思い出して足す» を
   **設計**で消す（思い出し漏れ自体が test-plan の不備＝鉄則2違反）。
6. **再生成前にソースをバックアップ／版管理する。** spec ソース（`screens/`・`journeys/`・`axes/`）と結果 CSV は
   **再生成の前にコピー/コミット**しておく。 生成パイプラインの事故やファイル消失からでも正本を必ず復元できる状態を保つ。

> 自己質問（仕様書を出す前）: 「**正本は1冊か？** 新機能ぶんを別仕様として並立させていないか。 マトリクスは
> **ソースから再生成**したものか（完成物に手で足していないか）。 前回から TC が増減したなら、 **版と changelog** に
> 理由を書いたか。 ソースはバックアップ済みか。」 1つでも No なら、 その仕様書は **未完**。
>
> 具体的な再生成パイプライン・changelog テンプレ・復旧手順は `references/single-source-of-truth.md`。

## 鉄則4 — 成果物は2系統で出す（クライアント版＝平易／エンジニア版＝証拠）

テスト仕様の最終成果物を **エンジニアの語彙のまま1冊** で出すと、 受注先の **非エンジニア（クライアント）** が
読めない。 «どの画面を開いたか» «死にボタンとは何か» «network/console/Playwright/RLS» 等が分からず、 «とても良いが
人が見るには分かりづらい» と評価される。 そこで成果物は **必ず2系統** に分ける（汎用・どのプロジェクトでも）:

1. **① クライアント版（非エンジニア向け・実画面の操作）。** «人が画面で操作して目視できる挙動» だけを、 **平易な
   日本語** で書く。 専門用語（network / console / Playwright / DB / HTTP コード / RLS / enum / 貫通 / 死にボタン 等）は
   **1語も出さない**。 タブ名は **日本語の画面名**（`home`→ホーム画面）。 列は ID / 画面 / テスト観点 / テスト項目 /
   前提条件 / 操作手順 / 期待結果 / 結果 / 備考。 結果は «完了» 等。 クライアントが確認するのは «実際の操作挙動»。
2. **② エンジニア版（裏取り）。** 全 TC（画面で見えない技術専用軸＝全ルートsweep・RLS・鍵設定・移行スクリプト・
   コード/DB 突合 を含む）＋ **証拠列**（network / console / Playwright spec / DB クエリ / HTTP）。 技術用語OK。

- **クライアント版から外すのは «画面で見えないもの» だけ。** 画面で操作・目視できる挙動は1件も間引かない。
- **用語は言い換える（裏側を混ぜない）。** 例: 「死にボタン」→「ボタンを押すと正しく動作するか」、
  「貫通」→「画面で最後まで確認」、「POST /api/... 200 / Cookie 発行」→「ログインでき次の画面に進む」。
  言い換え表は `references/client-engineer-views.md`。
- **完全性を数値で証明（漏れ0）。** `①画面可視 + ②技術専用 = 全TC` を画面ごとに件数照合して示す。 «クライアントが
  画面で確認できることは1件も抜けていない» を保証する。
- **2系統は同じ正本から決定論的に生成する**（鉄則3）。 手で選り分けると漏れるため、 全TCから **プログラムで
  自動導出**し、 除外は «画面で見えない技術専用» の定義済みパターンのみ。

### ★必須の最終成果物 — 2系統の Excel をスクリプトで生成（HTML/CSV単独は不可）

成果物は **必ず `.xlsx`（1画面=1タブ）を2冊**出す。 md/HTML/CSV «だけ» で終わらせない（過去、 HTML 単独・
1系統のみで納品し «違う» と差し戻された）。 生成は下記スクリプトで **決定論的に** 行う:

```bash
python3 "$SKILL_DIR/scripts/build_xlsx.py" <spec-dir> [out-dir]
#   例: python3 .../scripts/build_xlsx.py .qa/test-specs .qa
#   → .qa/テスト仕様書_クライアント版.xlsx  (画面可視のみ・平易・日本語画面名タブ・結果=完了/空)
#   → .qa/テスト仕様書_エンジニア版.xlsx    (全TC・原文・PASS/BLOCKED/要実走 色分け・概要タブ)
# openpyxl 未導入なら: pip3 install --break-system-packages openpyxl
```

- **納品時は必ず両 .xlsx を出す**（クライアント版がタブ別・専門用語ゼロ・結果列付きか確認）。
- 実行結果がある場合も **screens/*.md の結果列を正**として同スクリプトで再生成する（鉄則3）。
- CSV(`render_matrix.sh`)は補助。 **最終納品は xlsx 2系統が既定**。

**build_xlsx.py の入力フォーマット（外すと「screens/*.md が見つかりません」で空生成・厳守）:**
- 置き場: `<spec-dir>/screens/*.md`（例 `.qa/test-specs/screens/S1-....md`）。`build_xlsx.py .qa/test-specs .qa` で呼ぶ。
- 各ファイル先頭行: `# <ID> <日本語画面名> 画面別...`（例 `# S1 生徒-就職-準備期 画面別テスト仕様書`）。
- 本文は9列表: `| ID | 画面 | テスト観点 | テスト項目 | 前提条件 | 操作手順 | 期待結果 | 結果 | 備考 |`。
- **行IDは必ず3桁連番** `S1-001`。**`S1-01`（2桁）は正規表現 `\d{3}` に当たらず行が0件でスキップされ、"見つかりません" になる**（実際に踏んだ罠）。技術専用spec は `T-001` 等。
- 結果列に `PASS`/`完了`/`FIXED` を含めると「完了」判定。`BLOCKED`/`FAIL`/空は未完扱い。
- 生成後、ログの「クライアント可視N件 ＋ 技術専用M件 ＝ 全数」を必ず確認（件数照合＝完全性の証明）。

> 自己質問（納品前）: 「**xlsx を2冊（クライアント版/エンジニア版）** 出したか（HTML/CSVだけで済ませていないか）。
> クライアント版に **専門用語が1語でも残っていないか**。 タブ名は **日本語の画面名** か。
> 画面で見える挙動を **間引いていないか**（件数照合した）。 裏取り（証拠）は **②に分離**できているか。」

## 鉄則5 — 期待結果は「要件/意図」から書く。 «実装の現状» を期待値にするとバグを正常と追認する（★実バグ見逃しの直接原因）

«徹底検証して 1977 件 検証OK» と報告した後、 本番で «予約一覧に生のタイムスタンプ `2026-06-20T09:44:18.911Z` が出る»
«「授業内テスト問題」ボタンが動画フォームに飛ぶ» 等の **明白なバグが発覚** した。 しかも該当 TC は仕様書に在り、
**症状を目視・記録した上で「検証OK」にしていた**。 原因は捏造でも網羅漏れでもない — **期待結果を «実装がやっていること»
から書いていた**ためだ（「ISO 文字列がそのまま表示」「4枚とも同一 href へ遷移」）。 これでは «コードはコード通りに動く»
という **トートロジー** になり、 テストは **バグを「正常」として追認** する。 これは捏造 PASS より気づきにくく危険。 構造的に防ぐ:

1. **期待結果は «独立した正解源（オラクル）» から導く。** 要件・仕様・モック/デザイン・ユーザーの意図＝«こうあるべき»
   から書く。 **実装を読んで/動かして観測した挙動を期待結果にしてはいけない**（順序が逆＝必ず PASS する）。
   - 嗅ぎ分け: 期待結果が «現状のコードの説明» に読めたら書き方を間違えている。
     «ISO 文字列がそのまま表示» «同一 href へ遷移» «orderBy 無し→DB 物理順» は実装描写。
     正しくは «日時は『M月D日 HH:MM』等の読める形に整形» «各ボタンは対応する種別/画面へ遷移» と **あるべき姿**で書く。
2. **«現状記録(as-is)» は PASS ではない。** コードの挙動を観測・記録するのは備考としては可。 だが期待結果＝as-is にした
   TC を 検証OK にしてはいけない。 独立要件と一致して初めて PASS、 一致しなければ **FAIL（バグ）**。
3. **判定保留は «未検証»。** 「意図通りか確認」「仕様確認」「挙動を記録」「?」が残る TC は 検証OK にしない。 要件に照らして
   決着させるか、 未確定として **ユーザー/クライアントに確認**する。 保留のまま緑にするのは鉄則1（証拠なき PASS）の親戚。
4. **重大度ロンダリングの禁止。** 利用者の目に出る不具合（生タイムスタンプ・誤遷移・0/0/0 表示・崩れ）を «MEDIUM/可読性/メモ»
   と貼って通さない。 重大度は **優先度** を決めるだけで、 **PASS/FAIL を動かさない**。 ユーザーが «これ正常？» と聞く類は FAIL。
5. **到達性 ≠ 遷移先の正しさ。** 「リンクが実在ルートに解決する（死にリンクでない）」は必要条件だが十分条件ではない。
   各リンク/ボタンは **正しい遷移先** へ、 **正しい文脈（種別/パラメタ）** を持って遷移するかまで、 意図に照らして判定する。
6. **正解源が無い時の埋め方。** 書かれた仕様が無ければ、 モック/デザイン（鉄則2 のモック対比）・機能の目的・一般的 UX
   （日付は人間可読、 «テスト問題» ボタンはテスト編集を開く 等）から **あるべき姿** を導く。 それでも曖昧なら «要確認» として
   ユーザーに上げる — **実装に合わせて緑にしない**。

> 自己質問（PASS にする前）: 「この期待結果は **要件/意図から** 書いたか、 それとも **コードを見て** 書いたか。
> «現状はこう» を期待値にしていないか。 «意図通りか確認/メモ» のまま緑にしていないか。 遷移先は «実在» だけでなく
> «正しい先か» を見たか。 利用者が見て違和感のある表示を «MEDIUM» で逃がしていないか。」 1つでも怪しければ **FAIL か未確認**。

## 鉄則6 — 「実機でしか出ない10類型」を毎runで狙い撃つ（★30件検出の実績）

ScoliVio QA full run（246TC）で製品バグ**30件**を検出した。うちユーザーが確実に詰むもの7件・
セキュリティ2件。**全チケットに監査記録があり、ユニットテスト200本超が緑、CI 8ゲート全green、
12画面のビジュアルパス完了済み**の状態でこれだけ出た。

つまり **「描画される/テストが緑」は「動く」の証明にならない**。以下10類型は
[rules/common/lessons-learned.md](../../rules/common/lessons-learned.md) L-003（検証ギャップ図鑑）
に詳細があり、**各runで必ず狙い撃ちする**。

| ID | 類型 | QAでの狙い撃ち方（これをやらないと絶対に出ない） |
|---|---|---|
| G-01 | **描画≠動作**（死にボタン） | 全操作要素を**実ブラウザで実際に押す**。jsdomはネイティブ検証・チャートのポインタイベント・mousemoveを再現しないので、ユニットテストは緑のまま実機で死ぬ |
| G-02 | **単一防御層** | **上流を故意に壊す**（routeで禁止データを返す・不正値をAPIに直投入）。正常系では永久に表面化しない |
| G-03 | **UI断線 / Dead API** | `related_apis` の各エンドポイントが**UIのどの操作から呼ばれるか**を突合。呼び出しが無いAPIを列挙 |
| G-04 | **リンク404 / 孤立画面** | ナビ/カードの**href集合 ⇔ 実在ルート集合**を機械照合＋実機で全項目を開く |
| G-05 | **共通シェルの1画面検証** | 共通ヘッダ/ナビを含む**全画面**でレスポンシブを**数値測定**（`scrollWidth - clientWidth`）。1画面OKで済ませない |
| G-06 | **仕様と実装のドリフト** | 仕様JSON（states/related_apis/transitions/policies）と実装を**実機に入る前に機械突合**し欠落を一覧化 |
| G-07 | **列見出しだけ** | 見出しではなく**セルの値**を見る。実データでも `—`/空が変わらない列は未実装 |
| G-08 | **到達しないメッセージ** | 実装されたエラーメッセージ・分岐を**1つずつ実機で出す**。出せないものはデッドコード |
| G-09 | **期待結果を実装から書く** | 鉄則5（既存）。期待値は仕様・モック・要件から |
| G-10 | **QA自身の副作用・誤判定** | 破壊的操作はQAが作ったデータに限定。既存を変えるなら**変更前を記録して`finally`で復帰**。FAILは製品バグ/テスト誤りを切り分け、**記録を分離** |

### 実行順序（この順でやると効率が最大化する）
1. **静的突合を先に**（G-06/G-03/G-04）: 仕様JSON ⇔ 実装、related_apis ⇔ UI呼び出し、href ⇔ 実在ルート。
   ブラウザ不要で数分。ここで欠落が大量に出るので、**実機に入る前に修正する**（1画面ずつ実機で発見すると数十倍遅い）
2. **実機で全要素を押す**（G-01/G-07/G-08）: 押した結果まで見る。値・メッセージ・遷移
3. **故意に壊す**（G-02）: routeで500/禁止データ、DBへ不正値の直INSERT（トランザクションでロールバック）
4. **共通シェルを全画面で数値測定**（G-05）
5. **FAILの切り分け**（G-10）: プローブ（軽量スペック）で実挙動を確認してから製品バグと断定する

### 自己質問（各画面の実機実行を終える前）
- 「この画面の**全ボタンを実際に押したか**。押した結果を見たか」（G-01）
- 「`—`/空のセルは**実データでもそうなのか**、繋がっていないのか」（G-07）
- 「仕様の states / transitions / related_apis を**全部**実装に対応付けたか」（G-06）
- 「『起きてはいけない』事項を**上流を壊して**確認したか」（G-02）
- 「FAILを製品バグと断定する前に**実挙動をプローブで確認**したか」（G-10）

## test-plan モード (実装前)

### 起動条件

`task-decomposition` 完了直後、または「テスト仕様書を作って」「実装前にテスト設計したい」「画面別のテストケースを作って」「QA 計画書を作って」「TDD 用のテスト設計」「実装する前にテストを完璧に」のキーワードで起動。

### このモードの目的

**実装前**に、開発者が「何を満たせば完成か」を一意に決められる完璧なテスト仕様書を作る。実機操作はしない (機能がまだ無いため)。実装期間中、開発者はこの仕様書を満たすようにコードを書く (TDD 風)。

### 5軸出力

| 軸 | 単位 | 件数目安 | 出力 path | 中身 |
|---|---|---:|---|---|
| ① 画面別テスト仕様書 | 1画面 = 1ファイル | モック画面数分 | `.qa/test-specs/screens/<screen>.md` | 表示 / バリデーション / インタラクション / 視覚回帰 / a11y / レスポンシブ / エラー |
| ② ユーザージャーニー | 1フロー = 1ファイル | 10-25件 | `.qa/test-specs/journeys/<flow>.md` | 実ユーザー操作の連続ステップ + 各ステップ証拠基準 |
| ③ 権限マトリクス | 1冊統合 | 1件 | `.qa/test-specs/rls-matrix.md` | 全テーブル × ロール × 操作 のマトリクス |
| ④ クリーン環境/初期構築 ★必須 | 1冊統合 | 1件以上 | `.qa/test-specs/zero-state.md` | 空DB起動 / 初回ブートストラップ / 0→初回登録→ログイン貫通 / seed健全性（coverage-matrix H・H-seed）|
| ⑤ モック忠実性・導線・実操作 ★必須 | 1冊統合 | 1件 | `.qa/test-specs/mock-fidelity.md` | **モックを実レンダリングして**画面⇔モックの要素照合（**要素名だけでなく主要レイアウト領域=ペイン/サイドバー/パネル/セクションが全て存在するか**。領域丸ごと欠落は即FAIL）/ ナビ項目一致 / 全ルート到達性(孤立ゼロ) / 全ボタン実クリック / 登録・編集・CSVアップロード実行（coverage-matrix I）|
| ⑥ 負荷・スケール・容量 ★必須 | 1冊統合 | 1件 | `.qa/test-specs/scale-capacity.md` | スケール前提(想定ユーザー/テナント/レコード/同時実行) / N倍シーディング計画 / 並行負荷シナリオ+閾値(p95/エラー率) / クエリEXPLAIN / 上限到達時の挙動 / 規模・並行下の整合（coverage-matrix L）|
| ⑦ AI実動マトリクス ★AI実装時必須 | 1冊統合 | 1件 | `.qa/test-specs/ai-runtime-matrix.md` | プロバイダー×ツール×出力×状態の直積（第10軸・実キー実走前提。fake green は AI 検証に数えない）|
| 追加 | traceability | 1件 | `.qa/test-specs/traceability.json` | 画面/フロー ↔ dev_features ↔ tickets リンク |

> ④ は「seed済みDBでは検出できないバグ(初期構築/seed欠落)」、 ⑤ は「単体/契約テストでは検出できないバグ
> (作っていないボタン/タブ/列、 ナビ未配線の孤立画面、 モック乖離、 押せない操作)」、 ⑥ は「少データ・1ユーザーでは
> 検出できないバグ(スケール劣化/N+1/ページング崩れ/上限未定義/並行整合崩れ)」を捕まえる**専用軸**。
> いずれも «部品を見るテスト» の死角で、 実プロジェクトで本番事故になった。 必ず別建てで起こす。

### test-plan モード STEP

```
STEP 1: 入力確認 (feature-decomposition 出力 path / モック path / RLS ポリシー)
STEP 2: 画面別仕様書ドラフト (全画面分一気に / 各画面の表面積ぶん＝件数は導出・上限/目標なし / 各画面で対応モックと要素照合)
STEP 3: ユーザージャーニー設計 (主要フロー 10-25 件)
STEP 3.5: クリーン環境/初期構築ジャーニー設計 (0状態・seed健全性 / coverage-matrix H)
STEP 3.6: モック忠実性・導線・実操作の点検表設計 (全画面×モック要素 / 全ルート到達性 / coverage-matrix I)
STEP 3.7: 負荷・スケール・容量計画 (スケール前提宣言 / シーディング・並行負荷・閾値・上限挙動 / coverage-matrix L)
STEP 4: RLS マトリクス統合
STEP 5: traceability.json + 出力まとめ
```

### test-plan モードの DoD

- 全画面に対し test-spec MD が存在
- 全ジャーニーに対し journey MD が存在
- **クリーン環境/初期構築 (zero-state.md) が存在し、 空DB起動・初回ブートストラップ・0→初回登録→ログイン貫通・seed健全性 を網羅**
- **モック忠実性 (mock-fidelity.md) が存在し、 全画面のモック要素照合・ナビ項目一致・全ルート到達性(孤立ゼロ)・全操作要素・主要書込フロー を網羅**
- **負荷・スケール・容量 (scale-capacity.md) が存在し、 スケール前提の数値宣言・N倍シーディング計画・並行負荷+閾値(p95/エラー率)・クエリEXPLAIN・上限到達時の挙動・規模/並行下の整合 を網羅**
- **AI 実装がある場合、AI実動マトリクス (ai-runtime-matrix.md) が存在し、プロバイダー/tool/出力/状態の棚卸し＋行列を網羅**
- RLS マトリクス全テーブル網羅
- traceability.json で 画面 ↔ dev_features ↔ tickets が双方向リンク
- 実装者が読んで「何を作れば PASS か」が一意に決まる粒度

### 実装期間中の運用

- 実装者は test-spec MD を見ながらコードを書く
- 各 test_id が PASS する実装を目指す
- 仕様変更時は test-spec MD を先に更新 → 実装更新

### 実装完了後 = full / diff モードへ

実装完了後、本 skill を再度起動し **full** (全体) / **diff** (PR 変更分) / **feature** (指定機能) モードのいずれかで、test-spec MD を 1 件ずつ実機で潰す。証拠主義 (screenshot / DB check / network) は全モード共通。

ユーザ発話に応じてモードを自動判定。曖昧なら 1 行で聞く。

## 出力先と 3 形式の正本

**state.json が唯一の正本**。md / html はそこから派生。

- `*.md` — 人間可読（PR / Slack 用テキスト）

これにより「どの TC が済んでいるか」「何が失敗しているか」がいつでも機械でも人間でも確認できる。
実行中も TC 完了ごとに `state.json` をアトミックに書き換えるため、
別エージェント / ユーザが任意のタイミングで進捗を読める。

プロジェクトごとに `<project>/.qa/` に保存:

## 5 STEP プロセス

> **STEP 0（仕様書ゲート・鉄則0）を必ず通ってから実機実行(STEP 3)に入る。** これを飛ばした run は無効。

### STEP 0 — テスト仕様書の正本を作る（実行前・スキップ厳禁ゲート）

full/diff/feature/regression のどのモードでも、**実機操作(STEP 3)の前に必ず**:
1. 対象画面を列挙し、各画面 `.qa/test-specs/screens/<ID>-<screen>.md` を **9列・ID3桁** で作る（フォーマットは鉄則4参照）。
   - diff/feature でも対象画面ぶんは作る。技術専用(ルート/認証/DB/契約)は `T-001` 等の別 spec に分ける。
   - 期待結果は要件/意図から書く（鉄則5）。結果列は最初 空 or `planned`。
2. `python3 "$SKILL_DIR/scripts/build_xlsx.py" .qa/test-specs .qa` で **2系統xlsx を生成**（クライアント版/エンジニア版）。
3. 生成ログの件数（クライアント可視 ＋ 技術専用 ＝ 全数）を確認し、正本が1冊に収束していること（鉄則3）を確かめる。

**この3つが揃うまで STEP 3(実機実行) に進んではいけない。** 実行後は screens/*.md の「結果」列を PASS/FAIL/BLOCKED に更新し、
同スクリプトで xlsx を **再生成**する（完成物の手打ち禁止・鉄則3）。

### STEP 1 — プロジェクトをスキャンする

スキャンせずに勘で計画を書かない。**実物 を 読む**。

スキャン項目（自動）:
- `scripts/scan_project.sh` で：
  - `package.json` / `pyproject.toml` / `Cargo.toml` 等の dev script を抽出
  - フレームワーク種別（Next.js / Vite + React / FastAPI / Rails 等）を推定
  - ルーティングテーブル列挙（`src/router/*`, `pages/*`, `app/*`, `routes/*`）
  - API エンドポイント列挙（`api/*`, `routes/*.py`, `handlers/*.go`）
  - 認証実装の有無（auth middleware の検出）
  - DB スキーマ・マイグレーション（`migrations/*`, `prisma/schema.prisma`）
  - 環境変数（`.env*` の key だけ列挙、値は読まない）
- 既存 `.qa/runs/` から **過去の失敗** を学ぶ
- 既存 E2E ファイル（`tests/e2e/*` / `cypress/*` / `playwright/*`）があれば取り込む

スキャン結果は `.qa/plans/<plan>.md` の冒頭にサマリで貼る。

### STEP 1.5 — 調査して自分の前提を更新する（必須）

スキャンで「何を使っているか」が分かったら、**「それで何が壊れやすいか」を外部知識で補う**。
トレーニングデータの記憶で計画を書かない。

調査ソース（優先順）:

1. **Context7 MCP**（`mcp__context7__*`）— ライブラリ / フレームワーク公式ドキュメント
2. **WebSearch** — 最新 breaking change / 既知 Issue / CVE
3. **WebFetch** — GitHub Releases / Changelog を直読
4. **gh search code / repos** — 同じ組合せの実装例・テスト例
5. **既存 `.qa/runs/*/failures.md`** — 同プロジェクト過去 FAIL

最低でも以下を調査:

- 検出したフレームワーク × **実バージョン**（lock ファイルで確定）の breaking change と既知バグ
- 認証ライブラリの落とし穴
- DB / ORM のバージョン固有挙動
- **ドメイン推定**（医療 / 教育 / 金融 / EC / SaaS / AI 等）→ ドメイン固有の規制・典型バグを追加カテゴリに

結果は `.qa/plans/<plan>/research.md` に保存し、計画書から参照する。
詳細は `references/research-and-adapt.md`。

### STEP 2 — テスト計画書を書く（マークダウン）

**1 シート = 1 画面**。 画面ごとに `feature-specs/F-NN-<screen>.md` を作り、
各画面を **9 列フォーマット** の表で書く:

```
ID | 画面 | テスト観点 | テスト項目 | 前提条件 | 操作手順 | 期待結果 | 結果 | 備考
```

#### 粒度基準（最重要 — ここが弱いと QA の意味がない）

実プロジェクトで人手運用していた実テスト仕様書 `references/example-spec/inventory-app-test-spec.md`
が **採用すべき粒度感の参考**（細かさのレベルを掴むため）。 まず必ず読む。
※ そこが各画面30〜40件なのは **そのアプリの表面積の結果** であって、 **目標値でも上限でもない**（鉄則2-8）。
画面ごとに件数は変わる — 単純画面は少なく、 複雑画面は多くなって当然。

「画面が表示される / データが正しい」だけの粗い TC では不十分。
`references/coverage-matrix.md` の画面タイプ別チェック（入力フォーム / 一覧 / 詳細 / 認証 /
**マルチターン・状態継続** / 共通）を **全フィールド・全列・全ボタン・全ターンに展開** し、
**その画面の表面積ぶん（件数は導出・上限なし）** を出す。
特に以下は省略しがちなので必ず入れる:

- **入力初期値**: 各フィールドの Placeholder 文言・各 select/radio の初期選択（フィールド数だけ TC）
- **バリデーション**: フィールド × ルール（未入力でボタン無効 / 型 / 重複 / 全角不可 / 最大長 200 字）
- **一覧**: 並び順・各列のタグ配色・件数表示・ページネーション端（1 ページ目で「前へ」非表示等）・
  検索（条件ごと・複数条件・0 件・クリア）・CSV（ファイル名形式・列構成・文字コード）
- **詳細**: 一覧クリック値と各項目が一致・更新履歴ハイライト
- **戻る**: 入力なし→遷移 / 入力あり→リセットして遷移 の 2 本
- **登録/更新の成功フローを段ごとに**: DB 保存→（招待メール）→リセット→遷移→完了アラート/ポップアップ
- **権限**: 権限なしで画面を開く→一覧へリダイレクト・編集/承認ボタン非表示
- **エラーハンドリング**: API（接続失敗 / ネットワーク / レートリミット）→ アラート
- **レスポンシブ**: 横/縦スクロール（ヘッダー固定）・高さ幅追従
- **★マルチターン・状態継続（ステートフル機能では必須）**: チャット / ウィザード / 複数ステップ
  フォーム / カート / 下書きなど **状態を持つ機能には必ず「3 ターン以上の継続」を入れる**。
  「1 リクエスト＝1 レスポンス」の単発テストでは状態継続バグは **原理的に検出できない**。
  ① 作成→「続けて/進めて」で前の文脈を保持するか ② 仮 ID→実 ID 発番後も会話/状態が続くか
  ③ 再オープンで状態が復元され継続できるか ④ 画面 A の入力が画面 B に反映されるか
  ⑤ リロード/別タブで状態が生きるか。 詳細は coverage-matrix セクション F。
- **★入力の尊重（引き継ぎデータを無視・再質問しないか）**: フォーム/前画面/前ステップで
  **既に渡した情報を、 受け取り側（次画面・AI・次ステップ）が無視して聞き直す/取得し直す**のは
  UX 崩壊。 「与えた ID/値が tool 引数・API リクエスト・作成レコードでそのまま使われたか」を
  **実際の呼び出し内容で**確認する（「正しい応答が返った」だけでは偶然一致を排除できない）。
  AI/LLM など非決定な相手は **2〜3 サンプル**で「毎回 検索系（list_xxx）を呼ばず与えた値を使う」
  一貫性を見る。

詳しいスキーマと網羅マトリクスは `references/test-plan-format.md` と
`references/coverage-matrix.md` を読む。

**テスト観点（必ず展開する）**: 画面表示 / 入力フォーム（初期値）/ バリデーション / 検索機能 /
テーブル表示 / ページネーション / CSV / 登録・編集 / 詳細表示 / 戻る / 権限 / エラーハンドリング /
レスポンシブ / **マルチターン・状態継続** / **層またぎ整合（整合性）** / **クリーン環境・0状態・初期構築・seed健全性**。
各画面で「該当する観点を全部・各要素に 1 行ずつ」起こす。

- **★層またぎ・統合整合（取りこぼし高リスク・必ず入れる）**: 単一画面を眺めるだけでは出ない、
  «コードを横断して初めて分かる» バグ群。 `references/coverage-matrix.md` セクション G 参照:
  ① **BE↔FE の enum/ラベル整合**（API が受ける status と画面のフィルタ選択肢が一致するか）
  ② **ルート登録の実在**（ハンドラがあっても route 未登録で 404 にならないか＝全エンドポイントを実際に叩く）
  ③ **ナビ全リンクを param 無しで開く**（サイドバー/メニューの全項目を ?id 等なしで開いて落ちないか）
  ④ **リロード/セッション永続**（各画面で F5 リロードしてログアウトに飛ばないか・状態が残るか）
  ⑤ **一覧フィルタが実際に絞るか**（各フィルタ値で件数・中身が変わるか、エラーにならないか）
  ⑥ **作成→別 GET 再取得→DB 突合**（作った値が一覧/詳細/DB に正しく出るか。作成レスポンスだけで PASS にしない）
  ⑦ **集計値 vs DB 実数**（ダッシュボード等の数字を `select count(*)` と突き合わせ、内訳合計＝総数か）
  ⑧ **マイグレーション適用後の列/制約存在**（`\d table` で新カラム・CHECK・index が実在するか）

- **★クリーン環境・0状態・初期構築（seed済みDBでは原理的に検出不能・必ず別建て）**: `references/coverage-matrix.md`
  セクション H・H-seed 参照。 «既存/汚れたDBでは永遠に通り、 fresh でだけ壊れる» バグ群。 既存データ前提の
  ②ジャーニーとは**別軸**で、 **0（空DB）からの通しを必ず 1 本以上**起こす:
  ① **空DB起動**（全テーブル0件で開く・主要APIを叩く → 500/throw で死なず、 空UI/200/適切な4xx か）
  ② **空での認証拒否**（データ0件で各ログイン → 例外でなく適切に拒否 403/401 か）
  ③ **初回ブートストラップ**（最初の管理者作成 → ログイン成立。 「Auth＋権限テーブル」等の**二重要件**が成立するか）
  ④ **0→初回登録の貫通**（管理者で親(期生等)→子(学生)を実導線/CSVテンプレ DL→記入→取込で作成 → 払い出された
     **デフォルトPW**で当の学生がログイン 200 → 主要画面/API が空〜最小データで動く）
  ⑤ **seed/fixture 健全性**（**全 TRUNCATE → seed のみ実行（手動補正なし）→ 素でログイン成立** するか。
     seed が必須項目=ログインPW等を落としていないか実値で確認。 ＝今回の「seedがPW未設定」型バグを捕まえる）
  ⑥ **認証モデルの明示確認**（signup の有効/無効、 PW の出所＝自動採番/手入力 を実装で確認し計画に明記）

> 自己点検: 1 画面が 10 項目未満なら粒度不足。 ステートフル機能なのに「3 ターン以上の継続」TC が
> 1 件も無ければ重大な抜け。 **0状態/初期構築ジャーニーと「fresh seed で素にログイン成立」TC が無ければ重大な抜け**
> （seed済みDBで通っても fresh で壊れる型を見逃す）。 coverage-matrix の末尾チェックリストで確認する。

計画書ができたら **ユーザに見せて承認を取る**。承認なしに実行しない。

承認ゲートの具体的やりとり:

1. `test-plan.md` をユーザに提示し、1 行サマリで確認:
   「計 X ケース（P0:a / P1:b / P2:c）、想定 hh:mm、ヒト依頼 N 件。これで実行 OK？」
2. ユーザが「修正して」と言ったら計画を直して再提示。**実機操作は一切しない**
3. 「OK」「進めて」が来た時点で `plan.json` を `runs/<run-id>/state.json` にコピーし `status=approved` → `in_progress`

### STEP 3 — 実行する（実機で 1 件ずつ）

`references/workflow.md` のフローに従う。要約:

1. dev サーバの起動状態確認（必要なら `scripts/start_dev.sh`）
2. テストデータ準備（fixture が無ければ作る／既存を再利用）
3. Chrome MCP で **画面を見ながら** ステップ実行
   - 各ステップ完了で **スクリーンショット** を保存
   - 失敗時は **DOM スナップショット + console + network** も保存
4. データ層検証（操作後に **DB 直接照会** で永続化を確認）
5. 結果を **state.json** にアトミック書き込み（tmp → rename）+ `features/<feature>.md` に追記:
   - **PASS は status=passed + `evidence`（screenshot / db_checks / network のいずれか実体）必須。**
     証拠を取らずに passed にしてはいけない（鉄則参照・スキーマが拒否）。
   - FAIL は status=failed + failure オブジェクト充填、`failures.md` にも再現手順 5 行以内 + 根本原因仮説
6. **連続 3 件 FAIL したら一旦止めてユーザに報告**（カスケード潰しを避ける）
7. **★クリーン環境/0状態ジャーニーを必ず 1 本以上実走**（full は必須、 diff も seed/初期化/認証/プロビジョニングに
   触れていれば必須）。 既存の seed済みDBで全部 PASS でも、 これをやらないと「fresh でだけ壊れる」型を見逃す。
   手順の型: ① 全テーブル TRUNCATE（または使い捨てDB）→ ② 空状態スモーク（500/throw しないか）→
   ③ seed のみ実行 or 手動ブートストラップ → ④ 0→初回登録→デフォルトPWでログイン貫通 → ⑤ 検証後に再 seed で復元。
   **破壊的かつ本番DBに触れうるため、 共有/本番DBで行う場合は事前にユーザ承認を取る**（ローカル/使い捨ては承認不要）。
   証拠（TRUNCATE後 count=0 / seed後の必須列実値 / 0→ログイン200 の network）を `evidence` に残す。
8. **★モック忠実性・導線・実操作を必ず実走**（coverage-matrix I）。 単体/契約テストの死角を実画面で潰す:
   - **★到達性・nav配線の静的突合 (I4-S / env・ブラウザ不要・最初に必ず実施)**: ブラウザや実DBが無くても
     **これだけは必ずやる**。① 全 layout/nav 定義から **href 文字列を全抽出** ② 全 page ルートをファイルから列挙
     ③ **href が指すルートが実在するか**（実在しない=クリックで404になる死リンク）と **各 route にナビ経路が在るか**
     （無い=孤立画面）を機械差分する。rewrites/redirects/router.push も grep で確認。
     «nav href=`/agent/dashboard` なのに実ページは `(agent)/s/402`＝`/agent/*` ルート不在で**全リンク404**» の型
     (Ppon QA-002) は **この静的突合だけで検出できる**。「ブラウザが無いから到達性は後回し」は禁止。
   - **モック対比**: 各画面を対応モック(`04_実装/mocks/...` 等)と並べ、 ボタン/タブ/フォーム/入力欄/列/フォーマット/
     セクションが**全て存在するか要素単位で照合**。 欠落を列挙し FAIL。
   - **ナビ網羅+到達性 (実走)**: I4-S で洗い出した経路を**実際にクリック**して 404/空白でないか確認。
     経路ゼロの**孤立画面**(例 csv-import が未掲載で到達不能)を FAIL。 サイドバー/メニュー項目集合が
     モックと一致するかも照合。
   - **全操作要素を実クリック**: 各画面の全ボタン/タブ/トグル/リンクを実際に押す。 タブ切替・モーダル・フィルタ・
     ページネーションも実操作。
   - **主要書込フローを実機で最後まで**: 登録/編集/削除、 **CSV はテンプレDL→記入→アップロード→結果(成功/重複/
     フォーマット不正)→DB反映**まで通す。
   証拠（モック対比チェック表 / 到達経路 / 実クリックのスクショ / CSVアップロード後のDB照会）を `evidence` に残す。

Chrome 操作の定型は `references/chrome-driving.md`。
データ層検証の定型は `references/data-layer-checks.md`。

### STEP 3.5 — 自己監査（仕様書ゲート＋捏造PASS ゲート・レポート前に必ず）

レポート発行（STEP 4）の **前に必ず** 2つのゲートを通す。どちらか一方でも落ちたら report 禁止・run は未完(BLOCK)。

**ゲートA（仕様書・鉄則0）**: 成果物が実在するか `ls` で確認する。
```bash
ls .qa/test-specs/screens/*.md && ls .qa/テスト仕様書_クライアント版.xlsx .qa/テスト仕様書_エンジニア版.xlsx
```
- 対象の全画面ぶん `screens/*.md` が在り、2系統xlsx が在ること。無ければ **STEP 0 に戻って生成**してから続行。

**ゲートB（捏造PASS）**: 実行が一段落したら:

```bash
scripts/audit_evidence.sh .qa/runs/<run-id>
```

- exit 0 → 全 passed に証拠あり。STEP 4 へ。
- exit 2 → **未証明 PASS あり**。列挙された TC を (a) 実機で再実行して証拠を取る か
  (b) `status=planned` に戻す。捏造のまま report に進まない。

`render_report.sh` も同じ検出を内蔵し、未証明 PASS が残ると判定を **BLOCK（信頼不可）** にする。
「全部 PASS」に見せるための誤魔化しは判定で必ず露見する設計。

### STEP 4 — 集計してレポート（3 形式 + クラスタリング）

レポートは「失敗一覧」ではなく **「次に何をすればいいか分かる文書」** として書く。
ベタ並びの表を出して終わらせない。詳しくは `references/reporting.md`。

実行中に失敗を記録するときは **必ず以下 2 つを書く**:

- `root_cause_id` — 同根の失敗を束ねる kebab-case ID（例 `api-validation-missing`）
- `user_impact` — ユーザに起きる**実害**を 1 行（「P0」だけでは PM が判断できない）

レンダリング:

`scripts/render_report.sh runs/<run-id> reports/<report-id>` を実行 →

- `final.json` — verdict / totals / **clusters** / blockers（CI gate / PR コメント自動化）
- `final.html` — 上から **判定 1 行 → 結論 → 次の一手（クラスタ）→ カバレッジバー → 詳細** の縦読み。明るい背景・印刷対応・TC ごとのアンカーリンク・検索ボックス付き
- `final.md` — narrative。結論 → サマリ → 次の一手 → 守れていた振る舞い → 個別詳細 の順

`final.md` の中身:

- サマリ（PASS / FAIL / SKIP）
- カテゴリ別カバレッジ
- 失敗の根本原因仮説と影響度
- ユーザに依頼すべき作業（後述）
- 次回への持ち越し（時間切れで未実施になったテスト）

最後にユーザに 1 行で結果を伝える。

## Diff モードの詳細

git の HEAD vs origin/main の差分から **影響範囲** を算出して対象を絞る。

```
1. git diff --name-only origin/main...HEAD       # 直接変更ファイル
2. grep で参照元を辿り（import / require / API path） → 影響範囲を拡張
3. テスト計画は「影響範囲に触れる UI シナリオ」だけに絞る
4. 余裕があれば「影響範囲のすぐ隣（呼び出し元）」も追加
```

詳しくは `references/diff-mode.md`。

## NG

- **証拠なしで passed と書く（捏造PASS）** — 最悪の不具合。コードを読んで「動くはず」は PASS ではない。
  実行して screenshot/DB/network を残せないなら `planned` のまま。`audit_evidence.sh` で必ず暴かれる。
- **実機を触らずに計画だけ書いて終わる** — 実行・記録までやり切る
- **層をまたぐ整合を見ない** — 「画面が出た」で満足せず、enum 不一致 / 未登録ルート /
  param 無しリンク / リロード後セッション / 集計 vs DB 実数 を必ず突き合わせる（coverage-matrix セクション G）
- **★seed済み/汚れたDB だけでテストして「0からの構築」を見ない** — 既存データ前提のテストは
  «fresh でだけ壊れる» バグ（seed のPW未設定・初回ブートストラップ不成立・空状態500 等）を**原理的に検出できない**。
  必ず «全 TRUNCATE → seed のみ → 素にログイン» と «空DB→初回登録→ログイン貫通» を別建てで通す（coverage-matrix セクション H）
- **seed を「前提」扱いして検証対象にしない** — seed はテスト対象。 fresh で seed だけでは基本フローが成立しないなら不合格
- **★少データ・1ユーザーで通ったら「スケールでも通る」と判断する** — seed数件で全PASSでも、 想定規模(1年/3年)の
  データ量・同時実行で実測しなければ «増えた瞬間に破綻»（全件ロードでタイムアウト/seq scan/N+1/ページング崩れ/上限時500/
  並行で整合崩れ）を**原理的に検出できない**。 «捌けるはず» を推測でPASSにせず、 N倍シード→並行負荷→**p95/エラー率/
  クエリ時間を実測 assert**する（coverage-matrix セクション L・第9軸）
- **★render+assert(単体/契約テスト)だけで「実装済み」と判断する** — それは「作った部品が動くか」専用。
  «モックにあるのに作っていないボタン/タブ/列/フォーマット» «ナビ未配線で到達不能な孤立画面» «押すと動かない»
  «CSV取込の動線が無い» は**原理的に検出できない**。必ず実画面でモック対比・全ルート到達性・全ボタン実クリックを行う（coverage-matrix I）
- **★「実装済み」の誤判定** — 画面が在る/API200/単体テスト緑 だけでは実装済みではない。
  «モックの要素が揃い・ナビ導線から到達でき・実操作(登録/編集/CSVアップロード等)が最後まで通る» で初めて実装済み
- **★「ブラウザ/env が無いから到達性は後回し」** — 禁止。到達性・nav配線の突合 (I4-S) は **href 文字列 ⇔ 実ルート**を
  ファイルから機械比較するだけで、**ブラウザも実DBも要らない**。env無しの静的検証フェーズで**必ず最初に**実施する。
  これを省くと «全 nav リンクが 404» «孤立画面» の型 (Ppon QA-002) が env 発行まで丸ごと漏れる。
- **★fake LLM / echo / stub の green を「AI検証済み」と報告する** — AI の検証は実キー実接続のみ。実キーが無ければ
  BLOCKED と明記し「AI は未検証」と総括する（第10軸／`references/ai-runtime-matrix.md`）。
- **3 件以上のリトライで通った FAIL を PASS 扱い** — flaky として失敗扱いし、原因を書く
- **本番 DB を勝手に汚す** — 書き込みする場合は事前にユーザ承認、または disposable な
  テストデータに限る
- **★仕様書を «途中で足す/別仕様を並立させる»（ドリフト）** — 正本は1冊。 新機能/修正は完成物に継ぎ足さず、
  ソースに同形式で加えて **全体を再生成**する。 TC 総数が動いたら版＋changelog で明示（鉄則3／`references/single-source-of-truth.md`）。
- **完成 xlsx を手で直接編集する** — 生成物はソースから決定論的に作る。 手パッチは再現性・復元性・整合を壊す。
- **★クライアント向け成果物に専門用語を残す／1冊で済ます** — 非エンジニアが読めない。 ①平易な日本語(画面操作)と
  ②証拠(network/console/Playwright/DB)を必ず分け、 ①は専門用語ゼロ・日本語タブ名にする（鉄則4／`references/client-engineer-views.md`）。
- **★期待結果を «実装の現状» から書く（バグを正常と追認）** — «ISO そのまま表示» «同一 href へ遷移» のように
  コードの挙動を期待値にすると必ず PASS し、 バグが «検証OK» になる。 期待結果は **要件/意図/モック** から書く。
  «意図通りか確認/メモ» «MEDIUM可読性» で利用者に見える不具合を緑にしない（鉄則5／`references/oracle-from-requirement.md`）。
- **PII を `.qa/` に書き残す** — マスキング徹底
- **スクショに認証 token / 秘密情報** — UI に出てる場合は撮影前にぼかすか除外

## 🤖 第6軸（必須・汎用）: AIエージェント / チャット動作検証（agent-behavior）

> 適用条件: プロダクトに **AIエージェント / チャット / LLM対話 / ツール実行(tool use) / 自律実行 / AI生成・提案** のいずれかが含まれる場合は**必ず**この軸を起こす。
> なぜ必要か: 「画面が出る / API が 200 / 文章が返る」は **AIが意図どおり動くこと**を意味しない。**stub / echo / 定型応答 / LLM未接続 / tool未dispatch** が「実装済み」を装う事故が頻発する（例: 対話ビルダーが入力を無視して固定の既定値を返す、チャットが受信文をオウム返しするだけ、tool_use が実際には実行されずDBに何も起きない）。**部品ではなく“流れが目的に到達するか”を実機で潰す。**

### test-plan モード 追加成果物: `.qa/test-specs/conversation-scenarios.md`
全AIインターフェースを洗い出し、各シナリオを「**意図 → 期待するAIの行動(選ぶべきtool/action) → 期待副作用(DB/外部) → PASS基準**」で定義する。happy path だけでなく **言い回し違い・曖昧入力・複数ターン継続・拒否すべき要求・異常系** を含める。

### full / diff モード 実機実行（証拠必須）
実際に会話/対話を**走らせる**。応答テキストだけで PASS にしない。証拠として **実際のtool呼び出し列・引数 / DB差分(select) / スクショ / network** を残す。

### チェック観点（詳細は coverage-matrix セクション J）
1. **全AI面の洗い出し**: チャット/対話ビルダー/自律実行(スケジュール等)/ツール実行/AI生成・提案/承認フロー を漏れなく列挙。各々 **stub/echo/定型でないか**を判定。
2. **実会話を走らせる**: 多様な意図・言い回し・曖昧入力・**3ターン以上の継続**。
3. **目的到達の検証**: 意図 → 正しいtool/action選択 → 実行 → **副作用が実データに反映** → 期待結果。"それっぽい文章"でPASSにしない。
4. **ツール使用の実証**: 正しいtoolを正しい引数で呼んだか（**実呼び出し列を観察**）/ 与えた値を尊重したか(再質問・取得し直さない) / **危険操作で承認ゲートが発火し未承認では実行されない**か。
5. **非決定性対応**: 同一シナリオを **2〜3サンプル** 流し一貫性を見る。**stub検出**(毎回完全一致のecho/固定文言/LLM未接続)。
6. **異常系・回復**: LLMキー無効/レート超過/タイムアウト/ツール失敗時に、ユーザー向けに適切な振る舞い(明示エラー・リトライ・degrade)で**壊れず回復**するか。
7. **★P0 stub/未配線の摘発**: 「LLMに**実接続**しているか」「tool_use が**実際にdispatchされ副作用が起きる**か」「生成/提案が**入力に応じて変わる**(固定でない)か」を必ず確認。1つでも stub のまま「実装済み」とされていたら **P0 不合格**。

- 実機(full/diff)で各シナリオを実走し、tool呼び出し/DB差分の証拠付きで判定
- **stub/echo/LLM未接続/tool未dispatch が critical path に残っていない**ことを確認(残るなら未完として報告)
- **プロバイダー×ツール×出力×状態の網羅は第10軸 (ai-runtime-matrix) で実施**（第6軸単独では「1構成で動いた」までしか言えない）

## 🔁 第7軸（必須・汎用）: 全ルート×全画面の実スキーマ整合・実DB貫通スイープ（route-sweep）

> 適用条件: サーバ側に DB を読み書きする API/ハンドラがあるプロダクト全て（=ほぼ全て）。
> なぜ必要か: mock/契約テストが緑でも、ハンドラの insert/select の**列名・enum値・NOT NULL・FK が実スキーマ(実DB)と
> 不一致**だと実機で 500 / 0件 / 認可エラーになる。モックは列名や enum を検証しないため**永遠に緑で通過**する。
> しかも screens 経由で表面化した分だけ直すと、画面から叩かれない・分岐の奥のルートに**同型バグ(systemic)が残る**。

### 鉄則（第7軸）: 全サーバハンドラをスイープ完了するまで未完
- 「N個直したから十分」は不可。**総ルート数(母数)と検証済み数を数値で出し、残数0**になるまで続ける。
- 「screens で見えた分だけ修正して完了」は鉄則1・2と同じ捏造扱い。

### 手順（詳細 `references/route-sweep.md`）
1. **全サーバハンドラ列挙**（フレームワーク非依存: route.ts / pages/api / controllers / resolvers をメソッド単位で全件 → 総数 N）。
2. **静的突合**: 各ルートの insert/update/select の列名・enum値・NOT NULL・FK を実 DDL(マイグレ/schema)と機械突合。`status:'x'` 等の固定値や `*_id` 代入も grep。
3. **実DB貫通**（モック禁止）: 各ルートを実DB・実セッションで実行し 500/0件/認可エラーを炙り出す。書込は再 select で副作用確認。
4. **既知 systemic class (a〜g) を照合**: (a)列名不一致 (b)存在しない列 (c)無効enum値 (d)client メソッドの this 未バインド (e)認可role判定が DBロール≠アプリrole (f)リクエスト文脈GUCが別トランザクションで不伝播 (g)seed/fixture の id が検証で弾かれる。
5. **完了条件**: routes タブ全行 pass(または妥当4xx)+証拠。未検証が1件でも残れば未完。スイープ完了率を summary に明記。

- **段1 トークン照合**: 設計の真実(モックの tailwind.config / DESIGN.md / トークンJSON)と実装トークン

## 📈 第9軸（必須・汎用）: 負荷・スケール・容量検証（load-scale-capacity）

> 適用条件: DB に読み書きする / 複数ユーザー・複数テナントを抱える / 一覧・検索・集計・ダッシュボードを持つ
> プロダクト全て（=ほぼ全て）。
> なぜ必要か: 機能QA(第1〜8軸)が全 PASS でも、**それは「seed数件・1ユーザーで触ったら動く」を見ているだけ**。
> 実運用で **ユーザー/テナント/レコードが増えた瞬間に破綻**する型 — 一覧が全件ロードでタイムアウト、検索が seq scan で
> 数秒、ダッシュボード集計が N+1 で固まる、ページングが大量データで崩れる、同時アクセスでエラー率が跳ねる、プラン上限/
> 容量上限に達した時の挙動が未定義(500やデータ破損) — は **「データを増やして・並行で叩いて」初めて出る**。
> 件数が少ないテスト環境では **原理的に検出できない**。機能の正しさ(動くか)とは独立した「スケールで耐えるか」を別軸で潰す。

### 鉄則（第9軸）: 「少データで通った」を「スケールで通る」と言うな
- seed数件で全 PASS でも、**想定規模(1年後/3年後)のデータ量・同時実行で実測するまで未検証**。推測で「捌けるはず」を PASS にしない。
- 閾値は **実測値で assert**（「速い気がする」は不可）。p95/エラー率/クエリ時間を数値で記録し、宣言した目標と突き合わせる。
- 上限(プラン行数/容量/レート/トークン)に達した時の挙動を **実際に上限まで到達させて**確認する。机上 OK 禁止。

### 検証観点（詳細 `references/coverage-matrix.md` セクション L）
1. **スケール前提の宣言**: 想定ユーザー数(初期/1年/3年)・テナント数・1テナント当たり主要レコード数・ピーク同時実行数・
   総データ容量を見積もって明記。**この数値が後続シナリオ・閾値の根拠**になる(無いと「何件で十分か」が決まらない)。
2. **データ量シーディング(N倍投入)**: 代表テーブルを段階的に増やす(例 1万→10万→100万行 / マルチテナントは「多テナント×
   各多レコード」)。各段階で **一覧・検索・集計・ダッシュボード・ページング** が破綻しないか実機計測(タイムアウト/メモリ/
   全件ロード/ページングずれ/N+1)。「1ページ目だけ速い」を全体OKにしない。
3. **同時実行・負荷**: 代表エンドポイントと主要ユーザーフローを並行実行(k6 / autocannon / Playwright 並列 / `xargs -P`/`&`での
   curl 並列 等、入手可能な手段)で叩き、**p50/p95/p99 レイテンシ・エラー率・スループット**を測って閾値判定。1並列での数値を
   多並列の根拠にしない。
4. **クエリ性能**: 重い経路の SQL を **EXPLAIN(ANALYZE)** し、**seq scan・欠落インデックス・実行時間**を確認。フィルタ/ソート/
   結合に効くインデックスがあるか。**カーソル/キーセットページング**が大量データで O(1) 的に効くか(OFFSET 肥大で劣化しないか)。
5. **容量・上限**: ストレージ/添付サイズ/トークン上限/レート制限/プラン上限(行数・容量)に **実際に到達させ**、超過時の挙動が
   適切(明示拒否4xx/警告/段階的劣化)で、500・無言切り捨て・データ破損にならないか。境界値(上限ちょうど/+1)を踏む。
6. **劣化と回復(resilience)**: 高負荷・タイムアウト・依存先遅延の下で サーキットブレーカ/リトライ/バックプレッシャ/キュー滞留が
   適切に振る舞い、**負荷が引いたら自動回復**するか(詰まったまま固まらない)。第6軸の異常系の「規模版」。
7. **スケール時のデータ整合**: 大量・並行投入/更新の後でも **テナント分離(RLS)が破れない**・**集計値=実数(`count(*)`)**・
   重複/競合(同時作成での一意制約・採番)が壊れないか。第7軸セクションGの整合チェックを「規模・並行」条件で再実行。

### 計測ツール(入手可能なものを使う・無ければ代替)
- 負荷: `k6` / `autocannon` / `wrk` / `ab`。無ければ `seq N | xargs -P<並列> -I{} curl` や Playwright 並列で代替。
- 計測: レスポンス時間は `curl -w '%{time_total}'`、p95 等は複数サンプルを集計。EXPLAIN は DB クライアントで実行。
- シード: アプリのseedスクリプト / SQL の `generate_series` 一括INSERT / ファクトリ。**使い捨て/ローカルDBで行い、本番は承認必須**。

### test-plan モード 追加成果物: `.qa/test-specs/scale-capacity.md`
スケール前提(見積数値) / シーディング計画(対象テーブル×目標件数) / 負荷シナリオ(対象×並列×期間) / **閾値**(p95・エラー率・
クエリ時間の目標) / 上限挙動(上限種別×超過時の期待) / 整合チェック(規模・並行下) を表で定義。閾値は「あるべき数値」を先に置く。

### full / diff モード 実機実行（証拠必須）
シード→計測→**閾値 assert**→証拠(実測の p50/p95/p99・エラー率・スループット・EXPLAIN出力・上限到達時のレスポンス・
シード後の `count(*)` と集計値の一致)を残す。閾値超過・上限時500・整合崩れは **FAIL/BLOCK**。実測せず「捌けるはず」は PASS 不可。

> DoD 追加: 「scale-capacity が存在し、①スケール前提の数値宣言 ②代表テーブルの想定規模シード ③主要経路の並行負荷で
> p95/エラー率を閾値 assert ④重い経路の EXPLAIN ⑤上限到達時の挙動 ⑥規模・並行下の整合(RLS/集計=実数) を網羅し、
> 閾値超過・上限500・整合崩れ=0」。少データのみで完了報告した run は第9軸 未実施として **未完**。


## 🧠 第10軸（AI実装があるなら必須・汎用）: AI実動マトリクス検証（ai-runtime-matrix）

> 適用条件: LLM/embedding 等の **AIプロバイダー呼び出し・tool use・AI生成出力** を 1 つでも持つプロダクト。
> なぜ必要か: 第6軸(会話シナリオ)は「意図→到達」を見るが、それだけでは **「1プロバイダー・1ツール・
> 短い1ターンで動いた」** しか証明できない。実運用では プロバイダー障害/キー無効/レート、誤ツール選択、
> schema 崩れ出力、長文脈での圧縮発火、並行・中断再開 で壊れる。本軸は **「プロバイダー × ツール × 出力 × 状態」
> の直積** を実プロバイダーで潰し、「汎用的に・どういう状態でも動く」ことを実証する（G3: モックPASS禁止）。

### 鉄則（第10軸）: fake LLM の green は AI 検証ではない
- ALLOW_FAKE / echo / stub / モック応答での green を **「AI検証済み」と報告してはならない**。実キー実接続のみが証拠。
- 非決定な出力を 1 サンプルで判定しない。**事前定義した不変条件を 2〜3 サンプル全通過**で PASS。
- 実キーが無い環境では該当行を全て **BLOCKED(解除条件=キー設定)** とし、総括に「AI は未検証」と明記する
  （器のテストが全 green でも「AI が動く」とは言えない）。

### 4次元マトリクス（手順詳細・テンプレは `references/ai-runtime-matrix.md`）
1. **プロバイダー軸** — 使用する全プロバイダー/モデルごとに: 実接続スモーク（非echo確認）/
   **フォールバック実走**（主系キーを実際に無効化→副系へ切替）/ キー無効401・レート429実到達・タイムアウトの回復 /
   廃止・誤モデル名への耐性（沈黙フォールバック禁止）。
2. **ツール軸** — 定義済み tool を **1 つずつ**: 呼ぶべき入力で呼ぶ（言い回し 2-3 通り）/ 呼ぶべきでない入力で
   呼ばない（誤選択防止）/ 与えた ID・値を引数で尊重（取り直さない）/ **副作用が DB・外部に実在**（応答文で
   PASS にしない）/ tool 強制失敗時にモデルが回復（無限ループ・捏造しない）/ 危険操作は承認ゲートで停止。
   証拠は **実 tool 呼び出し列のログ**。
3. **出力軸** — 構造化出力の schema 全サンプル準拠 / 言語・文体指定の遵守 / max_tokens 到達時に壊れた
   JSON を消費側へ流さない / markdown・JSON をパーサ検証 / **プロンプトインジェクション混入入力**で指示に
   従わず秘密を漏らさない / 非決定でも変わらない不変条件（必ず含む・絶対含まない）の assert。
4. **状態軸** — 上記の代表行を状態を変えて再実行: 空文脈(初回) / **長文脈（圧縮・切詰めの実発火域）** /
   キャッシュ hit・miss / **並行 N 本（別ユーザーの文脈が混線しない）** / 中断→再開（stream 切断で二重副作用・
   半端保存が無い）/ 会話 3+ ターン / RAG 0件・大量件。

### 組合せの刈り方（silent cap 禁止）
直積は爆発するため、**各軸の全値を最低 1 回**踏んだ上で、軸間組合せは「本番デフォルト構成」＋
「リスクベース（過去事故・新規実装・危険操作）」に絞る。**刈った組合せは表に「未実施（理由）」として残す**。

### test-plan モード 追加成果物: `.qa/test-specs/ai-runtime-matrix.md`
冒頭に AI 面の棚卸し表（プロバイダー/tool/構造化出力/状態機構 — 無いものは「なし」と明記）、
本文はマトリクス表（ID/軸/対象/状態/手順/期待=不変条件/結果/証拠）。

### full / diff モード 実機実行（証拠必須）
実キーで実走し、**実リクエスト要約・応答 or tool呼び出し列・トークン使用量・レイテンシ**を evidence に保存。
実行前にコスト概算（本数 × 平均トークン × 単価）をユーザーへ提示する。

> DoD 追加: 「AI実装があるのに ai-runtime-matrix が無い run は**未完**。fake での green を AI 検証に数えていない。
> 全プロバイダーの接続/フォールバック/エラー回復・全ツールの実証・出力不変条件・状態軸の再確認が
> PASS か理由付き BLOCKED で全行決着」。

## 📊 検証マトリクス出力（画面別タブ・スプレッドシート対応）

検証結果を「**画面ごと・細粒度・タブ分け**」のマトリクスで出し、最終的に**全行が検証済み(pass/fail+証拠)**になった
状態を一望できるようにする。**正本は state.json**、CSV/シートはそこから派生。

- 生成: `scripts/render_matrix.sh <run-dir> [out-dir]` → `<out-dir>/matrix/<tab>.csv`（UTF-8）。
- タブ(=ワークシート=CSV): `summary` / `screens`(1画面=その画面の表面積ぶんの行数・上限なし) / `routes`(第7軸) / `rls-matrix` / `zero-state` / `agent-behavior` / `visual-fidelity`(第8軸) / `scale-capacity`(第9軸) / `ai-runtime-matrix`(第10軸) / `journeys`。
- **表計算 MCP/コネクタが接続済みなら タブ=ワークシートに直接 upsert**（test_id をキーに冪等）。無ければ CSV を出してインポート案内（勝手に外部送信しない）。
- 運用: 計画時に全タブの行を planned で先出し → 実行で 1 行ずつ pass/fail+evidence 更新 → 再生成。完了判定は summary 検証率100%・failed/blocker=0・未証明passed=0・routesスイープ100%。
- 詳細は `references/spreadsheet-matrix.md`。

## 🔚 完了後の handoff（通しテストへ移る）

第1〜10軸＋視覚忠実度＋マトリクス出力が全て決着したら、それで終わりにしない。**最後に必ず
通しテスト（[[e2e-journey-walkthrough]]）へ移る**。個別軸が全 PASS でも「ロールをまたいだ一連の
流れが、正しい順序で、実際に最後まで通るか」は別物だからだ（機能が個々に正しい ≠ 新規登録→設定→
運用→最終成果までユーザーとして通しで成立する）。

- **移行条件**: human-grade-qa の全軸 DoD が満たされ、マトリクスの summary が検証率100%・
  failed/blocker=0。
- **移行後にやること**: `e2e-journey-walkthrough` を起動し、各アカウントタイプ(管理者も含む)で
  新規登録→ログイン→設定→運用→最終成果(納品/予約完了/購入完了 等)を、依存順(プロビジョニング→
  設定→消費)で、既存データ通し＋新規作成後通し＋分岐まで、**ブラウザで実際に操作して**通す。
  結果は Excel(全行 PASS まで blocking)に出す。
- **本当の完了**: human-grade-qa の DoD ＋ 通しテスト Excel の全行 PASS(DONE?=YES) が揃って初めて
  「QA 完了」と報告してよい。通しテストが未達なら、まだ完了ではない。
