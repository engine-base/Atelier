# Reporting — 人間が読んで動ける形にする

QA レポートは **「失敗一覧」ではなく「次に何をすればいいか分かる文書」** であるべき。
ベタ並びの表だけ出して終わらせない。

## 報告の 3 階層

| 階層 | 対象読者 | 形式 | 含めるもの |
|---|---|---|---|
| 1. 判定行 | 全員（Slack 通知） | 1 行 | 判定 + 失敗件数 + 主因 1 つ |
| 2. エグゼクティブサマリ | PM / リード | 4-6 行 | 結論・どこまで動いた・どこで止まった・次の一手 |
| 3. 根本原因クラスタ + 詳細 | 実装者 | 構造化 | クラスタ別の修正提案、TC ごとの再現手順 |

このスキルが出す `final.md` と `final.html` は **3 階層を縦に並べた構造** にする。
読者は上から読めば自然と「どこを直す？」までたどり着ける。

## 根本原因クラスタリング（最重要）

**8 件のフラットな失敗一覧** より **3 つのクラスタ** に整理する方が圧倒的に行動につながる。
クラスタ化は以下の手順で:

### 1. AI 実行時に root_cause_id を振る

実行中、失敗を記録するときに `root_cause_id` を必ず付ける。同根のものは同じ ID:

```json
{
  "id": "TC-F01-04",
  "status": "failed",
  "root_cause_id": "api-validation-missing",
  "user_impact": "クライアントを信頼するしかなく、攻撃者は DB 制約名から内部スキーマを推測できる",
  "failure": {...}
}
```

ID 命名規則: kebab-case で **症状ではなく原因** を書く:
- ✅ `api-validation-missing`
- ✅ `ai-endpoint-no-auth`
- ✅ `state-batching-bug`
- ❌ `error-500` （症状）
- ❌ `bug-3` （内容なし）

### 2. レンダリング時にクラスタを集計

`render_report.sh` が `root_cause_id` でグルーピングし、各クラスタに以下を計算:

- メンバー TC のリスト
- 最高重要度（クラスタ内の最大 P0 > P1 > P2）
- 共通の症状（共通する failure.summary を要約）
- 推奨修正（クラスタごとに 1 つ提示）

### 3. レポート上部に「クラスタ別の推奨修正」を出す

詳細を読む前に **「この PR では 3 ヶ所を直せば 8 件全部解決する」** が分かるように。

```markdown
## 次の一手（クラスタ別 推奨修正）

### A. API 入力バリデーション欠如（3 件 / 全 P1）
- 該当: TC-F01-04, TC-F01-06, TC-F05-03
- 症状: 必須欠落 / 型不正で 500 + 制約名漏洩
- 修正: 全 routes で zod スキーマ検証を追加
- 工数: 半日

### B. AI endpoint 認証欠如（2 件 / 全 P0）
- 該当: TC-F04-04, TC-F07-02
- 症状: Bearer 任意文字列で 200
- 修正: Vite middleware で /api/ai/* を required-auth に統一
- 工数: 1 時間

### C. 会話 scope 分離欠如（1 件 / P0）
- 該当: TC-F07-01
- 修正: postgres_session の WHERE 句で scope/scopeId 完全一致
- 工数: 1 時間
```

## ユーザ視点で「実害」を必ず書く

「P0」「P1」だけでは PM やデザイナーは判断できない。`user_impact` を必ず:

| ❌ severity だけ | ✅ user_impact あり |
|---|---|
| P0 失敗 1 件 | コスト不正利用と全テナント会話本文の漏洩リスク |
| P1 失敗 3 件 | 攻撃者が DB 制約名から内部スキーマを推測可能 |
| P0 失敗 1 件 | 「現状を要約して」のリクエストで他校の会話が混入 |

実害を書くと:
- マージ判断が瞬時にできる
- リスクの説明資料になる
- 修正の優先順位が自然に決まる

## エグゼクティブサマリの書き方

4-6 行で **結論 + コンテキスト + 推奨アクション**:

```markdown
## 結論

**マージ不可**。AI チャット系 endpoint が無認証（P0 セキュリティ）かつ会話履歴の
スコープ分離が効いていないため、現状のままでは他テナントの会話本文が読めてしまう。

## サマリ

- 動作した: カリキュラム CRUD・ジャンル配分・カレンダー・finalize の基本フロー（合格 20/28）
- 動いていない: AI 系 endpoint の認証 / 会話 scope 分離 / API 入力バリデーション
- リリースへの影響: 上記 P0 を修正しない限りデプロイ不可
- 次の一手: 後述「次の一手」3 クラスタを順に直せば PR を再評価できる
```

## 失敗以外も書く（守れていたこと）

合格 20 件を **「動いた」リストだけ** にしない。
**「これは守れている」** をリグレ ID 付きで書くと、安心感と差分把握に繋がる:

```markdown
## 守れていた振る舞い

- 既知バグの再発なし: H1 (tool 直列), H10 (JST/UTC), Q2 (genre_id), Q4 (rate limit), U1 (UUID 非表示)
- プロンプトインジェクション拒否
- 並行 finalize race の DB-level serialization
- propose-lessons の text fallback
```

## 詳細セクションの粒度

詳細は **クラスタ → TC** の順に折りたたむ:

```
▶ クラスタ A: API 入力バリデーション欠如
  ▶ TC-F01-04 ...
  ▶ TC-F01-06 ...
  ▶ TC-F05-03 ...
▶ クラスタ B: AI endpoint 認証欠如
  ...
```

クラスタなし（root_cause_id 未付与）は最後に「その他」として:

```
▶ その他の失敗
  ▶ TC-F02-03 ...
```

## アンカーリンク（PR コメント貼付）

各 TC に `#TC-F01-04` のアンカーを置く。
PR レビュアーが「ここの修正は TC-F01-04 を再走で確認」のように直リンクできる。

## 印刷対応

会議で印刷する人もいる。`@media print`:

- ヘッダ判定バッジを目立たせる
- 折りたたみを全展開
- ページ区切りをクラスタ境界で
- リンク URL を脚注表示

## 何を載せないか

- スクショの生バイナリ（リンクで参照）
- 個人情報・トークン本体
- 過剰な数値（合格率 0.9286 のような小数）
- "OK でした" だけのコメント（必ず何を確認したか書く）
