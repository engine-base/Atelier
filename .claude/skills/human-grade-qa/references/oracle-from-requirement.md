# 期待結果は「要件/意図」から書く（鉄則5の詳細）

テストの正解（期待結果＝オラクル）を **実装から独立** させるための、 どのプロジェクトでも使える規約。
これを守らないと «コードはコード通り動く» というトートロジーになり、 **バグを「検証OK」として追認**する。

## なぜ起きるか（失敗の構造）

1. 画面/コードを先に見る → 2. «今こう動いている» を期待結果に書き写す → 3. 実装は当然その通り動く →
4. **PASS**。 こうして «生タイムスタンプ表示» «ボタンが誤ったページへ» が «検証OK» になる。
正解が実装のコピーなので、 **定義上どんなバグも検出できない**。

## 正しい順序

1. **先に «あるべき姿» を決める**（要件・仕様・モック/デザイン・機能の目的・一般 UX）。
2. それを期待結果に書く。
3. 実装を動かし、 実挙動と **突き合わせる**。
4. 一致＝PASS。 不一致＝**FAIL（バグ）**。 «実装に合わせて期待値を書き換える» のは禁止。

## Before → After（実装描写 → あるべき姿）

| ❌ 実装を写した期待結果（バグを追認） | ✅ 要件/意図から書いた期待結果（バグを検出） |
|---|---|
| 予約日時は「ISO 文字列がそのまま表示（整形なし）」 | 予約日時は「2026年6月20日 18:44」等、**人が読める形に整形**して表示。授業名も出す |
| 4枚のタイルは「いずれも同一 href `/materials/edit` へ遷移」 | 各タイルは **その種別の編集/配信** に遷移（テスト問題→テスト編集、問いかけ表→PDF配信、種別が選択済み） |
| 一覧は「orderBy 無し＝DB 物理順で表示」 | 一覧は **新しい順（または指定順）** で安定して並ぶ |
| 結果画面は「0/0/0% と表示」 | 結果画面は **実際の点数・正答率** を表示（0 固定はバグ） |
| 「`required` でブロック（実装通り）」 | 未入力は **送信できず、 何が必要か分かる** |

## 嗅ぎ分けチェック（期待結果がこう読めたら書き直す）

- «〜がそのまま表示» «整形なし» «生の〜» → 整形・表示要件を書いていない疑い
- «同一 href» «同じページへ» «〜へ遷移（実在）» だけ → 遷移先が **正しいか** を書いていない
- «orderBy 無し» «LIMIT 無し» «state のみ» など **実装語** が期待結果に出る → 実装描写
- «〜を記録» «挙動を確認» «意図通りか確認» → 判定を保留している（PASS にしてはいけない）
- HTTP コード/Cookie/関数名だけで、 «ユーザーに何が起きるべきか» が無い

## PASS/FAIL の判定規律

- **as-is（現状記録）は PASS ではない。** 備考に «現状こう» と書くのは可。 だが期待結果＝as-is の TC は緑にしない。
- **判定保留＝未検証。** 「意図通りか確認/仕様確認/?」が残る → 検証OK 禁止。 要件で決着 or ユーザーに «要確認» で上げる。
- **重大度ロンダリング禁止。** 利用者に見える不具合を «MEDIUM/可読性/メモ» で PASS にしない。 重大度は優先度のみ、 PASS/FAIL は動かさない。
- **到達性 ≠ 正しさ。** 「リンクが実在ルートに解決」は必要条件。 «正しい先か・正しい文脈(種別/param)か» まで意図で判定。

## 正解源（オラクル）が無い時

書かれた仕様が無ければ、 次の順で «あるべき姿» を導く:
1. モック/デザイン（鉄則2 のモック対比）
2. 機能の目的・名前（«テスト問題» ボタンはテスト編集を開くはず）
3. 一般的 UX 期待（日付は人間可読、 金額は通貨表記、 一覧は新しい順 等）
4. それでも曖昧 → **«要確認» としてユーザー/クライアントに上げる**。 実装に合わせて緑にしない。

## 自己質問（PASS にする前）
- この期待結果は **要件/意図** から書いたか、 **コードを見て** 書いたか？
- «現状はこう» を期待値にしていないか？
- «意図通りか確認/メモ» のまま緑にしていないか？
- 遷移先は «実在» だけでなく «正しい先» を見たか？
- 利用者が «これ正常？» と聞く表示を «MEDIUM» で逃がしていないか？

1つでも怪しければ **FAIL か未確認**。 緑にしない。
