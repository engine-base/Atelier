# テスト仕様書フォーマット — 9 列スタイル

実プロジェクトのテスト仕様書サンプル（Google Sheets 等）に準拠した **9 列フォーマット** を採用する。
全プロジェクトで同一構造を使うことで、計画書のレビュー・再利用・自動集計を容易にする。

## 9 列の正本定義

| 列名 | 必須 | 意味 | 例 |
|---|---|---|---|
| **ID** | ✅ | テストケース一意 ID | `TC-F01-01` |
| **画面** | ✅ | 検証対象の画面 or 機能名 | `ログイン画面` / `カリキュラム作成` |
| **テスト観点** | ✅ | 何を確かめる観点（後述語彙） | `認証` / `バリデーション` |
| **テスト項目** | ✅ | 1 行で「何を試すか」 | `正しい情報でログイン` |
| **前提条件** | ✅ | この TC 開始時の状態 | `未ログイン / 既存ユーザ A 存在` |
| **操作手順** | ✅ | ヒトが追える 3〜6 ステップ | `1. /login を開く 2. ...` |
| **期待結果** | ✅ | UI / API / DB の到達状態 | `/ にリダイレクト + Set-Cookie + ログイン記録 1 行` |
| **結果** | ✅ | 実行後の判定（後述語彙） | `合格` / `失敗` |
| **備考** | optional | 自動化手段・既知バグ参照・補足 | `自動: Chrome MCP, U1 リグレ確認` |

## ファイル構成

```
.qa/plans/YYYY-MM-DD-<mode>-<scope>/
├── test-plan.md            # マスター（人間が承認用に読む）
├── plan.json               # 機械用 seed（state.json の初期値）
├── research.md             # 調査ノート（フレームワーク・ドメイン適応）
└── feature-specs/
    ├── F-01-auth.md        # 機能ごとの 9 列テーブル
    ├── F-02-create.md
    └── ...
```

ファイル名規則:
- `F-NN-<slug>.md`
- NN は 01 から連番
- slug は kebab-case 短英単語

## ID 規則

```
TC-F<feature-num>-<NN>            例: TC-F02-07
TC-F<feature-num>-<NN>-FAIL-<NN>  例: TC-F02-07-FAIL-01（派生失敗ケース）
```

## 「テスト観点」語彙（必須 6 + 補助）

必ず最低 6 観点を 1 機能あたりカバーする:

| 観点 | 何を見るか |
|---|---|
| **正常** | Happy Path — 想定通り最後まで完走 |
| **異常** | エラー UI / 5xx 復帰 / タイムアウト / レート制限 |
| **バリデーション** | 必須・型・長さ・パターン（全フィールド × 全ルール） |
| **境界** | 最小・最大・空・上限超え・Unicode 多バイト |
| **権限** | 未ログイン・別ロール・別テナント・不正トークン |
| **復帰** | リロード・別タブ・履歴復元・ブラウザ戻る |

補助観点:

| 観点 | 使うとき |
|---|---|
| **リグレ** | 既知バグ（H1, Q2 等）の再発防止 |
| **セキュリティ** | 認証・認可・PII 漏洩・プロンプトインジェクション |
| **性能** | レスポンス時間・SSE フレーム数 |
| **整合性** | DB トランザクション境界・関連レコード |
| **クリーン環境/0状態** | 空DB起動・初回ブートストラップ・0→初回登録→ログイン貫通・seed健全性（fresh で初めて出る型）。 詳細 coverage-matrix H |

> **クリーン環境/0状態は「ジャーニー軸」で必ず別建て 1 本以上**。 既存データ前提のジャーニーに混ぜない
> （混ぜると seed済みで通って fresh で壊れるバグを見逃す）。 専用ファイル例: `feature-specs/F-00-zero-state.md`。

## 「重要度」語彙

- **P0** — リリースを止める。セキュリティ / データ破壊リスク
- **P1** — 通常リリースまでに直す。代替手段あり
- **P2** — 直したい程度

P0 は全数実行が必須、P1 は主要分岐、P2 は時間が許せば。

## 「結果」語彙（実行後）

- **未実施** — まだ走らせていない
- **実行中**
- **合格** — PASS。**必ず証拠（screenshot / DB照会 / network のいずれか）を残す。**
  証拠が無ければ「合格」にしてはいけない（証拠なし合格＝捏造。未実施に倒す）。
- **失敗** — FAIL（**必ず備考に再現手順 + 原因仮説 + 回避策**）
- **スキップ** — 環境制約で見送り（理由を備考に）
- **ブロック** — 先行 TC 失敗で実行不能
- **不安定** — リトライで挙動が割れる、原因調査要

state.json 内では英語キー（passed/failed/skipped/blocked/flaky/running/planned）、
人間が読む md/html では上記日本語語彙にマップ。

## 「自動化手段」（備考列に書く）

- `Chrome MCP` — 主軸。Web UI を「ユーザのフリ」で触る
- `Playwright` — 再走可能な spec を残す
- `curl` / `httpie` — API 単体検証
- `DB 直接` — 永続化確認（psql / node pg / mysql）
- `iOS Sim` / `Android Emu` — モバイル
- `human` — 人間に依頼

## 1 画面分の最小ボリューム（実仕様書 粒度）

**1 シート = 1 画面**。 件数はその画面の **表面積から導出**する（上限/目標を置かない＝鉄則2-8）。
粗すぎ（«表示される/データ正しい» だけの 6〜15 件）は粒度不足だが、 逆に «30〜40 に合わせて足す/削る» のも誤り。
`references/coverage-matrix.md` の画面タイプ別チェックを **全フィールド・全列・全ボタンに展開** した
**結果として** 件数が決まる（単純画面は少なく、 複雑画面は 60〜80 超もあり得る）。
下表の「目安件数」は «この画面タイプならこの観点を必ず展開せよ» という**チェック対象の目安**であって、 数字目標ではない。

| 画面タイプ | 目安件数(導出結果の幅) | 主な内訳 |
|---|---|---|
| 入力フォーム（登録/編集） | 30〜40 | 初期値(フィールド数)・バリデーション(フィールド×ルール)・戻る2本・登録成功/失敗・完了ポップアップ・権限・APIエラー・レスポンシブ |
| 一覧 | 30〜40 | 検索(条件ごと)・並び/列表示/タグ配色・ページネーション端・CSV(名/内容/列/文字コード)・権限・APIエラー・レスポンシブ |
| 詳細 | 20〜40 | 項目ごとの表示一致・更新履歴・各アクション(権限有/無)・戻る・APIエラー・レスポンシブ |
| 認証 | 10〜15 | 表示・認証(正/誤/無効)・バリデーション(各フィールド×ルール)・APIエラー |

「初期値」「未入力」「型」だけでフィールド数 ×3 行になる。 これを省略しないこと。

## バリデーション・サブテーブル（必須）

フォームがある機能は **必ず** フィールド × ルールの表を `feature-spec.md` に展開する:

| # | フィールド | ルール | 入力 | 期待 |
|---|---|---|---|---|
| 1 | email | 必須 | "" | 「メールを入力してください」 |
| 2 | email | 形式 | "abc" | 「メールの形式が不正です」 |
| 3 | password | 最小 8 | "abc1!" | 「8 文字以上にしてください」 |
| 4 | password | composition | "abcdefgh" | 「数字 / 記号を含めて」 |

クライアント側 / サーバ側の両方で発火するかを分けて確認。

## 失敗時に「備考」に書く 4 点セット

```
要約: 1 行
再現手順: 5 行以内
期待: ...
実際: ...
原因仮説: ファイル名 / 行番号レベルで
回避策: ユーザがその場で取れる手段
```

## レビューチェックリスト（書き終えた後の自己確認）

- [ ] 全機能に **正常系が 1 件以上** ある
- [ ] 全入力フィールドに **バリデーションケース** がある
- [ ] **権限分岐**が網羅されている（不正 token / 別ロール / 未ログイン）
- [ ] 物理デバイス依存は **人間依頼** として明示
- [ ] **クリーン環境/0状態のジャーニーが別建てで 1 本以上ある**（空DB起動・初回ブートストラップ・
      0→初回登録→デフォルトPWでログイン貫通・**fresh seed で素にログイン成立**・認証モデル明示）
- [ ] 想定実行時間が現実的（1 TC 平均 2-5 分）
- [ ] 計画書だけ読んでヒトでも実行できる粒度
- [ ] **9 列が全部埋まっている**（空欄が無い、空欄なら `—` を書く）

## 参考: 元サンプルの 9 列

実プロジェクト（教育系 SaaS の Google Sheets サンプル）から抽出:

```
ID | 画面 | テスト観点 | テスト項目 | 前提条件 | 操作手順 | 期待結果 | 結果 | 備考
```

このスキルが採用するフォーマットは上記と完全一致。ヒトが手動でメンテしやすく、
AI が機械的に state.json に変換しやすい構造。
