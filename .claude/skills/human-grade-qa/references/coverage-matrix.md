# Coverage Matrix — 網羅マトリクス（実テスト仕様書 粒度）

「人間レベルの QA」とは、 1 画面を **入力フィールド単位・列単位・ボタン単位・遷移単位** で潰すこと。
件数は画面の **表面積から導出**する（上限/目標を置かない＝鉄則2-8。 単純画面は少なく、 複雑画面は多い）。
機能が「動く」だけでなく、 初期値・無効状態・端条件・権限・レスポンシブまで見る。

基準となる実仕様書: `references/example-spec/inventory-app-test-spec.md`
（実プロジェクトで人手運用していたテスト仕様書の写し。 列・粒度はこれに合わせる）。

## テストケースの列（全 TC 共通）

| 列 | 内容 |
|---|---|
| ID | 画面内連番 (1, 2, 3...) |
| 画面 | 対象画面名 (1 シート = 1 画面) |
| テスト観点 | 大分類（画面表示 / 入力フォーム / バリデーション / 検索機能 / テーブル表示 / ページネーション / CSV / 登録 / 編集 / 詳細表示 / 戻る / 権限 / エラーハンドリング / レスポンシブ 等） |
| テスト項目 | 具体的に何を確認するか（フィールド名・列名・ボタン名を明記） |
| 前提条件 | セッション・データ・権限・画面状態 |
| 操作手順 | 1. … 2. … と番号付きで、 誰でも再現できる粒度 |
| 期待結果 | UI / API / DB / ログ で何が起きるか（検証手段も書く: 例「APIレスポンスから確認」） |
| 結果 | 未着手 / 完了 / FAIL（実行後に更新） |
| 備考 | スクショ名・補足・未実装理由 |

## 画面タイプ別 必須チェックリスト

各画面を以下のタイプに分類し、 該当タイプのチェックを **全フィールド・全列・全ボタンに展開** する。
「該当する全項目を 1 行ずつ TC 化」するのがこの粒度の肝。

### A. 入力フォーム画面（登録 / 編集 / 設定）

1. **初期値（フィールドごとに 1 TC）**
   - 各入力の Placeholder 文言が正しい（例「例：山田」）
   - 各 select/radio の初期選択（例「社外が選択状態」「有効ラジオが選択状態」）
   - 条件表示フィールドの初期可視状態（例: 所属区分=社外のとき取引先が表示・社内で非表示）
2. **バリデーション（フィールド × ルールごとに 1 TC）**
   - 必須: 未入力で完了 → インプットがエラー表示 / 送信ボタン無効
   - 型チェック: メール型不正 / 数値欄に文字 等 → エラー表示
   - 重複: 既存と同じ値（メール等）→ 重複エラー
   - 文字種: 全角不可の欄に全角 → 入力できない / エラー
   - 最大長: 上限超（例 200 文字）→ エラー / 入力不可
3. **依存・連動**
   - 区分切替で項目の表示/非表示が変わる
   - 切替時に確認ポップアップ → キャンセル / 実行（実行で関連入力リセット）
4. **戻る**
   - 入力値なし → 一覧へ遷移
   - 入力値あり → 入力をリセットしてから一覧へ遷移（破棄確認があるならそれも）
5. **登録 / 更新（成功フローは段ごとに検証）**
   - 必須すべて入力 → 送信 → ①DB に保存 ②(あれば)招待メール送信 ③入力リセット ④遷移 ⑤完了アラート/ポップアップ（各段を期待結果に列挙）
   - 必須未入力 → 送信ボタン無効 かつ 未入力欄エラー
   - 完了ポップアップ: 「一覧に戻る」/「続けて登録」（続けて=リセット&留まる・ID更新）
6. **権限（全体）**: 登録/編集権限なしで画面を開く → 一覧へリダイレクト（画面を見せない）
7. **エラーハンドリング**: API エラー（接続失敗 / ネットワーク / レートリミット）→ アラート表示
8. **レスポンシブ**: 幅を狭く→横幅追従 / 高さを狭く→高さ追従

### B. 一覧画面

1. **検索機能（条件ごとに 1 TC）**
   - 検索条件パネルの開閉
   - 各条件: テキスト部分一致 / プルダウン各値 / チェックボックス（例「無効も表示」）
   - 複数条件の AND
   - 0 件 → 「該当するデータがありません」
   - 条件クリア → 全件に戻る
   - 検索欄のバリデーション（不正形式でエラー）
2. **テーブル表示**
   - 既定の並び順（例: ID 昇順）
   - 行クリック → 詳細へ遷移
   - 各列の値が正しい（列ごとに確認）
   - 状態タグの配色（例: 緑「有効」/ 灰「無効」/ 緑「承認済」/ 赤「未承認」）
   - 条件付き表示（例: 社内→取引先列は「-」/ 社外→ID 表示）
3. **ページネーション（端条件まで）**
   - N 件超でページャ表示 / 件数表示（「1件〜50件（全260件）」）
   - ページ番号クリック / 「前へ」/「次へ」
   - 1 ページ目で「前へ」非表示 / 最終ページで「次へ」非表示
   - 検索後のページネーション
4. **CSV ダウンロード**
   - DL 実行 / ファイル名形式（例 `users_YYYYMMDD_HHmmss.csv`）
   - 内容: 全件 / 検索後は検索結果のみ
   - 列構成（全列名を期待結果に列挙）
   - 文字コード（UTF-8 BOM 付き等で文字化けしない）
5. **新規登録ボタン** → 登録画面へ遷移
6. **権限**: 閲覧/操作権限の有無で表示・遷移が変わる
7. **エラーハンドリング**: API エラー → アラート
8. **レスポンシブ**: テーブル横スクロール / 縦スクロール（ヘッダー固定）/ 高さ追従

### C. 詳細画面

1. **詳細情報表示（項目ごとに 1 TC）**: 一覧でクリックした行の各項目が一致して表示される
2. **更新履歴 / 関連テーブル**: 表示・各セル・変更点のハイライト
3. **状態タグ配色**（一覧と同基準）
4. **戻る**: 「＜…」で一覧へ
5. **アクションボタン**: 編集 / 承認 等 → 権限ありで遷移/実行・権限なしで非表示
6. **アクション実行の結果**: ステータス/日時/実行者が更新される（DB 反映を確認）
7. **エラーハンドリング** / **レスポンシブ**

### D. 認証画面（ログイン / 初回ログイン / パスワード再設定）

1. **画面表示**: 要素が正しく表示 / 入力項目が見える
2. **認証**: 正しい情報 → 遷移（APIレスポンスから成否確認）/ 誤情報 → エラー通知 / 無効アカウント(status=inactive) → エラー
3. **バリデーション**: メール未入力→ボタン無効 / メール型 / PW 未入力→ボタン無効 / PW 型 / 長文(200字超)
4. **エラー時**: API エラー（接続失敗 / ネットワーク / レートリミット）→ エラー通知
5. **後続**: PW 設定成功 → 完了画面 / 失敗 → エラー

### E. 共通・横断（全画面に効く）

- **404 / 不正 URL** → 404 表示 / 「一覧へ戻る」動作
- **未認証ガード**: 保護画面に未ログインで直アクセス → ログインへ / 無効トークン → 破棄してログインへ
- **権限ガード**: ロール/テナント越境不可（他人・他テナントのデータが見えない・操作できない）
- **日時表示**: タイムゾーン固定（JST 等）で実行環境に依存しない
- **空データ**: 各画面 0 件時の表示
- **境界・セキュリティ**: SQL/HTML インジェクション文字列 / 絵文字・4byte / 改行・全角空白の扱い

### F. マルチターン / 状態継続（★ 単発テストでは絶対に出ない・最重要）

**「1 リクエスト送って 1 応答が返る」だけのテストは状態継続バグを 1 件も検出できない。**
実プロジェクトで「途中で文脈が消える」「リロードしたら入力が飛ぶ」「作成したものが次画面に
反映されない」系のクレームはここから出る。 ステートを持つ機能（チャット / ウィザード /
複数ステップフォーム / カート / 下書き保存）には必ずこの観点を全部展開する。

- **同一会話の継続（チャット / AI / コメント）**:
  - ターン 1 で作成/設定 → ターン 2 で「続けて」「進めて」→ **前の文脈を保持しているか**
  - ターン 3, 4 と続けて、 N 回目でも最初の入力を覚えているか（履歴がコンテキストに乗るか）
  - 途中で別の話題 → 元の話題に戻れるか
  - 同一スレッドの session_id が全ターンで一致しているか（DB で確認）
- **ID/scope の遷移**: 作成系は「仮 ID（new-xxx）で開始 → 実 ID 発番」で **ID が変わる**。
  - 実 ID 発番後の次ターンが、 同じ会話/状態につながるか（空セッションに落ちないか）
  - リスト/サイドバーから再オープン → 元の会話/状態が復元されるか
  - 再オープン後に継続 → 同じ状態につながるか
- **画面間の引き継ぎ**: 画面 A で入力/作成 → 画面 B に渡す → **B に正しく入っているか**
  - 中央フォーム → 右パネル / モーダル → 親 / ウィザード Step1 → Step3
- **永続化と復元**: 入力途中でリロード → 復元 or 警告 / 別タブで開いて変更 → 反映
- **★作りかけ（in-progress）の途中リロード（最頻出・最も壊れやすい）**:
  ウィザード / チャット / 複数ステップフォームを **完了前に F5 リロード** して、
  **画面・入力・スレッド・ヘッダが壊れないか**を必ず見る。
  - クライアントの React state（useState）だけに持っている値は **リロードで全消失**する。
    → 中央パネル・カードが空/0/プレースホルダになる、 スレッドが別物に変わる、
      ヘッダから選択中の対象（学校/顧客/案件）が消える、 等の典型バグ。
  - **検証手順**: ①作りかけを作る ②**完了前に**ページをリロード ③同じ画面に戻り、
    入力済みの値・進行中の会話・選択対象が **実データのまま残っているか**を確認。
    localStorage / sessionStorage / URL / サーバのどこに永続化されているか（あるいは
    されていないか）も確認する（DevTools Application タブ）。
  - 「作成して仮 ID → 実 ID 発番」系は、 途中リロードで **仮 ID の作りかけが孤立**して
    一覧/サイドバーに「名無し/プレースホルダ」で出る事故が多い。 必ず踏む。
- **状態リセット**: 「リセット」「新規」ボタンが **関係する全状態をクリア**するか
  （片方だけ消えて不整合にならないか）
- **★引き継ぎ/事前入力データの尊重（downstream で無視・再質問しないか）**:
  画面 A / フォーム / 前ステップで **既に与えた情報を、 受け取り側（次画面・AI・次ステップ）が
  無視して聞き直す / 取得し直す** のは UX 崩壊。 必ず確認する。
  - フォームで学校/顧客/対象を選んで渡した → 受け取り側が「どれにしますか？」と再質問しないか
  - AI/エージェントに条件を渡した → AI が一覧取得ツール（list_xxx）を呼んで聞き直さないか
    （**実際に呼ばれたツール列を見る**。 与えた ID を使わず検索系を呼んだら NG）
  - ウィザード Step1 の入力が Step3 で空になっていないか
  - **検証手段**: 渡したデータ（ID/値）が「そのまま使われた」ことを、 ツール引数 / API リクエスト /
    DB の作成レコードで確認。 「正しい応答が返った」だけでは不十分（偶然一致を排除）
  - **非決定な相手（LLM 等）は複数サンプル**: 1 回 OK でも、 2〜3 回流して
    「毎回 与えたデータを尊重し、 検索系を呼ばない」一貫性を確認する

**実行手順の鉄則**: ステートフル機能は必ず **3 ターン以上** 連続実行し、 各ターンで
「前の状態を覚えているか」を確認する。 API テストなら同一 scope/session で連続 POST し、
レスポンスとツール呼び出しを観察（例: 2 ターン目で「最初から作り直す」挙動になったら文脈喪失）。
UI テストなら実際に画面を遷移・リロード・再オープンして状態が生きているか見る。

### G. 層またぎ・統合整合（★ 単一画面では絶対に出ない・取りこぼし高リスク）

「各画面は単体で PASS なのに実運用で落ちる」バグはここを飛ばすと残る。 コードを **横断**して
初めて見えるため、 画面別 TC とは **別建て**で機能横断の TC を必ず起こす。 各項目は
「実際に叩く / 実際に開く / 実数と突き合わせる」まで行い、 想像で PASS にしない。

| # | 観点 | テスト項目（具体） | 検証手段 | 典型バグ |
|---|---|---|---|---|
| G1 | BE↔FE enum/ラベル整合 | API が受理する値（status/role/type 等）の集合と、 画面のフィルタ選択肢・ラベル定義が一致するか | grep で両側を列挙して差分確認 + 各値を実際に送って 200/422 を見る | 片側に値が欠け「取得に失敗」 |
| G2 | ルート登録の実在 | ハンドラが存在する全エンドポイントが実際に **登録**され応答するか | エンドポイント一覧を **全件 curl** し 404/405 が無いか | ハンドラはあるが route 未登録で 404 |
| G3 | ナビ全リンク（param 無し） | サイドバー/メニュー/タブの **全項目**を ?id 等 **無し**で直接開く | 各リンクへ遷移してエラー無く描画されるか | 詳細前提の画面が直リンクで落ちる |
| G4 | リロード/セッション永続 | 主要画面で F5 リロード | リロード後にログイン画面へ飛ばないか・状態が残るか | 期限切れトークンで強制ログアウト |
| G5 | 一覧フィルタの実効 | 各フィルタ値を順に適用 | 件数/中身が実際に変わるか・エラーにならないか（全件と同じなら絞れていない） | フィルタが効かない / 特定値で 500 |
| G6 | 作成→再取得→DB 突合 | 作成後、 **別 GET** と **`select`** で実在確認 | 作成レスポンスだけで PASS にしない。 一覧/詳細/DB の 3 箇所で確認 | 作成成功表示だが保存されていない |
| G7 | 集計値 vs DB 実数 | ダッシュボード等の数字 | `select count(*)` と突合・内訳合計＝総数か | 数字が DB と合わない |
| G8 | マイグレーション適用 | 新カラム/CHECK/index | `\d table` で実在確認・新旧シードの整合 | 列追加忘れ / 既存行が NULL のまま |

> **証拠（必須）**: G 系も passed には証拠を残す。 curl のレスポンス、 `select` の結果、
> リロード後のスクショ等を `evidence` に入れる。 証拠の無い passed は捏造扱い（SKILL.md 鉄則）。

### H. クリーン環境 / 0状態 / プロビジョニング（★ seed済みDBでは原理的に検出不能・必須）

**なぜ別建てか**: 「seed済み/汚れたDB」を相手にしたテストは、**fresh（空）でだけ顕在化するバグを永遠に見逃す**。
代表例＝「seed が学生のログインPWを設定し忘れていて、新規DBに seed すると誰もログインできない」。
既存DBには過去の状態でPWが残っていたため、何度テストしても通ってしまう。 こういう
「**初期構築・初回登録・seedの健全性**」のバグは、 **データを0にしてからの通し**でしか出ない。
よって「seed済み/途中状態のテスト（A〜G）」とは **別軸**として、 **0からの通しを必ず1本以上**起こす。

| # | 観点 | テスト項目（具体） | 検証手段 | 典型バグ |
|---|---|---|---|---|
| H1 | 空DB起動 | 全テーブル0件の状態でアプリを開く・主要APIを叩く | 空状態UIが描画され、 空API=200 か適切な4xx を返すか（500/throw で死なないか） | 空配列前提漏れで undefined 参照→500 |
| H2 | 空での認証拒否 | データ0件で各ログインを試行 | 例外でなく適切に拒否（管理=403/401・学生=401 等）するか | 認可テーブル空で 500 / クラッシュ |
| H3 | 初回ブートストラップ | 最初の管理者を手順通り作成 → ログイン成立 | 「Auth ユーザー＋権限テーブル行」等の**二重要件**を満たす手順が成立し 200 になるか | 片方だけ作って永遠にログイン不可 |
| H4 | 初期データ投入の通し | 管理者で 期生/クラス等の親 → 子（学生）を **実UIの導線**で作成 | CSVテンプレ **DL→記入→アップロード**で学生作成まで実際に通す | テンプレ列と取込仕様の不一致 |
| H5 | 0→ログインの貫通 | H4 で払い出された **デフォルトPW**で当の学生がログイン | 学生ログイン 200 → 主要画面/API が空〜最小データで動く | 作成はできるがログインできない |
| H6 | 認証モデルの明示確認 | 管理=発行のみ/学生=自己登録(signup)の有無 | signup の有効/無効、 PW の出所（自動採番/手入力）を実装で確認し計画に明記 | 仕様認識と実装のズレ放置 |

#### H-seed. seed / fixture の健全性（★ seed それ自体をテスト対象にする）

seed は「テストの前提」ではなく「**テスト対象**」。 汚れたDBで通っても fresh で壊れるなら不合格。

| # | 観点 | テスト項目 | 検証手段 | 典型バグ |
|---|---|---|---|---|
| S1 | fresh seed の成立 | **全テーブルを TRUNCATE → seed のみ実行**（手動補正なし） | seed 直後にログイン等の基本フローが**素で**成立するか | 既存DBでは通るが fresh で破綻 |
| S2 | 必須項目の欠落 | seed が落としている必須列が無いか | ログインPW・必須FK・status 等を seed 行で実値確認 | PW/必須値が NULL のまま |
| S3 | 冪等性 | seed を2回流す | 重複/制約違反で壊れないか（onConflict 等） | 2回目で落ちる |
| S4 | 本番との分離 | 本番DBに demo seed を流していないか | 本番=実データ運用、 seed=dev/検証のみ を明示 | 本番に架空データ混入 |

> **実施手順の型**（毎回 fresh から）: ① 全テーブル TRUNCATE（または使い捨てDB）→ ② 空状態スモーク（H1/H2）
> → ③ seed のみ実行 or 手動ブートストラップ（S1〜/H3）→ ④ 初期データ投入の通し（H4/H5）→ ⑤ 検証後に復元（再 seed）。
> **証拠**: TRUNCATE 後の count=0、 seed 後の必須列の実値（PW 等）、 0→ログイン 200 の network を `evidence` に残す。
> 本番DBで H/S をやる場合は **必ず事前にユーザー承認**（破壊的・本番投入のため。 SKILL.md「本番DBを勝手に汚さない」）。

## I. 実操作網羅・死にボタン・UI到達性・反映貫通（★単体/契約テストでも到達確認でも検出できない・必須）

«画面が開く / API が 200 / 自動テスト緑» «だけ» で「実装済み/PASS」にした結果、 死にボタン・作成しても画面に出ない・
UIから到達できないデッドコード・本番の実状態で詰む、 を大量に見逃した。 これらは «部品を見るテスト» と
«数画面だけ深く＋残りは到達確認» の死角。 **full モードでは全画面に対して別建てで必ず実走**する。

| # | 観点 | テスト項目（具体） | 検証手段 | 典型バグ |
|---|---|---|---|---|
| I1 | 全インタラクティブ要素の実操作 | 各画面の **全ボタン・全リンク・全フォーム送信・全タブ・全トグル・全 select** を 1 つずつ実際に操作 | 画面ごとに要素を列挙し、 各々をクリック/入力/送信。 未操作が1つでも残れば planned | «開いた»だけで未操作の要素が放置される |
| I2 | 死にボタン（ハンドラ＋API実在） | 各ボタン/リンクが (a) onClick/href/type=submit 等の **ハンドラを持つか** (b) 叩く **API メソッド(POST/PUT/DELETE)が route に実在するか** | コード確認＋実クリックで «何も起きない» を検出。 route.ts に該当メソッドが export されているか grep | ボタンはあるが未結線 / GETのみで作成APIが無い |
| I3 | 一般化の禁止（各個別実行） | 作成/編集/削除フローを **画面ごとに個別に最後まで実行** | «同型だから他もOK» の推測 PASS を禁止。 各フォームを実送信 | 1つ通ったから他もOKと決めつけ別物の失敗を見逃す |
| I4-S | ★到達性・nav配線(静的・env/ブラウザ不要・必ず最初に実施) | nav/menu の **href 文字列集合** と **実 page ルート集合** をファイルから突合する。**双方向で見る**: (a) href→ルート不在=404、(b) route→nav未掲載=孤立 | ① 全 layout/nav の href を抽出 ② 全 page ルートを列挙 ③ **href→実在しないルート=404リンク** と **route→どの href からも指されない=孤立** を機械差分。rewrites/router.push も grep で確認 | **nav href=`/agent/dashboard` だが実ページは`/s/402`でルート不在=全リンク404**（Ppon QA-002）/ 実装画面がメニュー未掲載で孤立 |
| I4-S2 | ★href→**そのパス直下の index page 実在**まで確認(死にリンクの見落とし防止) | href `/x` に対し、`/x` の **index ページ(例: app/(g)/x/page.tsx)** が実在するかを確認する。**`x/` ディレクトリが在るだけ・`x/new` や `x/[id]` など子ルートだけでは `/x` 自体は404**。「ディレクトリが在る=到達可能」と早合点しない | href 集合の各 `/x` について `x/page.tsx`(動的セグメント無しのindex)をファイル存在チェック。確証のため dev 起動後に **全 href を実際にHTTPで叩き 404 を炙り出す**(静的で漏れた死にリンクを動的probeで二重に捕捉) | **nav「AI社員」`/ai-employees` だが index page 不在(子の`/new`・`/[id]`のみ)で /ai-employees が404**(jobrain F-005) / `/settings` が子ページのみで index 無く404 |
| I4 | UI到達性（全ルート） | 実装済み **全 page ルートを列挙**し、 各々へ **ナビ/リンク/ボタンから実際に辿り着けるか** | 全ルート列挙→UIから到達を試行。 経路ゼロ=孤立/デッドコード | 機能はあるがUIにリンクが無く到達不能 |
| I5 | 作成→UI反映の貫通 | create/update 後、 **別GET再取得→一覧/詳細/関連画面(例:生徒側)に表示→DB突合** | 作成成功表示«だけ»で PASS にしない。 UI に出るところまで | 保存はされるが画面に反映されない |
| I6 | 主要書込を最後まで | 登録/編集/削除、 CSVテンプレDL→記入→アップロード→結果(成功/重複/不正)→DB反映、 受講操作(解答→採点→記録/提出→反映/視聴→進捗保存) | 各書込を end-to-end で実走し、 結果がUI＋DBに出る | 途中までで «できたつもり» |
| I7 | 実状態・エッジ網羅 | **実デプロイ先(本番)の実状態**＋ «0/空»（必須selectの元マスタ0件で詰む）＋ «重複/全半角ゆれ»（同名マスタ2件）＋ «任意入力の未設定»（締切null で後段が必ず失敗） | ローカルseedだけで通さない。 実環境/0/重複/未設定で操作 | seedでは通るが本番状態で詰む |

> **モック対比**: モックがある場合、 各画面を対応モックと並べ ボタン/タブ/フォーム/入力欄/列/セクションが
> **全て存在するか要素単位で照合**し、 欠落を FAIL。 «作り直し»で要素が脱落していないかを必ず突き合わせる。
> **証拠**: 実クリックのスクショ / route.ts のメソッド存在 grep / 作成後の別GETレスポンス＋DB突合 / 到達経路 を `evidence` に。

## M. 実機でしか出ない10類型の狙い撃ち（★製品バグ30件を検出した実績・必須）

[rules/common/lessons-learned.md](../../../rules/common/lessons-learned.md) L-003 の
検証ギャップ図鑑（G-01〜G-10）に対応する具体的なTCを、各画面/各runで必ず起こす。
**ユニットテスト200本超が緑・CI全green・ビジュアルパス完了の状態で30件出た**ので、
「テストが緑だから不要」という判断は成立しない。

| TC観点 | 具体的な手順（これをやらないと出ない） | 対応G |
|---|---|---|
| 死にボタン検査（実操作） | 全ボタン/リンク/select/トグルを**実ブラウザで押し**、押した結果（遷移/DB変化/表示変化）を確認。jsdomはネイティブ検証・チャートのポインタイベント・mousemoveを再現しないので緑のまま死ぬ | G-01 |
| 単一防御層の摘発 | 「起きてはいけない」事項について**上流を故意に壊す**（routeで禁止データ/500を返す・DBへ不正値を直INSERTしてロールバック）。UI/API/DBの何層で守っているか数える | G-02 |
| UI断線（Dead API） | `related_apis` の各エンドポイントについて「UIのどの操作から呼ばれるか」を突合。呼び出しが無いAPIを列挙（APIは緑・画面も緑・その間が断線） | G-03 |
| リンク到達性 | ナビ/カードの**href集合 ⇔ 実在ルート集合**を機械照合（ブラウザ不要・数行）＋実機で全項目を開いて<400 | G-04 |
| 共通シェルの全画面測定 | 共通ヘッダ/ナビ/フッタを含む**全画面**で `scrollWidth - clientWidth` を数値測定。1画面OKにしない（ログイン画面だけPASSして全画面が溢れていた実例あり） | G-05 |
| 仕様⇔実装の機械突合 | 仕様JSON（states/related_apis/transitions/policies）と実装を**実機に入る前に**突合し欠落を一覧化。1画面ずつ実機で発見するより数十倍速い | G-06 |
| 列見出しだけの摘発 | 見出しではなく**セルの値**を見る。実データでも `—`/空が変わらない列は未実装（列見出しだけあって値が永久に入らない実例あり） | G-07 |
| 到達しないメッセージ | 実装されたエラーメッセージ・分岐を**1つずつ実機で出す**。出せないものはデッドコード | G-08 |
| 期待値の出所 | 期待結果は仕様/モック/要件から書く（鉄則5） | G-09 |
| QA自身の衛生 | 破壊的操作はQAが作ったデータに限定。既存を変えるなら**変更前を記録し`finally`で復帰**。FAILは製品バグ/テスト誤りを**プローブで切り分け**、記録を分離 | G-10 |

### 実行順序（効率が最大化する順）
1. **静的突合を先に**（G-06/G-03/G-04）— ブラウザ不要で数分。ここで欠落が大量に出るので実機前に修正する
2. **実機で全要素を押す**（G-01/G-07/G-08）
3. **故意に壊す**（G-02）
4. **共通シェルを全画面で数値測定**（G-05）
5. **FAILの切り分け**（G-10）

## 重要度の付け方

- **P0**: 認証・決済・データ整合・権限境界・主要 CRUD の正常系。 壊れたらリリース不可。
  **死にボタン(I2)・作成→反映の断線(I5)・UI到達不能(I4)・本番状態で詰む(I7) も P0**（ユーザが触って即発見＝リリース不可）
  **0からの初回構築（H3/H4/H5）と fresh seed 成立（S1/S2）も P0**（新環境で動かない＝リリース不可のため）
- **P1**: 主要バリデーション・一覧/詳細表示・戻る・検索・エラーハンドリング
- **P2**: 初期値の文言・配色・ページネーション端・CSV 詳細・レスポンシブ・境界の細部

### J. AIエージェント / チャット 動作検証（★ AI/LLM/tool-use を含むプロダクトで必須・stub誤認を潰す）

「画面が出た/200/文章が返った」では AI が意図どおり動く保証にならない。**実会話を走らせ、tool呼び出し・副作用・目的到達まで**実機で確認する。応答テキストだけ・モック応答での PASS は禁止。

| # | 観点 | テスト項目（具体） | 検証手段 | 典型バグ |
|---|---|---|---|---|
| J1 | AI面の洗い出し | チャット/対話ビルダー/自律実行/ツール実行/AI生成・提案/承認フロー を全列挙 | コード横断で LLM呼出・tool dispatch箇所を grep し一覧化 | 一部AI面が未テストで放置 |
| J2 | 実LLM接続 | 実際に会話を1往復させ応答を得る | network で実APIコールを確認(モック/echoでない) | echo stub / LLM未接続を実装済みと誤認 |
| J3 | 意図→ツール選択 | 「Xして」に対しAIが正しいtoolを選ぶ | 実際の tool_use 名・引数を観察 | 誤ったtool / tool呼ばず作文だけ |
| J4 | 副作用の反映 | tool実行後 DB/外部に実際に書かれたか | `select`/再GETで実データ確認 | tool_use 表示のみで実行されない |
| J5 | 入力の尊重 | 与えたID/値をそのまま使い再質問しない | tool引数/作成レコードで確認・LLMは2〜3サンプル | 渡した値を無視し検索/再質問 |
| J6 | 複数ターン継続 | 3ターン以上で文脈保持 | 連続実行し前ターン参照を確認 | 2ターン目で文脈喪失/作り直し |
| J7 | 承認ゲート | 破壊的/送信/金銭操作で承認要求・未承認で非実行 | 承認前に副作用が無いことをDBで確認 | 承認前に実行されてしまう |
| J8 | 非決定性/stub検出 | 同一入力2〜3回で一貫性、固定文言でないか | 出力を複数サンプル比較 | 毎回同一のecho=stub |
| J9 | 異常系・回復 | LLMキー無効/レート/タイムアウト/tool失敗 | わざと失敗させユーザー向け挙動を確認 | 無効キーで白画面/500・回復不能 |
| J10 | 生成/提案の実体 | 対話ビルダー等が入力に応じ内容が変わる | 異なる入力で出力差分を確認 | 入力無視の固定既定値(Phase stub) |

> **証拠(必須)**: J 系の passed には「実際のtool呼び出し列」「DB差分(select結果)」「複数サンプルの出力」「実APIのnetwork」のいずれか実体を残す。応答テキストだけ・モック応答は証拠にならない。
> **P0**: J2(実LLM接続)/J4(副作用反映)/J7(承認ゲート)/J10(生成の実体) は P0。1つでも stub/未配線なら「実装済み」と判定してはならない。

### K. 全ルート×実スキーマ整合・実DB貫通（★第7軸 route-sweep / systemic バグの面的検出）

screens 経由で表面化した分だけでなく、**全サーバハンドラ**を実DDL突合＋実DB実行で検証する。mock緑の死角。

| # | 観点 | テスト項目 | 検証手段 | 典型バグ |
|---|---|---|---|---|
| K1 | 母数確定 | 全 route/handler をメソッド単位で列挙し総数N | ルーティング規約に沿い全件grep | 一部ルートが未検証のまま放置 |
| K2 | 列名整合 | insert/select の列名が実テーブルに存在 | ハンドラ ⇔ DDL 突合 | "column X does not exist" 500 |
| K3 | enum値整合 | enum列への代入値が定義に含まれる | 代入値 ⇔ enum定義 | "invalid input value for enum" 500 |
| K4 | NOT NULL/FK | 必須列を漏れなく与え FK 先が実在 | DDL の制約 ⇔ insert | NOT NULL違反 / FK違反 |
| K5 | client this束縛 | DBクライアントのメソッドを分離呼びしていない | grep `const x = client.method` → bind/直呼び | "reading 'rest'" 等で全API500 |
| K6 | 認可role | RLS/ガードが DBロールでなくアプリroleを見る | 述語 ⇔ クレーム/セッション変数 | 書込/管理が常に拒否 |
| K7 | 文脈伝播 | リクエスト文脈(GUC等)がクエリと同一Txで効く | pre-request hook 等の有無 | RLS が空値評価で0件/エラー |
| K8 | 実DB貫通 | 各ルートを実DB・実セッションで実行 | 実トークン/cookieで叩く(モック禁止) | 500/0件/403 |
| K9 | seed妥当性 | seed/fixture の id が本番同等の妥当形式 | 検証(uuid等)に通るか | "validation failed" |

> **完了条件**: 全ルート(N件)を K2–K8 で検証し pass(または妥当4xx)+証拠。残数0まで未完。routes タブに記録。

### L. 負荷・スケール・容量（★第9軸 load-scale-capacity / 「増えた瞬間に壊れる」を面的検出）

少データ・1ユーザーでは原理的に出ない «スケール劣化» 群。**想定規模までデータを増やし・並行で叩き・上限に到達させて**実測する。
推測(«捌けるはず»)で PASS にしない。閾値は数値で assert。

| # | 観点 | テスト項目 | 検証手段 | 典型バグ |
|---|---|---|---|---|
| L1 | スケール前提宣言 | 想定ユーザー/テナント/1テナント当たりレコード/ピーク同時実行/総容量 を見積り明記 | 要件・事業計画から数値化(後続の根拠) | 「何件で十分か」が無くテストが恣意的 |
| L2 | N倍シーディング | 代表テーブルを段階投入(例 1万→10万→100万 / 多テナント×多レコード) | seedスクリプト/`generate_series`一括INSERT(使い捨てDB) | 投入自体が遅い/失敗=設計上の上限露呈 |
| L3 | 一覧/検索/集計の規模耐性 | 大量データで一覧・検索・集計・ダッシュボードがタイムアウト/全件ロード/メモリ超過しないか | 各画面/APIを大量データ下で実測(`time_total`) | 全件ロードで固まる/集計N+1で数秒 |
| L4 | ページング | 大量データでページング/カーソルが端まで正しく効くか | 最終ページ・境界・OFFSET肥大を踏む | OFFSET劣化/件数ずれ/重複・欠落 |
| L5 | 同時実行・負荷 | 代表EP/主要フローを並行実行し p50/p95/p99・エラー率・スループット | k6/autocannon/wrk/ab、無ければ `xargs -P`/Playwright並列 | 並行でエラー率急増/レイテンシ爆発/デッドロック |
| L6 | クエリ性能 | 重い経路を EXPLAIN(ANALYZE) し seq scan・欠落index・実行時間 | DBクライアントで EXPLAIN | index無しで seq scan/フィルタ・ソートが効かない |
| L7 | 容量・上限 | ストレージ/添付/トークン/レート/プラン上限に**到達させ**超過時の挙動 | 上限ちょうど/+1 を実際に踏む | 超過で500/無言切り捨て/データ破損 |
| L8 | 劣化と回復 | 高負荷/依存遅延でCB/リトライ/バックプレッシャが働き、引いたら回復 | 負荷を掛けて落とし→解除して復帰確認 | 詰まったまま固まる/カスケード障害 |
| L9 | 規模・並行下の整合 | 大量・並行投入後も RLS分離/集計=`count(*)`/一意制約・採番が崩れない | 規模・並行条件でセクションGの整合を再検証 | 並行作成で重複/集計ずれ/テナント越境 |

> **証拠(必須)**: L 系の passed には「実測の p50/p95/p99・エラー率・スループット」「EXPLAIN 出力」「上限到達時の実レスポンス」
> 「シード後の `count(*)` と集計値の一致」のいずれか実体を残す。「速い気がする」「捌けるはず」は証拠にならない。
> **完了条件**: スケール前提(L1)を宣言し、想定規模で L3–L9 を実測 assert。閾値超過・上限500・整合崩れ=0。scale-capacity タブに記録。
> **破壊的シードは使い捨て/ローカルDBで行う。共有/本番DBに対しては事前にユーザ承認**。
