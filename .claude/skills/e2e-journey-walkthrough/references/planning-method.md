# シナリオ設計 — 代表ミニプロジェクトを1本・依存順・実成果物・実結果観察

SKILL.md [1] の詳細。**「その製品で回すべき代表業務(ミニプロジェクト)」を1本のストーリーとして設計**し、
依存順のジャーニー行(実務ステップ)に落とす。画面チェックリストではない(それは human-grade-qa)。

## 1. まず「代表ミニプロジェクト」を1本決める

その製品を実際に導入した人が最初に回すであろう、一番代表的な業務を1つ選ぶ。抽象でなく具体で。
- Atelier(開発案件管理): 「新規クライアントの小さめ開発案件を、ヒアリングから納品まで1件回す」
- 予約サイト: 「新規店舗を1つ開店させ、枠を出して、一般ユーザーが1件予約する」
- EC: 「新規出店者が商品を1つ出し、ユーザーが1個買って、発送・受取まで」
このストーリーが背骨。全ロールのジャーニーはこの1本に紐づく。

## 2. ロール別ジャーニーの骨格（実務を通す）

各ロールで、実際の業務として下記を1本通す。**「やる実務」「作る実成果物」「観察する実結果」を必ず持つ**。

| phase | やること(実務) | 実成果物 / 観察する実結果 |
|---|---|---|
| onboard | 新規登録(利用規約等も実際に踏む)+初期設定 | アカウント・初期セットアップが出来ている |
| auth | ログイン/ログアウト(別ログイン経路/招待トークンも本経路で) | セッション確立 |
| provision/configure | そのロールの準備・作成・設定(実務そのもの) | **後続が使える実物**(テナント/枠/招待/初期設定)。招待なら**メール到達**も観察 |
| operate | 日常の実務(依頼/承認/実装/コメント/調整/デザイン作成/動線定義 等) | **実成果物**(要件/デザイン/コメント/予約/注文)+**状態遷移** |
| outcome | そのロールのゴール | **最終成果の実物**(納品物がクライアント画面に出る/予約完了番号/購入完了/レポート) |

## 3. Atelier(開発案件管理) の代表シナリオ（本リポジトリ）

「新規クライアントの小開発案件を1件、ヒアリングから納品まで回す」を、依存順で:
```
運営(admin):   スキル/テンプレ/運営ナレッジが整っている(前提整備)
  └ owner:      新規登録(規約)→ワークスペース作成
       → クライアント招待(メール送信を観察) + メンバー招待(デザイナー等)
       → ヒアリングを実施し記録   → 要件定義を作成
       → 実際に開発タスクを進める(作成/割当/実行/承認)
       → 打合せ/MTG の日程を調整する
       → デザイナーメンバー: デザインを作成(モックは OSS Open Design で作る)
       → 各画面の動線・エラー挙動(このボタンで→ここ/この時こういうエラー)を画面ごとに定義
  └ クライアント: 招待経路でサインイン → 進捗/デザイン/成果物を閲覧
       → デザインや成果物に**コメントを入れる**(社内も入れる) → やり取りが両側に反映
  └ owner:      コメント反映 → **納品**(成果物確定・クライアント側に納品物が出る=最終成果を目視)
```
※「クライアントがコメント」「デザイン作成」等は**実際にやる**。順序厳守(デザインが無いのにコメントは不可)。

## 4. 予約サイト の代表シナリオ

```
運営: 新規店舗テナントを発行(店舗オーナー招待/メール観察)
  └ 店舗: ログイン → 営業時間/メニュー/料金 → 予約枠・日程を実際に設定
       └ ユーザー: 新規登録→ログイン → 店舗検索 → 空き枠を選んで**実際に予約**
            → **予約完了番号が出る**/**確認メールが届く**/店舗側の予約一覧に反映 を観察
            └ 店舗: 予約を承認/変更 → ユーザー側の状態遷移とメールを観察
```

## 5. EC / 業務系 も同型

- EC: 出店承認→商品/在庫登録→ユーザーが購入(注文番号/確認メール/在庫減)→発送→受取/レビュー。
- 業務系(申請承認 等): 申請者が申請→承認者が承認→反映/通知→完了状態、をストーリーで。

いずれも「代表業務を1本・依存順・各ロールが実務をやって実成果物を出す・実結果(状態/メール)を観察」。

## 6. 依存順(DAG)の作り方

エンティティごとに (生成主体, 消費主体, 前提) を書き出し、「Xが無いとYが成立しない」の辺を引いて
トポロジカルソート。消費(予約/コメント/閲覧/受領)は前提が全て揃ってから。`depends_on` に前提行の
id を列挙(BLOCKED 判定の根拠)。

## 7. 既存データ通し と 新規作成通し（両輪）

`data_condition` 列で区別:
- **existing**: 既に用意済み/前ロールが作った実データで回す(回帰・速い)。
- **create-new**: 自分/前ロールが**その場で作成・編集・削除**してから回す(作成導線と反映を見る)。

## 7.5 CRUD を各エンティティで一通り（★閲覧だけにしない）

各ロールが扱う主要エンティティごとに、**作成→閲覧→編集→削除(またはアーカイブ/無効化/失効)**を
ジャーニー行に入れる。「整備済を確認」「一覧を見る」だけで終わらせない。同種でも実際にやる。
各操作で観察する実結果:
- **作成(C)**: 一覧に出る・他ロール側に反映・監査/通知
- **閲覧(R)**: 一覧/詳細で正しい値
- **編集(U)**: 変更が反映・他ロール側にも反映・状態遷移(下書き→公開等)
- **削除/失効(D)**: 一覧から消える/アーカイブされる・消費側(ユーザー/クライアント)から見えなくなる・
  依存先の挙動(例: 枠削除→その枠の予約不可、招待失効→クライアント入れない)
例(Atelier 運営): スキルを **1件アップロード→一覧確認→編集→削除**。テンプレ/運営ナレッジも同様。
例(予約サイト 店舗): 予約枠を **作成→編集(時間変更)→削除**し、ユーザー側検索/予約への反映を観察。
※削除は**自分が作ったテスト用データに限定**(既存の本番データは消さない)。

## 8. 現実の分岐(物語の枝として)

網羅チェックリストではなく、実運用で起きる枝をシナリオに織り込む: 差し戻し/再依頼、期限切れ招待、
満枠/在庫切れ、権限外(クライアントは編集不可・他テナント不可)、キャンセル/中断→再開、二重送信。
`branch` 列に種別を書く(happy/validation/permission/empty/limit/conflict/cancel/isolation)。

## 9. 実結果の観察（このスキル特有・重要）

各行で「**実際に何が起きたか**」を必ず確認・記録する:
- **状態遷移**: 下書き→公開 / 予約済→確定 / タスク実装中→承認待ち 等が本当に変わったか。
- **メール/通知**: 招待・予約確認・コメント通知等。実送信環境なら受信、不可なら送信ログ/キュー投入を確認。
- **相手ロールへの反映**: owner が作った成果物がクライアント画面に出る、店舗の枠がユーザー検索に出る 等。
これらが `evidence`。「画面が出た」だけでなく「意図した結果が起きた」を証拠にする。

## 10. 計画の受け渡し(plan.json)
`scripts/journey_workbook.py init --plan plan.json` に渡す。1要素=1行(実務ステップ)。スキーマは
`references/excel-schema.md` の「plan.json スキーマ」。`order`(依存順) と `depends_on` で順序を表現し、
`action`(やる実務)・`expected`(出るべき実成果物/実結果) を具体に書く。
