# e2e-journey-walkthrough（通し / リアル・ドッグフーディング）

## このスキルの役割（一言で）

**製品を実際に使って、その製品で回すべき代表的な業務(ミニプロジェクト)を、
最初から最後まで一周させ、実際の成果と結果を出す。** 人になりきって本当に使う。

例(このリポジトリ=開発案件の管理 Atelier): ユーザーが新規登録(利用規約も見る)→ワークスペース作成
→クライアント招待+メンバー招待→**ヒアリング**→**要件定義**→実際に**開発**を進める→**打合せの調整**を
やってみる→**デザイン**をデザイナーが作る(モックは OSS Open Design で作成)→そこに**クライアントと
社内がコメント**→**各画面の動線/エラー**(このボタンで→ここ、この時こういうエラー)を定義→**納品**まで。
これを1本のストーリーとして本当に通す。

例(予約サイト): 運営が**各店舗テナントを発行**→各店舗が**予約枠・日程を設定**→ユーザーが**実際に予約**→
**どういう状態になるか・確認メールは届くか**まで観察。

## human-grade-qa との棲み分け（重要 / 混同禁止）

| | human-grade-qa | e2e-journey-walkthrough (本スキル) |
|---|---|---|
| 見るもの | **画面/機能が個別に正しいか**(描画/トークン/API/RLS/状態/AI/負荷) を軸ごとに網羅 | **その製品で想定した業務が、実際に一周まわり切って成果が出るか** |
| 粒度 | 画面単位・機能単位の網羅QA | 業務ストーリー単位のドッグフーディング |
| 例 | 「/portal が 200 でモック忠実に描画」 | 「クライアントを招待して、その人が実際にデザインにコメントを入れられ、社内が動線を定義し、納品まで届いた」 |

→ **画面が描画されるか/API が 200 か は本スキルの目的ではない**(human-grade-qa がやる)。
本スキルは「登録→…→最終成果」の**業務が本当に成立し、実物(成果物・状態・メール)が出る**ことを見る。
両方あって初めて「作った製品が実際に使えて、想定の仕事が回る」と言える。

### ⚠️ この棲み分けは「仕様書を見ない理由」にはならない（実際に事故った）

2026-08-25、この節を根拠に「これは通しだから画面網羅は human-grade-qa の担当」と判断し、
**既に存在していた 40 画面 764 項目の正本 `.qa/test-specs/screens/*.md` を一度も開かず**、
自作の使い捨てスクリプトで 16 チェックだけ実行して「一周した」と報告する事故が起きた。
実際に触ったのは 45 画面中 10 画面。クライアントポータル(R-T08 = 致命級)にも課金にも
触れていなかった。**棲み分けは「担当の分担」であって「無視してよい」ではない。**

そこで本スキルには次の 2 つが必須手順として入っている(下の [1.5] と [3.0])。

- **通しで触る画面については、その画面の TC ID を消化対象として宣言し、実際に消化する**
  (通しの中で自然に踏む TC は、通しの中で埋める。踏まないものは残件として明示する)
- **AI・チャットが絡む行は `ai-runtime-matrix` の AI-xxx ID に紐づける**

こうすると「通し」の成果が **正本の消化率**として数字で出る。16/764 を「一周した」と
書くことが構造的にできなくなる。

## 絶対原則

1. **本当に業務をやる**。ダミー投入で"通した"ことにしない。実際に画面を操作し、実際の成果物
   (ヒアリング記録/要件/デザイン/コメント/動線定義/予約/納品物 等)を作り、**最終成果を画面で目視**する。
1.5. **CRUD を実際に一通り回す(閲覧だけで済ませない)**。各ロールが扱うエンティティ
   (スキル/テンプレ/運営ナレッジ/ワークスペース/メンバー/プロジェクト/タスク/工程/デザイン/成果物/
   予約枠/商品 等)は、**作成→閲覧→編集→削除(あるいはアーカイブ/無効化/失効)**を実際にやって、
   各操作の結果(一覧反映・他ロール側反映・状態・監査/通知)を観察する。**同種のものでも「既にある/
   整備済を確認」で済ませない**。運営の初期整備も「整っている」の確認ではなく、実際に **1件 追加→
   編集→削除** して回す。破壊的操作(削除)は自分が作ったテスト用データに限定する。
2. **実結果を観察する**。状態遷移(下書き→公開/予約済→確定 等)、**メール到達**、通知、相手ロール側への
   反映を、実際に確認する(メールは実送信できる環境なら受信を、不可なら送信ログ/キュー投入を確認)。
3. **順序が命**。プロビジョニング→設定→消費。前提(テナント/枠/成果物/招待)を作る前に、消費
   (予約/コメント/閲覧/受領)を先にやらない。成立し得ない通しは無意味。
4. **各アカウントタイプで演じる**。管理者/運営・テナント/店舗・作成者・メンバー・クライアント・
   エンドユーザー等、ロールを自然な順序で全部本人として動かす(管理者を飛ばさない)。
   **Excel の `role` 列を数えれば飛ばしたロールは一目で分かる** — 実際 2026-08-25 に見つけた
   過去の通しは owner 15 / client 2 で、**運営が 0 行**だった。init の前に role 別の件数を数え、
   0 のロールが無いことを確かめる。
5. **1本の物語として通す**。バラバラのアクション確認ではなく、1つのミニプロジェクトが登録から
   最終成果まで連続して繋がること。前ロールが作った実データを次ロールが使う(=順序が守れている証拠)。
6. **分岐も現実の業務の一部として踏む**。差し戻し/再依頼/期限切れ/満枠/権限外/キャンセル等、
   実運用で起きる分岐をシナリオに織り込む(網羅チェックリストとしてではなく、物語の枝として)。
7. **Excel に全て出す。全行 PASS まで完了にできない**(blocking)。
8. **自作の使い捨てスクリプトで本スキルを代替しない。** 通しを名乗るなら、正本(`.qa/test-specs/`)を
   読み、分母を宣言し([1.5])、Excel に落とし、ゲートを通す([6])。ハーネスを書くこと自体は構わないが、
   **それは正本の TC を消化する手段であって、正本の代わりではない**。「その場で思いついた項目を
   実行して報告する」は、実行した本人にはやり切った感覚が残るが、**何を検査しなかったかが
   誰にも分からない**。今日それで 764 項目中 16 項目を「一周」と報告した。
9. **見つけたバグは、直すだけでなく正本に行を足してから完了とする。** 正本に無い観点で見つけた
   バグは、**次も同じように見逃す**。2026-08-25 に見つけた「同意記録の版が登録日になっていた」は
   S-A01 の 16 項目のどこにも無い観点だった。**正本を実行するだけでは、正本の穴は永久に埋まらない。**
   実行 → バグ発見 → 修正 → **正本へ追記** の循環で初めて分母が育つ。
10. **「できなかったこと」を成果の隣に必ず書く。** AI 実行基盤が無い / 権限が無い / 外部連携が
   未設定 — 理由は何であれ、**踏めなかった範囲を名前つきで書く**。書かないと、読んだ人は
   「全部確認された」と受け取る。BLOCKED は恥ではないが、黙って落とすのは報告の捏造に近い。

## 全体プロセス

```
[0] 発見    製品が何のアプリで、代表業務(ミニプロジェクト)は何か、誰が(ロール)、
            何を(実成果物)、どの順で作り・使うかを掴む。
[1] シナリオ設計  ドメインに合った「現実的なミニプロジェクト」を1本設計し、依存順の
            ジャーニー(各ロールの実務ステップ+実成果物+観察する実結果)に落とす。
[1.5] 分母の宣言  既存の正本(.qa/test-specs/screens/*.md, ai-runtime-matrix.md)を読み、
            鮮度を確かめ、今回消化する TC ID を列挙する。ai_required で実行場所を分ける。
            ★ここを飛ばすと「やった分」が「やるべき分」に化ける(実際に事故った)。
[2] 出力    シナリオを Excel 化(全行 status=TODO)。scripts/journey_workbook.py
[2.1] 埋める  action/steps/expected/depends_on/branch/note を **空欄なしで** 埋める。
            ★過去の通し Excel は全行 PASS なのに手順も期待結果も空で、何をやったか
            復元できなかった。空欄の Excel は記録ではない。
[2.5] 計画レビュー(実行前の関門)  「何を通すか(代表業務)・ロール実行順・依存・各ロールが
            作る実成果物・観察する実結果・使う環境(本番/dev)」を先に提示して合意を得る。
            実行は実データ/実メールを生むので、計画に納得してから[3]に入る(いきなり実行しない)。
[3.0] 判定基準  各行の合否は正本の「期待結果」列をそのまま使う。自作の緩い判定
            (「空でない」「N 文字以上」)を発明しない。
[3] 実行    ブラウザ MCP で「本人として」実際に業務をやり、実成果物を作り、実結果を観察。
[4] 記録    各行に PASS/FAIL/BLOCKED + 証拠(スクショ/実成果物/状態/メール) を書き戻す。
[5] 収束    FAIL は直すか起票、BLOCKED は依存解消、全行 PASS まで [3]-[4]。
[6] 完了    Excel 全行 PASS + Summary 100% で初めて完了。1行でも未達なら未完了。
```

設計の詳細(ドメイン別の代表シナリオ・依存順・実結果の観察対象)は `references/planning-method.md`、
Excel の列と blocking は `references/excel-schema.md` を読む。

## [0] 発見（何の製品で、代表業務は何か）

**このアプリで一番回すべき業務ストーリー(ミニプロジェクト)は何か**を先に決める。
コード/ルート/権限ガード/モック/スキーマ/既存資料/DB を横断して:

- **ドメインと代表業務**: 何を提供する製品で、成功とは「何が出来上がる/起きる」ことか。
  Atelier=開発案件を受けて納品する。予約サイト=店舗が枠を出しユーザーが予約する。EC=出店して売る。
- **アカウントタイプ/ロール**と入口(サインアップ/別ログイン経路/招待トークン)。
- **実成果物と生成主体**: 誰が何を作り、誰が消費するか(ヒアリング記録/要件/デザイン/予約/注文/納品物…)。
- **依存関係(DAG)**: 「Xが無いとYが成立しない」を洗い出す。実行順の根拠。
- **観察すべき実結果**: メール/通知/状態遷移/相手側反映など「実際に何が起きるか」の対象。

## [1] シナリオ設計（現実的なミニプロジェクトを1本） — ★まず計画から

**いきなり触り始めない。まず「何を通すか」を計画するのが最初の仕事。** 最初の成果物は
「**代表業務(ミニプロジェクト)は何か / どのロールが何を どの順で やるか / 依存(前提)は何か**」。
特にロール実行順は**管理側の設定が先、ユーザー側の反映は後**が原則(例: 運営が店舗テナントや枠を
設定していないのにユーザーが予約はできない/反映されない、owner がデザインを作る前にクライアントは
コメントできない)。この順序を depends_on と order で先に固定してから実行に入る。

`references/planning-method.md` の方法で、**ドメインに合った代表シナリオを1本**組み、依存順の
ジャーニー行(=検証可能な実務ステップ)にする。各ロールで「新規登録→ログイン→**実務**→実成果物→
最終成果」を通し、`depends_on` で順序を固定。各行に「**やる実務**」「**作る実成果物**」「**観察する
実結果(状態/メール/通知)**」を必ず書く。既存データ通しと新規作成通しの両輪、現実の分岐(差し戻し/
期限切れ/満枠/権限外/キャンセル)も物語の枝として入れる。MCP/外部連携経路があればその通しも。

## [1.5] 分母の宣言（実行前の関門・これを飛ばすと通しが自己申告になる）

シナリオが決まったら、**触る前に「今回どこまで消化するか」を数字で宣言する。**
分母が無いと、実行後に「やった分」が自動的に「やるべき分」に化ける。今日そうなった。

### 分母の作り方

1. **既存の正本を先に読む。** `.qa/test-specs/screens/*.md`(画面別)と
   `.qa/test-specs/ai-runtime-matrix.md`(AI 実動)。**無ければ通しを始めない** —
   human-grade-qa の test-plan モードで先に作る(鉄則0 と同じ理由)。
2. **正本の鮮度を確かめる。** 正本は放っておくと現実から遅れる。次を機械的に見る:
   - 実在する画面(`app/**/page.tsx` 等)に対し **仕様書が無い画面** が無いか
   - 最終更新日から後に入った変更(git log)が反映されているか
   - **古い正本を 100% 消化しても、新しい機能は 1 行も検査されない。** 穴があれば先に埋める。
3. **消化対象 ID を列挙する。** 通しで踏む画面の TC ID + AI-xxx ID を並べ、
   「今回の分母 = N 件 / 全体 = M 件」を宣言する。
4. **踏まないものを明示する。** 「今回は課金と運営画面に入らない」なら、その ID 群を
   **残件として名前つきで残す**。黙って落とすのと、名前をつけて残すのは全く違う。

### ai_required で実行場所を分ける

AI の実行(チャット応答・成果物生成・モック改訂・Bridge 経由のタスク遂行)は、
**実行者の環境に AI 実行基盤が無いと物理的に走らない**。この差を曖昧にすると
「未確認」が「たぶん動く」に化ける。各 ID に次を付ける:

| タグ | 意味 | 扱い |
|---|---|---|
| `ai_required: no` | AI 無しで完結する | **実行環境で 100% 消化する。落とさない** |
| `ai_required: yes` | AI 実行基盤が要る | 走らせられないなら **BLOCKED として残し、実行できる環境向けの手順書を出す** |

`ai_required: yes` を「環境が無いので対象外」と黙って消すのは禁止。**BLOCKED は残件であって、
消化ではない。** 手順書には「どの画面で何を入力し、何が出れば PASS か」を、実行者がそのまま
なぞれる粒度で書く。

## [2.1] Excel は「行ごとに次の人が実行できる」まで埋める（空欄は記録ではない）

Excel を出すこと自体は難しくない。**難しいのは、後から読んだ人がその行を再現できること。**

実事故(2026-08-25 に発覚): 過去の通し Excel は 3 回分あり **全 17 行 PASS** だったが、
`action` / `steps` / `expected` 列が **すべて空**だった。ID とロールしか残っておらず、
**何をやって何を確かめたのか誰にも復元できない**。しかも `role` は owner と client だけで、
**運営(admin)を一度も演じていなかった**（絶対原則4 違反）。
記録は残っていたが、次の人が使える正本にはなっていなかった。

だから、**init に渡す plan.json の時点で次を全部埋める**:

| 列 | 埋め方（空欄で init しない） |
|---|---|
| `action` | その行で何をするか **1 行**。「予約する」ではなく「空き枠を選んで予約する」 |
| `steps` | **画面での具体操作**を番号つきで。次の人がそのままなぞれる粒度 |
| `expected` | **何が画面に出れば成功か**。「正しく動く」ではなく「作成した枠が一覧に出る」 |
| `depends_on` | 前提行の id。**土台を飛ばして消費側から始めた通しは成立しない** |
| `branch` | happy 以外も必ず混ぜる（validation / permission / empty / limit / conflict / cancel / isolation） |
| `note` | **実行場所**（この環境で消化できるか / AI 実行基盤が要るか）を書く |

**行 = 1 ステップ**。1 行が「登録する」のように大きすぎると、その行の PASS が何を保証するか
分からなくなる。**入力エラーを一つずつ出す・同意なしで拒否される・正しく入れて通る**は別の行。

> 自己質問（init の直前）: 「この plan.json を **半年後の自分が読んで、そのまま実行できるか**。
> `action`/`steps`/`expected` が空の行は無いか。**全ロールが登場しているか**（運営を飛ばしていないか）。
> happy 以外の分岐が入っているか。」1 つでも No なら、まだ init しない。

## [3.0] 判定は正本の「期待結果」から書く（自作の緩い判定を作らない）

実行時、各行の合否は **正本の期待結果列をそのまま使う**。自分で判定条件を発明しない。

事故例(2026-08-25): 工程画面の判定を `本文が 40 文字以上あるか` と書いた。ログには 9 工程が
出ていたので目視では正しかったが、**テストとしては「空白でない」しか見ていない**。工程が
3 個に減っても通る。同様に 5 画面を `20 文字以上 + ナビがある` で判定し、
**サイドバーを意図的に外した全画面を「壊れている」と誤判定**した。

- 「空でない」「文字数が N 以上」「エラーが出ていない」は **判定ではなく生存確認**。
  正本にそう書いてあるとき以外は使わない。
- 期待結果が「モックの全要素が表示される」なら、要素を列挙して 1 つずつ確かめる。
  「role=alert + toast が出て状態が壊れない」なら、実際にエラーを起こして両方を見る。
- **自動判定が「怪しい」と言ったら、画面を実際に見てから結論を出す。** 上記の事故では
  自動判定が正常な画面を 1 件 NG と誤報しており、スクリーンショットを見て初めて分かった。

## [2] 出力（Excel）

`scripts/journey_workbook.py` で Excel 化(列/blocking は `references/excel-schema.md`)。
保存先 `<project>/.qa/e2e-journey/journey-<YYYYMMDD>.xlsx`。全行 TODO で開始。
```bash
python3 scripts/journey_workbook.py init   --out <xlsx> --plan <plan.json>
python3 scripts/journey_workbook.py update --out <xlsx> --id <id> --status PASS --evidence <path> --note "..."
python3 scripts/journey_workbook.py status --out <xlsx>   # 全PASSで exit 0、未達で exit 1
```

## [3]-[4] 実行と記録（本人として本当に使う）

依存順に1行ずつ、ブラウザ MCP で実際に業務をやる:
1. **新規登録/ログイン**: 実UIで登録(利用規約等も踏む)。account_type ごとの別経路(client/admin)も本経路で。
2. **実務を実行**: そのロールの仕事を画面から本当にやる(ヒアリングを記録、要件を書く、デザインを作る、
   コメントを入れる、動線/エラーを定義する、枠を作る、予約する 等)。実成果物を残す。
3. **実結果を観察**: 状態が変わったか、相手ロールの画面に反映されたか、**メール/通知が出たか**を確認。
4. **最終成果を目視**: ゴール(納品物がクライアント画面に出る/予約完了番号が出る/購入完了 等)を確認。
5. 各行を `journey_workbook.py update` で記録(PASS/FAIL/BLOCKED + スクショ + 実成果物/状態/メール)。
ロール切替は別セッション/別 cookie。次ロールは前ロールが作った実データを使う。

## [3.5] AI・チャットの通しは「会話が返ってきた」で終わらせない

AI が中核の製品では、**AI が絡む行こそ一番手を抜かれやすい**。理由は単純で、応答が返ってくると
「動いた」と感じてしまうから。だが実務で壊れるのは応答そのものではなく、**その周り**である。

通しに AI が出てくるとき、最低限この 6 面を物語の中で踏む。`ai-runtime-matrix.md` に該当 ID が
あればそれに紐づけ、無ければ**新しい行として起こす**(正本が古いのは普通に起きる)。

| 面 | 何を見るか | 抜けると何が起きるか |
|---|---|---|
| **実行経路** | どの経路で動いたか(利用者自身の契約 / サーバー鍵 / ローカル CLI)を**画面か記録で確定**する | 「動いた」が、**意図しない経路＝意図しない課金**で動いていても気づかない |
| **文脈の注入** | ペルソナ・案件状態・過去の会話・添付・RAG が**実際に応答へ反映**されているか(固有名を仕込んで再現を見る) | 器だけ動き、AI が何も知らないまま喋る |
| **ツール実行** | ツールが**起動したか / 誤起動しないか / 上限で壊れないか**。承認モードがあるなら**承認・拒否の両方**を押す | 承認を素通りする経路が残る |
| **成果物への着地** | 応答が**保存され、画面と DB の両方に出る**か。途中で切れたとき**半端な行を残さない**か | 会話は綺麗だが成果物が生まれない／壊れた断片が残る |
| **失敗と回復** | 鍵が無い・上流が落ちた・上限・混雑・中断。**画面に理由が日本語で出て、打った文章が消えず、再試行できる**か | 全部「失敗しました」に潰れ、利用者が原因に辿り着けない |
| **秘密の保持** | system prompt・内部プロンプト・社内の管理番号が**応答にも配布物にも出ない**か | 中身が漏れる。指示上書き(injection)にも耐えるかを見る |

**「AI 実行基盤が無いから対象外」は書かない。** `ai_required: yes` として BLOCKED に残し、
実行できる環境向けの手順書を出す([1.5])。**踏めなかったことと、踏む必要が無いことは別物。**

> 自己質問(AI が絡む行を PASS にする前): 「応答が返ったこと以外に、**何を確かめたか**。
> 経路・文脈・ツール・保存・失敗時・秘密のうち、この行で見たのはどれか。1 つも言えないなら
> それは『会話が成立した』だけで、通しの合格ではない。」

## [5]-[6] 収束と完了（blocking）

- **FAIL**: 通らないなら実装バグ。直すか起票し、当該行は FAIL のまま(残る限り完了ではない)。
- **BLOCKED**: 依存(前ロールの実成果物)未達 → 依存を先に解消。順序違反の兆候。
- **完了(DoD)**: `status` が全行 PASS(exit 0)、Summary 100%。1行でも TODO/FAIL/BLOCKED があれば
  「通し完了」と報告しない。報告には Excel パスと Summary(内訳/100%)、および**各ロールの最終成果の
  実物(スクショ/状態/メール)**を添える。

### 完了系の語は、ゲートの出力を貼ってからしか書けない（機械強制）

散文の歯止め(「自己質問せよ」)は、実行した本人には**やり切った感覚が残っている**ので簡単に
すり抜ける。だから機械に数えさせる。**「完了」「完璧」「一周した」「通した」「全部やった」
「done」「100%」を 1 語でも書く前に**、必ず両方を走らせて**出力をそのまま報告に貼る**:

```bash
# ① 通しの Excel が全行 PASS か
python3 scripts/journey_workbook.py status --out <xlsx>

# ② 分母([1.5]で宣言した正本の TC)の消化率
bash "<human-grade-qa の SKILL_DIR>/scripts/completion_gate.sh" .qa/test-specs
```

- どちらかが未達なら、総括は **【未完了（残 k 件）】** と書き、内訳を併記する。
- 「背骨は通った」「主要な流れは確認できた」等の**部分肯定も、同じ文に《全体は未完了・残 k》を
  併記**しなければ書かない。部分肯定だけを読んだ人は、全部終わったと受け取る。
- **報告に「できなかったこと」の節を必ず置く**(絶対原則 10)。BLOCKED の ID と理由、
  実行できる環境向けの手順書の場所を書く。

> なぜここまでするか: 2026-08-25、正本 764 項目のうち 16 項目だけを実行して「一周した」と
> 報告した。悪意は無く、**16 項目を実際にブラウザで丁寧に実行していた**。だからこそ危ない —
> 丁寧にやった実感が「網羅した」という言葉に化ける。**数えるのは人ではなく機械の仕事。**

## 汎用性（どのプロジェクトでも）

ハードコードしない。**[0]発見で毎回ドメイン/代表業務/ロール/実成果物/依存/観察対象を掴み直す**。
`references/planning-method.md` に 予約サイト / EC / SaaS(開発案件管理=Atelier) / 業務系 の
**代表シナリオ**テンプレと当てはめ方を用意。新ドメインでも 発見→シナリオ設計→Excel→実務通し→
blocking完了 の骨格は同じ。
