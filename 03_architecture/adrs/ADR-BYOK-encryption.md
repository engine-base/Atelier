# ADR: BYOK API キーの暗号化方式 — Fernet を正式採用する

- **状態**: Accepted (2026-08-15)
- **決定者**: dev (T-F-51) / 起票: PM (GAP-123) / 経営者へは PM から報告
- **対象**: 顧客が持ち込む LLM プロバイダの API キー (BYOK) の保管
- **関連**: `03_architecture/selected-stack.json` / T-F-19 / T-D-95 / GAP-123

---

## 1. 背景 — 何が食い違っているか

`03_architecture/selected-stack.json` は BYOK 暗号化に **Supabase Vault** を想定しており、
タスク T-F-19 の表題も「Supabase Vault（BYOK 暗号化）」になっている。

一方、実装は次の 2 層で成立している:

| 層 | 実体 |
|---|---|
| アプリ層の暗号化 | `apps/api/src/services/byok_keys/__init__.py` — **Fernet** (AES-128-CBC + HMAC-SHA256)。鍵は `ATELIER_BYOK_ENCRYPTION_KEY` env から読む |
| DB 層の露出制御 | `supabase/migrations/t-d-95_e022_byok_api_keys.sql` — `encrypted_key` 列を `authenticated` / `anon` から **列レベルで revoke**。service 層の `_COLS` も同列を返さない |

暗号化そのものは機能しており実害は出ていないが、**確定済技術 (CLAUDE.md ルール 9) からの
乖離が無記録**のまま残っている。本 ADR はこの食い違いを一方向に閉じるためのもの。

> 本 ADR は**文書化と裁定のみ**で、実装は変更しない (T-F-51 の制約)。
> 決定に応じた追随は後続タスクで行う (§6)。

---

## 2. 脅威モデル

守る対象は**顧客の API キー**。想定する脅威を、影響の大きい順に置く。

| # | 脅威 | 説明 |
|---|---|---|
| T1 | **DB のダンプ / バックアップ流出** | 最も現実的。Supabase のバックアップ、誤設定の公開、退職者の持ち出し |
| T2 | **DB 読み取り権限を持つ内部者** | `authenticated` ロールでの越境、運用者の SQL コンソール |
| T3 | **アプリサーバの侵害** | Fly.io のコンテナに侵入され env とメモリを読まれる |
| T4 | **鍵の紛失 / 誤ローテーション** | 復号不能になり顧客が再登録を強いられる (可用性側のリスク) |

---

## 3. 選択肢の比較

### A. 現行の Fernet + env 鍵 (アプリ層暗号化)

| 観点 | 評価 |
|---|---|
| T1 DB 流出 | **強い** — 復号鍵は DB の中に無い (Fly secrets)。ダンプ単体では平文にならない |
| T2 内部者 | **強い** — 列レベル revoke で `encrypted_key` 自体が読めず、読めても鍵が別管理 |
| T3 アプリ侵害 | 弱い — env に鍵があるため復号可能 (どの方式でも同様) |
| T4 鍵管理 | 中 — ローテーションは全行の再暗号化が必要。`MultiFernet` で新旧鍵の併用は可能だが未実装 |
| 運用コスト | **低** — 追加インフラ 0。既存の secrets 運用 (`ATELIER_AUTH_JWT_SECRET` / `ATELIER_VAULT_ENCRYPTION_KEY`) と同じ形 |
| 移植性 | **高** — Postgres 実装に依存しない |
| 現状 | **すでに稼働中**。移行リスク 0 |

### B. Supabase Vault への移行 (DB 層暗号化)

| 観点 | 評価 |
|---|---|
| T1 DB 流出 | 強い — 暗号化済で保存され、ルート鍵はダンプに含まれない |
| T2 内部者 | **やや弱い** — 復号が **DB 内**で行われるため、復号権限を持つロール (service_role / superuser) が SQL 一発で平文を取れる。現行は「DB 権限だけでは平文に到達できない」 |
| T3 アプリ侵害 | 弱い — アプリが復号 API を呼べる以上、A と同じ |
| T4 鍵管理 | 良 — 鍵管理を Supabase に委譲できる |
| 運用コスト | **中〜高** — Supabase 固有の運用が増える。実装・テスト・RLS 越境試験のやり直しが必要 |
| 移植性 | **低** — BYOK 保管が Supabase に強く結合する |
| 移行リスク | **中** — 既存行の再暗号化と切替が必要。失敗すると顧客が API キーを再登録する事態になる (T4 が顕在化) |

### 判断に効いた点

1. **主脅威 T1 に対して両者は同等**。DB ダンプ単体では平文にならない、が両方の性質。
2. **T2 では A が優る**。現行は復号鍵が DB の外にあるため、DB 権限だけでは平文に到達できない。
   Vault は復号が DB 内で完結するぶん、DB の高権限ロールが平文を取れる。
   BYOK は「顧客の資産を預かる」性質上、**内部者経路を狭く保つ方を重く見る**。
3. **B に移る利益は主に鍵管理の委譲**だが、その代償が Supabase への結合と移行リスク。
   現時点で A の鍵管理が破綻している事実は無い (Fly secrets 運用は JWT 署名鍵・Vault 暗号鍵で
   既に回っている)。
4. A は**すでに動いており、テストと列レベル権限まで揃っている**。動いているものを、
   同等以下のセキュリティ特性のために作り替える理由が無い。

---

## 4. 決定

> **現行の Fernet + `ATELIER_BYOK_ENCRYPTION_KEY` + 列レベル権限を、BYOK 暗号化の
> 正式な方式として採用する。Supabase Vault へは移行しない。**
> `03_architecture/selected-stack.json` と T-F-19 の記述を、この実装に合わせて更新する。

「今後検討」ではなく、この方向で確定する。再検討のトリガは §7 に明示する。

---

## 5. 決定に伴い受け入れるリスクと、その手当

| リスク | 手当 |
|---|---|
| 鍵ローテーション時に全行の再暗号化が要る | `MultiFernet` による新旧鍵併用の手順を運用手順書に整備する (後続タスク T-F-52) |
| 鍵を失うと復号不能 | `SECRETS.md` の保管ルールに従い 1Password 等へ保管済。バックアップ手順を上記手順書に含める |
| アプリ侵害時は復号され得る (T3) | どの方式でも同じ。Sentry のマスク (T-F-48/49) とアクセス制御で被害範囲を抑える |

**現行の暗号化・列レベル権限は一切弱めない。** 本 ADR は実装を変更していない。

## 7. 再検討のトリガ

次のいずれかが起きたら本 ADR を見直す。

- 顧客・監査から「鍵管理を外部 KMS に委譲していること」を要求された (SOC2 / ISMS の指摘等)
- Supabase が Vault を BYOK 用途で明確に推奨し、DB 外復号の経路を提供した
- 鍵ローテーションの運用が実際に破綻した (T4 が顕在化した)
- BYOK の保管対象が API キー以外 (顧客の個人データ等) に広がった
