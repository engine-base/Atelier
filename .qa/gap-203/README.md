# GAP-203 — 混雑を「故障」に見せない（断らずに順番待ち）

## きっかけ

経営者から「**上限を超えたらユーザーが使えなくなるのか、UX 最悪だよね**」。

## 何が起きていたか（実際にコードを読んで確認した）

同時本数の上限を 1 本でも超えると **その場で 503**。しかも画面側は
サーバーが返した日本語を読まずに `HTTP 503` としてだけ扱っていた:

```ts
// apps/web/app/chat/s_e01/_components/stream.ts （直す前）
throw new Error(`chat stream failed: HTTP ${res.status}`);  // ← 本文を読んでいない
```

その結果、利用者に見えるのは汎用の

> AI 応答の取得に失敗しました。時間をおいて再試行してください。

だけ。**混んでいるだけなのに壊れたように見え、しかも打った文章まで消えていた。**

## 直し方

### ① 断らずに並ぶ

上限は「同時に**実行**できる数」であって「受け付けられない数」ではない。
なので上限に当たったら列に並んでもらい、**空き次第そのまま実行に入る**。

- 並んでいる間は `queued` イベントで「順番待ち N 番目」を流し続ける
- 席が空いたら **列の先頭へ引き渡す**（後から来た人は割り込めない）
- 画面には「順番待ち 3 番目（目安 約 2 分）— 空き次第そのまま実行します」

### ② 目安の秒数は実測からしか出さない

直近の実行時間（最大 20 件）の平均から出す。**材料が無いうちは秒数を出さない**
（根拠の無い数字を出して外れると、次から信用されない）。

### ③ 断るときも理由が画面に届く

無限には並ばせない。**列まで一杯 / 待たせすぎ**のときだけ断る。そのときも
SSE の本文として日本語を返し、画面がそれを表示する:

> ただいま大変混み合っています。時間をおいてもう一度お試しください。
> （お客様の文章は消えていません）

### ④ 打った文章を消さない

送信に失敗したら入力欄へ戻す。押し直すだけで再送できる（書き直させない）。

### ⑤ 運営から見える

S-T01「同時チャット (SSE)」の行に **順番待ち人数 / 延べ待たせた人数 / 最長待ち
時間 / 並べずお断りした回数**を出す。「断ってはいないが待たせている」と
「断った」を**区別して**見られる。

## ここで見つかった実バグ（e2e で踏んだ）

**順番待ちの最中に画面を閉じると、席が戻らなかった。**

Python の async generator は、外側が閉じられても `async for` の中の generator を
自動では閉じない（GC 任せ）。そのため列に並んだままになり、**混むほど使える席が
目減りしていく**状態だった。→ 内側を明示的に持って `finally` で必ず閉じるようにし、
「席を割り当てられたのに受け取る前に抜けた」場合も必ず返すようにした。

自動テストと e2e の両方で固定してある。

## 実測（`e2e-output.log`）

本物の `guarded_stream` を使い、フェイクを挟まずに確認:

```
上限 2 本を埋める → 3 人目は 503 ではなく queued（1 番目）が届く
  → 断った回数 0（断っていない）
前の人が終わる    → 並んでいた人がそのまま本文を受け取る
待機中に閉じる    → 列から外れ、席は 2 本とも戻る
列まで一杯        → error として日本語の理由が本文で届く
実行時間を実測    → そこで初めて目安が出る（それまでは出さない）
```

## どこで動くか / 誰の費用か

サーバー側とブラウザ側の作り方を変えただけ。**追加費用 0 円**。
利用者の PC（Bridge）は 1 行も変えていない。

## まだやっていないこと（正直に）

- 順番待ちの上限は **上限本数の 2 倍**（1 台なら 2000 人まで並べる）。ここを
  超えると断る。今の実測（1 台 1000 人同時）から見て当面到達しないが、
  **到達したときの体験は「断り」のまま**。
- 目安の秒数は「直近の実行時間の平均 × 何巡目か」という単純な計算。
  実行時間の分布が偏ると外れる（外れても表示だけの問題）。
- 503 を「Bridge 未接続」の合図として使っている画面（GAP-168 の導線）は
  今回触っていない。チャット画面は混雑と区別できるようになったが、
  **他の画面はまだ 503 = 未接続として扱う**。
