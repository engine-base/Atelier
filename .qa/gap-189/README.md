# GAP-189 — 実行の制御：中断・実行中の追い足し・繋ぎ直し

経営者指摘 (2026-08-20):
> 「中断とか入ってないけど、これ Claude だとできるけど」
> 「止まっても裏のターミナルは変わらないんでしょ？ セッションも、
>   だったら続けてとかで自動で後ろは繋がるよね？」

## 直す前の実態（調べて分かった事実）

| ご認識 | 実際 | 根拠 |
|---|---|---|
| PC 側の作業場所は変わらない | **その通り** | `chat-relay.ts` — 毎回 `cwd: chatWorkspaceDir()` 固定。途中まで作ったファイルは残る |
| 実行は裏で走り続ける | **その通り** | ブラウザを閉じても Bridge は動き続け、出力は `chat_relay_chunks` に溜まる |
| セッションも繋がっている | **繋がっていなかった** | 起動引数は `-p` だけで `--resume` も `--session-id` も無い。毎回まっさらな `claude` を起動し、会話の中身はサーバーが DB 履歴＋ローリング要約から組み直して渡し直していた |

さらに、調べていて **実バグ** を発見した:

> `chat_sse/__init__.py` は assistant の返答を**ストリーミングを抜けた後**に保存していた。
> つまり生成中にブラウザを閉じる/リロードすると、**PC は最後まで仕事をして chunk も
> DB に残っているのに、その回の答えがスレッドから消えていた。**

そして中断は存在せず、生成中は入力欄が `disabled` で割り込みもできなかった。

## 直したこと

### 1. 中断 — クラウドだけでなく **PC 上の claude を実際に止める**

- `POST /chat/runs/{job_id}/cancel` で `cancelled`（終端状態）にする
- Bridge は `GET /chat-relay/{job_id}/control` を 2 秒ごとに読み、真なら
  **子プロセスに SIGTERM → 2 秒後に SIGKILL**
- 通信できないときは中断とみなさない（通信不良で走っている仕事を殺さない）
- **そこまでに出ていた本文は捨てず**、`（ここで中断しました）`を付けてスレッドに残す
- 他人の実行は止められない（`requested_by` 照合 / R-T08 系の分離）
- 中断済みジョブへの Bridge の完了報告は静かに受け取る（`done` で塗り替えない）

### 2. 実行中の追い足し指示 — 取りこぼさない

- 生成中でも入力欄は塞がず、送信ボタンが「あとで送る」に変わる
- 押すと `POST /chat/threads/{id}/queued` で **受領した瞬間に DB へ保存**
  → この後ブラウザが落ちても指示は消えない
- 今の実行が終わると `consume` で 1 件ずつ取り出して続けて流す。
  `for update skip locked` なので、同じスレッドを 2 画面で開いても二重に流れない
- 待ちの指示はコンポーザ上に一覧表示され、流す前なら取り消せる
- 上限 20 件（事故で無限に積まれるのを防ぐ）

### 3. 繋ぎ直し — 画面を閉じても答えが消えない

- **返答の保存をブラウザからサーバーへ移した**。`complete_job`（ジョブ確定）が
  chunk から本文を組み立てて `chat_messages` に入れ、`assistant_message_id` に控える
  （冪等 — SSE 側と二重投稿にならない）
- `GET /chat/threads/{id}/run` で「まだ走っている実行」が分かる
- `GET /chat/runs/{job_id}/attach`（SSE）で溜まった分を先頭から流し直して繋ぎ直す
- 画面を開いた時に自動で確認し、走っていれば繋ぎ直す

### どこで動くか・誰の費用か

| 部分 | どこで | 誰の費用 |
|---|---|---|
| 停止ボタン・待ち行列・繋ぎ直し API | Fly.io / Supabase（運営） | 運営 — 数十 ms の DB 操作。実質増分ゼロ |
| 中断の見張り（2 秒ごと 1 リクエスト） | 利用者の PC → 運営 API | 運営（実行中のみ・極小） |
| 実行そのもの | **利用者の PC の Claude** | **利用者のプラン枠** |

**中断は利用者のプラン枠の節約になる**（途中で止めれば以降のトークンを使わない）。

## 証拠 — `e2e-run-control.log`（実 PostgreSQL / 再現スクリプト同梱）

Bridge の役を実プロセスで演じ、**本物の子プロセスの生死**で確かめている。

1. **中断が PC まで届く** — 居座る実プロセス（pid あり）を起動 → 停止 →
   Bridge の見張りが検知 → `生存=False (exit=-15 = SIGTERM)`。
   ジョブは `cancelled`、途中までの本文はスレッドに残る
2. **中断済みへの完了報告** — `done` にならず `cancelled` のまま。吹き出しは 1 件（二重投稿なし）
3. **繋ぎ直し** — SSE を一切繋がずに Bridge の完了だけで、答えがスレッドに残る。
   ツール実況（`Bash`）は本文に混ざらない
4. **追い足し** — 2 件が保存され、順に 1 回ずつ取り出され、再取得は `None`（二重消費なし）
5. **分離** — 他人は止められない（`forbidden`）、他人からは走っている実行も待ちの指示も見えない

## 残っていること（別 GAP）

**Claude 側セッションの `--resume` 継続は未対応**（GAP-190 として起票）。
今は毎回まっさらな `claude` を起動し、会話の中身はサーバーが渡し直している。
話の内容は続くが、Claude Code 側のセッション状態（TODO・作業途中の状態）は毎回消える。
スレッドが「どの PC からでも開ける」設計と噛み合わせる必要があるため分離した。
