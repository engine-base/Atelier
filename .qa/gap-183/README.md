# GAP-183 — 自動実行の「見張り役」を利用者の PC に移す（運営コスト 0 円）

経営者とのやり取り (2026-08-19):
> 「このcronのスケジュールはFly.ioでやってんだろ？ コストはどうなるの？ こちらが持つのか？」
> 「基本はPCでやるけど、ここもスリープだと起動して過ぎたものはその時に実行されるんだよね？」
> 「滑り止め的にこれは準備してもいいかもね」

## 直す前の実態

GAP-179 で入れた発火役は **毎分動くクラウド cron** だった。Fly.io は
`auto_stop_machines = "stop"` / `min_machines_running = 0`（5 分アイドルで完全停止 ＝ ほぼ $0）
という設定なので、**毎分叩くとマシンが 24 時間起動しっぱなしになり、誰も使っていなくても
運営に固定費が発生する**。料金表の実額で **$2.02/月**。

## 直したあと — 役割分担

| 役割 | 誰が | 何を | 費用 |
|---|---|---|---|
| **時計（見張り役・主）** | **利用者の PC (Bridge)** | 60 秒ごとに `POST /bridge/run-due-schedules` を 1 本叩くだけ | **運営 0 円** |
| 時計（滑り止め） | Fly.io の cron | 15 分ごと。PC が長期間落ちていても集計が止まらない保険 | 月 $0.7 程度 |
| 実行係 | Fly.io の API | DB から発火時刻を過ぎた行を取り出し、集計 SQL を実行 | 同上に含む |
| AI が要る処理 | 利用者の PC の Claude | ナレッジ整理・進捗レポート | 利用者のプラン枠 |

毎分 → 15 分に落としたことで、クラウド側の稼働率は約 1/3 になる。

## 二重実行の防止（見張り役が 2 つある以上、必須）

PC とクラウドが同時に同じ行を拾うと、AI を使う自動実行が**利用者のプラン枠を二重に消費**する。
「たまたま大丈夫」ではなく構造で防いだ:

1. 発火対象を `for update skip locked` で取る（他方が処理中の行は黙って飛ばす）
2. **実行の前に** `next_run_at` を次回へ進める（実行中に拾われない）

## スコープ（マルチテナント）

利用者トークンで叩かれた場合は **その人が所属する workspace のプロジェクトだけ**を対象にする。
他人の PC が他社の予定を動かすことはない。インスタンストークン（セルフホスト / 運営）なら全件。

## 証拠

`e2e-schedule-watcher.log`（実 PostgreSQL）:

1. **他社の予定を動かさない** — A社の PC が見張ったとき、A社の実行履歴 1 件 / B社は 0 件
2. **二重実行しない** — PC とクラウドを同時に走らせ、拾った合計が 1 件・実行履歴も 1 件
3. **スリープ復帰** — `next_run_at` を 3 日前に戻して「PC を 3 日止めていた」状態を再現 →
   起動直後の 1 回で実行され、次回が未来の 09:00 (JST) に繰り上がる

テスト: `apps/api/tests/routes/test_bridge_schedules.py`（2 — スコープ / 二重実行）、
`apps/bridge/__tests__/schedule-ticker.test.ts`（10）、
`apps/web/tests/bundle-i/gap179-cron-actions.test.tsx`（画面表記 1 追加）

## 画面での表記

自動スケジュール画面の先頭に、隠さず書いた:

> 自動実行の時刻は、**お使いのパソコン（Bridge）が起動している間**に見張っています。
> パソコンがスリープ・停止していた間に過ぎた分は、**次に起動したときにまとめて実行**されます。
> パソコンが長期間落ちていても集計だけは止まらないよう、サーバー側でも 15 分ごとに確認しています。

## 既知の制限（正直に）

- PC を 3 日間止めていた場合、日次ダイジェストは **3 日分ではなく起動した日の 1 回**だけ生成される
  （溜まった分を全部作るとノイズになるため）。遡り生成が必要なら別途対応する。
