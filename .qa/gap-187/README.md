# GAP-187 — 議事録を根拠に次フェーズを提案する

経営者指示（「1,2 だね」の ②）: 議事録からフェーズ提案まで。

## 直す前の実態

フェーズ提案（GAP-150）は既にあったが、根拠が **「既存フェーズとタスクの状況」だけ**
だった。打合せで決まったこと・出た要件・未決事項こそが「次に何を確定すべきか」の
一番の材料なのに、それが提案の根拠に一切入っていなかった。

## 直したこと

### 議事録の 9 セクションを根拠に渡す（要約だけに頼らない）

GAP-184 で厚くした解析を活かし、**決定したこと / 出た要件 / 未決事項 / リスク /
数値・日付・金額 / 次回** を見出しごとに畳んで渡す。

### 「議事録に無いことを足すな」を指示に入れる

system プロンプトで
「提案は必ず議事録に書かれている内容を根拠にすること。議事録に無いことを推測で
足さないこと。reason には議事録のどの決定・要件・未決事項を根拠にしたかを具体的に
書くこと」を明示。

### 提案するだけで確定しない

作られるのは `pending` の提案 1 件のみ。**フェーズは 1 件も増えない**。
承認は既存のフェーズ提案フロー（GAP-150）と同じで、進行画面で人が承認して初めて
工程になる。未処理の提案がある間は 2 件目を作らない（人が捌けなくなるのを防ぐ）。

### 根拠を隠さない

`phase_proposals.source_meeting_id` にどの打合せ由来かを残す。
画面でも「まだ確定していません。進行画面で承認すると工程になります」と明示し、
承認画面へのリンクを出す。

### 嘘の提案を作らない

PC 未接続 / 枠上限 / 解析なし のときは、それらしい提案をでっち上げず、
**提案の行を 1 件も残さずに**理由を返す（画面はその理由をそのまま表示）。

### どこで動くか・誰の費用か

| 部分 | どこで | 誰の費用 |
|---|---|---|
| 提案の生成（AI） | **利用者の PC の Claude** | **利用者のプラン枠** |
| 提案の保存・承認 | Fly.io / Supabase | 運営（数十 ms） |

## 証拠 — `e2e-phase-from-meeting.log`（実 PostgreSQL、再現スクリプト同梱）

1. 提案へ渡す要点に、決定・要件・未決・リスク・数値・次回がすべて入る
2. 提案が作られ、`status=pending` / `source_meeting_id` に出典が残る
3. LLM へ実際に「構成は A 案で確定」「写真素材は誰が用意するか」「80 万円」
   「来週水曜 14:00」等が渡っていることを実測。「推測で足すな」の指示も確認
4. **phases は 0 件**（提案するだけで確定しない）
5. 未処理の提案がある間は 2 件目を拒否
6. PC 未接続では `bridge_offline` を返し、**提案行は 1 → 1 で増えない**
