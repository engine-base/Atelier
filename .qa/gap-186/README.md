# GAP-186 — 議事録の抽出項目を「確認して採用」→ 要件・タスク・決定へ

経営者指示（2026-08-19、「1,2 だね」の ①）:
> 議事録から抽出した要件を、確認して採用 → 要件に追加できるように

## 直す前の実態

GAP-184 で議事録の解析を 9 セクションに厚くしたが、**出るだけで終わっていた**。
「問い合わせフォームに自動返信が必須」と抽出されても、それをタスクや決定として
プロジェクトに残す導線が無く、人が手で打ち直すしかなかった。

## 直したこと

### 反映先を決めた（どこへ行くのかを隠さない）

| 議事録の項目 | 反映先 | 理由 |
|---|---|---|
| 抽出要件 | `tasks` | 実装単位に落ちるもの |
| アクション | `tasks` | 誰が何をいつまでに |
| 決定したこと | `decisions`（decided） | 決まったこと |
| 未決事項 | `decisions`（unresolved） | まだ決まっていないこと |
| リスク・数値・議題 | **反映先なし** | 「読むためのもの」。無理にタスク化すると台帳がノイズで埋まる |

要件の種類・優先度はそのまま引き継ぐ:
機能→`feature` / 非機能→`infrastructure` / 制約→`foundation`、
必須→`high` / 推奨→`medium` / 任意→`low`。

### 自動反映はしない

AI の抽出をそのまま正にすると、**聞き間違い・言い過ぎがプロジェクトの要件として
固定される**。GAP-156（既存資料の取り込み）と同じで「提案 → 人がチェック → 確定」。
一覧を開いただけでは実データは 1 件も増えない。

### 引用を必ず残す

作られたタスク・決定の本文に **文字起こしからの引用**が入る。
採用する前も後も「本当にそう言っていたか」を照合できる = 創作を人が検出できる。

### 工数を偽らない

議事録に工数は書かれていないので、作ったタスクの本文に
「工数は議事録に書かれていないため未確定です。分解時に見直してください。」
と明記する（それらしい数字をでっち上げない）。

### 二重採用しない・追跡できる

`meeting_adoptions` 台帳（`(meeting_id, kind, item_key)` に unique）で、
同じ項目を 2 回押しても増えない。台帳は「この要件はどの議事録から来たか」の
追跡も兼ねる。項目キーは見出しを正規化して作るので、解析をやり直しても同じ項目なら
同じキーになる。

### どこで動くか・誰の費用か

| 部分 | どこで | 誰の費用 |
|---|---|---|
| 採用の一覧・反映 | Fly.io / Supabase（運営） | 運営 — **LLM を一切呼ばない**（保存済みの解析結果を読むだけ） |
| 元の解析 | 利用者の PC の Claude（GAP-184/185） | 利用者のプラン枠 |

採用そのものに AI は使わない。決定的な処理なので、押した分だけ確実に反映される。

## 証拠 — `e2e-meeting-adopt.log`（実 PostgreSQL、再現スクリプト同梱）

Storage だけメモリに差し替え。採用ロジック・タスク/決定の作成・監査ログは本物。

1. 採用候補は反映先を持つ 4 種のみ（リスク「素材の到着遅れ」は出ない）
2. **一覧を見ただけではタスク 0 件 / 決定 0 件**（自動反映しない）
3. 6 件のうち人が選んだ 3 件だけを採用 → タスク 2・決定 1。
   タスク本文に引用と「工数は未確定」が入り、決定は `with_user=true` /
   `reflected_to=議事録: 打合せ_20260820.mp3`
4. 同じものをもう一度押しても増えない（「すでに採用済み」と正直に返す）
5. 採用済みは一覧で `済` と出て、反映先 ID へ辿れる
6. 台帳から「どの議事録から来たか」が引ける
7. 存在しない項目は黙って無視せず `missing` として返す
