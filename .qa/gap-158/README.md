# GAP-158: 出力デザインテンプレート — クライアント提出 HTML/PDF の「見た目の型」

経営者フィードバック (2026-08-19):
「テンプレの認識が違いすぎる。基本これらはスキルでやるので決まった内容には
なりやすい。だからフォーマットとかではなく**出力のデザインを作る場所**。
テンプレートに関してはそのタブ作っていい。そしてそこのデザイン (md や json は
スキルで整えるし、最後人間に見せる (クライアントに見せる) html や pdf の
デザインのテンプレって意味です)。なのでここも **open design の機能で作る状態**で
十分です。それをしっかり見れる感じで」

→ GAP-154 の「構成テンプレ (content_md に見出し・項目を人が書く)」は認識違い
だったため**廃止**し、作り直した。

## 何が変わったか

| | GAP-154 (廃止) | GAP-158 (今回) |
|---|---|---|
| 実体 | Markdown の構成メモ | **HTML 1 枚 (実際の見た目)** |
| 作り方 | 人が手で書く | **ワンダに指示 → 生成 (Open Design 方式)** |
| 意味 | 内容の構成を縛る | **視覚デザインだけを揃える。内容はスキルが担う** |
| 置き場所 | WS設定の中 | **専用タブ「テンプレート」** |
| 版 | 1 種類 1 件 (上書き) | **版連鎖 (改訂 = 新版・履歴不滅)** |

DB は `output_templates` を drop し `output_design_templates` を新設
(未リリースの直前 commit のためデータ移行なし)。

## 実装

- **どこで動くか / 誰の費用か**: 画面と保存は SaaS クラウド側。**テンプレ生成
  (ワンダ) は利用者本人の PC の Bridge 経由 = 本人の Claude サブスク**
  (relay → agent_sdk → API キー の確定チェーン。GAP-138 と同一)。
  実行経路が無いときは **503 で正直に断る** — 偽テンプレは作らない。
- **専用タブ「テンプレート」** (`/templates`): 3 ペインの Open Design スタジオ。
  - 左: 14 種類 (見積書/提案書/請求書/契約書/NDA/議事録/要件定義/アーキ設計/
    デザイン仕様/機能分解/タスク一覧/実装ドキュメント/テスト仕様書/納品書)。
    設定済みは緑ドット。
  - 中央: **A4 実寸 (794×1123) を枠に合わせて縮小した大きいプレビュー**。
  - 右: ワンダへの指示 (経過秒つき) + 版履歴 (クリックで過去版を閲覧)。
- **ワンダの契約** (`services/outputs/templates.py`): 完全な HTML 全文のみ /
  内容はダミーでよく**レイアウト・配色・タイポ・表の様式・余白が本体** /
  A4 縦の印刷・PDF 出力に耐える / 外部リソース非依存 (CSS は `<style>` 内包) /
  改訂時は指示箇所以外を変えない。
- **注入 (要の部分)**: 成果物の生成 (チャット) と改訂 (スティーブ) の system prompt に
  該当種類のテンプレ HTML を自動注入し、
  「**このテンプレのレイアウト・CSS・表の様式・トーンを踏襲し、内容 (テキスト・
  数値・項目) だけを依頼内容とスキルの構成に従って差し替えること**」を強制。
  = 内容はスキル、見た目はテンプレ、の分離が prompt レベルで担保される。

## WS設定について (「元々の WS の中身がガラッと変わっているけどなんで？？」)

**原因は GAP-154 の実装ミスです。** ナビの「WS設定」は元々
`/workspace-settings → /auth/s_a03` の rewrite で**実在の設定画面**(名前・アイコン・
メンバー・招待管理・MCPトークン・AI学習・プラン・退会) に繋がっていました。
GAP-154 で `app/workspace-settings/page.tsx` を新規作成したことで、
Next.js の実ルートが rewrite より優先され、**元の設定画面を覆い隠して**
出力テンプレ画面に置き換わってしまっていました (中身がガラッと変わった正体)。

今回そのディレクトリを削除したので、**WS設定は元の設定画面に完全復帰**しています
(`158-ws-settings-restored.png` で実測)。テンプレは独立した「テンプレート」タブへ。

- `158-studio-estimate.png` — 見積書 v2 の A4 プレビュー + 版履歴(2) +
  左リストの設定済みドット。「内容の構成・文言はスキルが整えます — ここは
  デザインだけ」の位置づけを画面に明示
- `158-past-version.png` — 版履歴から v1 を開いた状態 (「過去版を表示中」)
- `158-studio-hearing.png` — 種類切替 (議事録・ヒアリングメモ)
- `158-create-form.png` / `158-created-proposal.png` — UI からワンダに指示
  (「表紙は紺の帯 + 大きめタイトル、本文は 2 カラムで図表を右側に」) →
  「ワンダが v1 を作成しました」→ 提案書 v1 がプレビューに出るまで
- `158-ws-settings-restored.png` — WS設定が元の設定画面に復帰したことの実測
- `curl-evidence.txt` — 一覧 → v1 作成 → 改訂 v2 → 版履歴 → 署名 URL で HTML 配信 →
  **チャット context-preview への自動注入の実文面** → RLS 越境 404 →
  実行経路なしの 503 (偽成功なし) まで実 HTTP の記録

**LLM 経路の但し書き (正直な記載)**: この環境には Bridge も API キーも無いため、
上記 e2e の生成は `ATELIER_ALLOW_FAKE_LLM=1` の決定的スタブで**配線全体**
(指示 → 生成 → mockdb 保存 → 版 → プレビュー配信 → prompt 注入) を検証しています。
テンプレ HTML の中身の美しさは実 LLM (本人サブスク) 実行時の品質であり、
ここで証明しているのは配線と契約 (A4/印刷・外部リソース非依存・注入文面) です。
実行経路が無いときに 503 を返し**偽のテンプレ行を積まない**ことも実測済み
(`curl-evidence.txt` 項目 8)。
