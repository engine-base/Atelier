# GAP-201 — 待っている間は DB 接続を手放す（同時チャット 44 → 300 人）

## きっかけ

GAP-198 で「同時チャットの上限は 1 台 22 人 / 2 台 44 人」と報告したところ、
経営者から「**そんなに少ないとやばいじゃん、どうするの**」。

## 原因は「接続を握りっぱなし」だった

チャットは、利用者のパソコン（Bridge）で AI が動いている間ずっと画面と
サーバーをつなぎっぱなしにします（SSE）。そのとき、サーバー側は
**リクエストの DB 接続を 1 本掴んだまま**待っていました。長いと数分。

つまり「**同時に喋れる人数 = DB 接続の本数**」。DB 接続を増やす以外に
打つ手がない、という構造でした。

## 直し方: 待ちに入る前に確定して、接続を返す

AI の実行待ちの間、サーバーは DB に用がありません。だから

```
文脈を組む（DB 使う）→ ★ここで確定して接続を返す★ → 実行待ち（DB 使わない）→ 保存（DB 使う）
```

にしました。実測（`e2e-output.log`）:

```
文脈構築中          : 接続 1 本
commit 直後         : 接続 0 本   ← 待っている間は 0
100 本が待機中      : 接続 0 本 / メモリ増 0.4 MB
（比較）以前の方式   : 10 本待機で接続 10 本 ← 人数ぶん食い潰す
```

**副産物**: ユーザーの発言がこの時点で確定するので、生成に失敗しても
「送ったのに消えた」が起きなくなりました。

## ここで見つかった、もう 1 つの穴（RLS が消えていた）

`role` と `claims`（＝「この人のデータしか見えない」を DB に効かせる設定）は
**トランザクション単位**なので、**途中で commit すると消えます**。

払い出し時に 1 回だけ入れる作りだったため、**リクエストの途中で commit した
あとに走る SQL は、RLS が効かない状態（接続ロールのまま）で動いていました**。
今回「待つ前に commit する」ようにすると、これがそのまま穴になります。

→ `after_begin` フックで、**トランザクションが始まるたびに自動で貼り直す**
ようにしました。commit しても rollback しても RLS は効いたままです。
テストで「フックが無ければ消える」ことも固定してあります。

## 新しい上限は何で決まるか（実測）

DB 接続では決まらなくなったので、**待っている間のポーリング負荷**が上限に
なります（0.25 秒ごとに「続きが届いたか」を見に行く）。

同じ計測を 2 回走らせました（`measure-poll-output.log` に両方残してあります。
数字はマシンの都合でぶれるので幅で書きます）。

| 同時待機 | ポーリング 1 回の p95 |
|---|---|
| 50 | 46〜55 ms |
| 100 | 57〜74 ms |
| **150** | **76〜90 ms** |
| 200 | 104〜141 ms |
| 400 | 699〜787 ms（**飽和** = 応答が遅れ始める） |

ポーリング間隔 250 ms に対して十分な余裕がある **150 本/台**を既定にしました。

| | 1 台 | 2 台 |
|---|---|---|
| 同時チャット（GAP-198 時点） | 22 人 | 44 人 |
| **同時チャット（GAP-201 後）** | **150 人** | **300 人** |

`fly.toml` の `soft_limit` もこの数字に合わせています（150 / hard 300）。

## どこで動くか / 誰の費用か

サーバー側の作り方を変えただけで、**追加費用は 0 円**。VM のサイズも
DB のプランも変えていません。

## 次に足りなくなったときの手（今はやらない）

1. **ポーリングの往復を減らす** — 今は 1 回あたり 3 クエリ（続き・状態・承認）。
   1 クエリにまとめれば単純に約 3 倍さばけます。
2. **ポーリングをやめて push にする**（LISTEN/NOTIFY 等）。
3. Supabase の Supavisor（接続を数百に増やす）。

断った回数は運営画面（S-T01「同時チャット (SSE)」）に出るので、
**必要になるタイミングは数字で分かります**。
