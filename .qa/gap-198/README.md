# GAP-198 — SSE 同時接続の上限見直し（fly.toml の 50 は嘘だった）

## 依頼

「SSE 同時接続の上限見直し — 同時チャット 50 人で 2 台目が起動。それ以上は
遅くなる（実測 p95 2.6 秒 @ 同時 100）」

## 測ったら前提が違った

`fly.toml` には `soft_limit = 50` と書いてあった。しかし **SSE は張っている間
ずっとリクエスト scope の DB セッションを 1 本掴んだまま**である。実測:

```
SSE を 1 本張っている間の使用中接続: 1 (張る前 0)
ストリーム終了後の使用中接続: 0
```

つまり **本当の同時チャット上限は Fly の 50 ではなく DB プールの本数**だった。
GAP-197 以前は 1 台 15 本なので、**15 人目から待たされていた**。
しかも上限に当たると `pool_timeout`（当時 30 秒）ぶん黙って待たされ、
最後に DB のエラー文が出るだけ。利用者にも運営にも「混んでいる」ことが
分からなかった。

## 直したこと

1. **上限をアプリが自分で持つ** — DB プールの上限から逆算する
   （プール 30 − 予備 8 = **22 本 / 台**）。予備を残すのは、チャットで
   全部使い切って**普通の画面操作（一覧・保存）まで詰まらせない**ため。
2. **黙って遅くならない** — 上限に達したらその場で
   `503「ただいま混み合っています（同時に開ける上限 22 本に達しました）。
   少し待ってからもう一度お試しください。」`
   **実測 0 ms で返る**（待たされない）。
3. **切断しても枠が返る** — `finally` で必ず返却。返らないと上限が減り続けて詰まる。
4. **SSE を返す全経路が同じ守りを通る** — チャット / 繋ぎ直し / 実行ログ /
   モック生成。テストで「素通りしている経路が無いこと」を機械的に確認する。
5. **運営画面に出す** — S-T01 に「同時チャット (SSE)」行。
   接続中 / 上限 / **混雑でお断りした回数**。実際に足りているかを数字で見る。
6. **fly.toml の数字を実態に合わせた** — `soft_limit` 50 → **22**、
   `hard_limit` 100 → 60。50 のままだと「1 台で 50 本さばける」という嘘の前提で
   2 台目の起動が遅れる。

## 結果 (`e2e-output.log`)

```
[1] SSE 1 本 = DB 接続 1 本 (実測) / 終了後は返る
[2] 上限 3 に対して 4 本目 → 0 ms で status=503 + 日本語メッセージ
[3] 1 本閉じたら空いた枠に次の人が入れた (お断り回数 1 が記録される)
```

## どこで動くか / 誰の費用か

運営サーバー（Fly.io）。**費用は増えない**。`soft_limit` を下げたので
2 台目の起動は**早くなる**が、Fly は起動している秒数でのみ課金されるため、
「混んでいる時だけ 2 台」という挙動は変わらない。

## いま何人まで同時にチャットできるか（正直な数字）

| | 1 台 | 2 台（max_machines_running=2） |
|---|---|---|
| 同時チャット | **22 人** | **44 人** |
| 普通の API 呼び出し用の予備 | 8 本 | 16 本 |

44 人を超えるには GAP-197 の README に書いた **Supavisor（transaction pooler）**
への切り替えが要る。今は入れていない — 実 Supabase での検証が必要なため。
**上限に当たったことは「お断りした回数」として運営画面に出る**ので、
必要になったタイミングは数字で分かる。
