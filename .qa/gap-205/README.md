# GAP-205 — 増やすときに困らない状態にしておく

## きっかけ

経営者から「**supabase はなんの設定が必要なの？ $2.02 ずつ増えるわけではないんでしょ？
でも最大限いつでも、もし来たらすぐ対応できる状態にしておかないといけない**」。

## 何が問題だったか

GAP-202 で同時 2000 人まで捌けるようになったが、その先の壁は
**機械代ではなく DB 接続**だった。そしてその事実は

- 起動ログの数字を読み解かないと分からない
- 切り替えには **コード変更**が要る（asyncpg は pooler 経由だと prepared
  statement で落ちる）
- 押し出し通知（GAP-202）は pooler 経由では届かない

という状態で、**混み始めてから慌てる**作りだった。

## やったこと

### ① 切り替えを「設定だけ」にした

`ATELIER_DB_URL` を Supavisor の接続文字列にするだけで、アプリが
**自動で pooler モードと判断**し、prepared statement を無効にする。
（`pooler.supabase.com` か `:6543` を見る。明示したいときは
`ATELIER_DB_POOLER_MODE=1`）

**繋ぎ先を変えたのに設定を変え忘れる**、という一番ありがちな事故を
構造的に防いでいる。直結のときは無効にしない（遅くなるだけで得が無い）。

### ② 「あと何台増やせるか」を常に出す

S-T01 に **「増やせる余地 (machine 数)」** の行を追加。

```
DB 接続 (直結): 1 台あたり最大 30 (常設 20 + 追加 10) × 2 台 = 最大 60 / 予算 60
  — この予算で動かせるのは 2 台まで。これ以上 machine を増やすには
    Supavisor 経由へ切り替えが要ります (docs/scaling-runbook.md)
```

**増やそうとした日に壁を知る**のを無くすのが目的。

### ③ 手順書（`docs/scaling-runbook.md`）

段階 1〜4 で、何を見て・何を変えるかだけ書いてある。判断ではなく実行で済む。
**手順書が実在し、必要な環境変数が書かれていること**をテストが毎回検査する
（リンク切れ・記載漏れを防ぐ）。

## 実測できたこと / できないこと（正直に）

| | 状態 |
|---|---|
| prepared statement 無効のまま実 SQL が通る | **実 Postgres で確認済み**（パラメータ付き・繰り返し実行） |
| pooler の自動判定・予算計算・警告文 | テストで固定（13 件） |
| **Supavisor 本体の挙動** | **未検証。実 Supabase でしか試せない** |
| Supabase の実際の接続上限・料金 | **ダッシュボードで要確認**。推測の数字は書かない |

## 押し出し通知の扱い（重要）

Supavisor の transaction mode では `LISTEN/NOTIFY` が届かない。そのため
**待ち受け専用の 1 本だけ直結**を使う（`ATELIER_DB_LISTEN_URL`）。

設定し忘れても落ちない。**自動で従来のポーリングへ戻り**、S-T01 の
「チャットの押し出し通知」行が警告になる（GAP-202 で実装済み）。
つまり**黙って遅くなることはなく、画面を見れば設定漏れに気づける**。

## どこで動くか / 誰の費用か

設定と表示だけ。**追加費用 0 円**。切り替えを実行するまで挙動は今までと同じ。

## 費用の整理（正直に）

- **machine**: 1 台 月 $2.02、使わない間は $0。**線形**
- **Supabase**: 台数と無関係の**組織単位の月額**。段階的に上がる。
  **「$2.02 ずつ」ではない**
- **同時 2000 人までは Fly 側 月 $4。** その先は Supabase のプラン判断
