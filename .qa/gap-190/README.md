# GAP-190 — スレッドを「同じ Claude セッション」で走らせる

経営者確認（2026-08-20）:
> 「そのセッション内ではずっと同じターミナルのセッションとして走れるという
>   認識だよね？ それだと色々上記の問題も治ると思っているけど」
> 「スレッドがあれば、そのスレッドは再起動しても同じこれまでの会話の入っている
>   ものが引き継がれるってことだよね？」
> 「（アイドルタイムアウトは）それで OK。ただ再起動できるってことだよね？？」

**すべて Yes。実 CLI と実ファイルで確認した上で実装しました。**

## 直す前の実態

毎回まっさらな `claude -p` を起動し、会話の中身はサーバーが DB 履歴＋ローリング
要約から組み直して**毎回送り直していた**。そのため:

- Claude Code 側のセッション状態（TODO・作業途中）が毎ターン消える
- 履歴を毎回送るので、**利用者のプラン枠を余分に消費する**

## 設計の要点 — 「再開できるか」を誰が決めるか

セッションは PC ローカル（`~/.claude/projects/`）なので、**サーバーはその PC に
実体があるかを知り得ない**。推測すると「再開したつもりで会話が飛ぶ」事故になる。

そこで **Bridge が自分の PC の実ファイルを見て決める**:

1. サーバーはジョブに **2 つ**載せる
   - `prompt` … 新しい発言だけ（再開できたとき用）
   - `prompt_full` … 履歴を畳んだもの（再開できなかったとき用）
2. Bridge は transcript の実ファイルを見て選ぶ
   - あれば `--resume <id>` ＋ 新しい発言だけ → **履歴を送らない = プラン枠の節約**
   - 無ければ `--session-id <id>` ＋ 履歴込み → **会話が飛ばない**
3. Bridge は**実際に使ったセッション ID と再開できたか**を報告し、サーバーが
   スレッドに保存する → 「別の PC で開いた」「PC を初期化した」が**自己修復**する

パス解決は決定的:
`~/.claude/projects/<cwd の / を - に置換>/<session-id>.jsonl`（実測で一致を確認）。

`--append-system-prompt` は**再開時も毎回渡す** — ペルソナ・案件状況・RAG は
ターンごとに変わるので、履歴を送らなくても最新の文脈は効かせる。

## 証拠 — `e2e-session-continuity.log`（**本物の claude CLI を起動**、再現スクリプト同梱）

1. `--session-id` で開始 → transcript が実ファイルとして残る（2,984 bytes）。
   **Bridge が計算するパスと実際のファイル位置が一致**
2. プロセスが終了した後（= PC 再起動と同じ状態）、**履歴を一切送らずに**
   別プロセスで `--resume` → 「予算は？」に **「80万円」** と回答。
   **会話が引き継がれた**
3. 送信量: 履歴込み 72 文字 → 新しい発言だけ 16 文字（**78% 減**）。
   会話が伸びるほど差は大きくなる
4. 別ディレクトリ（＝別 PC 相当）ではセッションが無い → 履歴込みに切り替え、
   **会話は飛ばない**（同じく「80万円」）
5. DB: スレッドは同じセッションを持ち続け、Bridge が別 ID を報告したら
   **そちらで上書きして次ターンから確実に再開できる**（自己修復）

## どこで動くか・誰の費用か

| 部分 | どこで | 誰の費用 |
|---|---|---|
| セッション ID の採番・保存 | Fly.io / Supabase | 運営（数十 ms） |
| 再開可否の判定 | **利用者の PC**（ファイルを見るだけ） | ゼロ |
| 実行 | 利用者の PC の Claude | 利用者のプラン枠 |

**この変更は利用者のプラン枠を減らす方向にしか効きません。**

## GAP-189 との関係（置き換えではなく併存）

| | 担当 |
|---|---|
| 中断・実行中の追い足し・繋ぎ直し | GAP-189 |
| 返答をサーバーが保存（PC が落ちても消えない） | GAP-189 |
| 会話・作業途中の状態を PC 側で保つ | **GAP-190（本件）** |

PC が落ちた・ネットが切れたときに答えが消えないのは GAP-189 のおかげなので、
セッション継続はそれを置き換えません。

## 残っていること（別 GAP にしていない範囲の明示）

**常駐プロセス（1 プロセスを跨ターンで保持する形）は入れていません。**
今回入れたのは `--session-id` / `--resume` による継続で、毎ターン新しい
プロセスを起動します。これで「会話・TODO の継続」と「プラン枠の節約」は
実現しますが、**実行中のターンへ指示を直接差し込む**（Claude Code の
インタラクティブと同じ挙動）には常駐プロセスが要ります。
現状の追い足しは GAP-189 の「実行が終わったら次に流す」方式です。
必要になったら GAP-191 として起票してください。
