# GAP-202 — 「届いた？」と聞きに行くのをやめ、届いた瞬間に知らせてもらう

## きっかけ

経営者から「上限を超えたらユーザーが使えなくなるのか、UX 最悪だよね」「実行は
各自のパソコンなのに、なんでサーバーが止まるのか」。

## なぜサーバーが詰まっていたのか

AI が動くのは利用者のパソコン（Bridge）で、運営サーバーは**郵便屋**でしかない。
なのに、その郵便屋がこうしていた:

```
待っている 1 人につき 1 本、0.25 秒ごとに DB へ 3 クエリ（続き・状態・承認）
→ 300 人待機で 1 秒あたり 1,200 回の「届いた？」
```

**計算では詰まっていない。「届いた？」と聞き続ける部分だけで上限が決まっていた。**

## 直し方: 書いた側が知らせる

`pg_notify` を **DB の trigger** に置いた。SSE 側は寝て待ち、動きがあったときだけ起きる。

**アプリではなく trigger に置いた理由**: 書き込み経路は chunk 追記・状態更新・
承認・期限切れ・中断と複数ある。アプリ側に置くと「1 か所書き忘れて、そのチャット
だけ固まる」が起きる。DB に置けば経路を増やしても漏れない。

- 通知は **commit したときに配送される**ので「まだ読めないのに起こされる」がない
- 同一トランザクション内の同じ通知は Postgres が 1 通に畳む（chunk 20 行 → 1 通）
- LISTEN の接続は **プロセスに 1 本だけ**。そこから各チャットへプロセス内で配る

## 止まらないための保険（正直に）

通知は取りこぼしうる（接続断・再接続の隙間）。なので:

- 接続が落ちたら**待っている全員を起こして読み直させる**、そして再接続する
- 落ちたと報告されないまま通知だけ消えた場合の保険として、**30 秒ごとの再確認**を残す
- 待ち受けがそもそも張れない環境では、**従来の 0.25 秒ポーリングへ自動で戻す**

つまり通知が全部死んでも、**遅くなるだけで止まらない**。e2e でわざと壊した設定を
使って確認済み。

**そして黙って劣化させない**: 運営画面 S-T01 に「チャットの押し出し通知」行を出し、
繋がっていなければ理由つきで警告する。

## 実測

### ① 待っている間の DB 負荷（`measure-output.log`）

| 同時待機 | 旧 聞きに行く | 新 知らせてもらう |
|---|---|---|
| 50 | 5 秒で 2,820 クエリ | **0** |
| 100 | 5,259 | **0** |
| 150 | 7,776 | **0** |
| 200 | 10,251 | **0** |
| 400 | 10,605（飽和） | **0** |

### ② 画面に文字が出るまで（`e2e-output.log`）

本物の SSE ループで実測して **最遅 8.9 ms / 平均 7.3 ms**。
旧方式は 0.25 秒ごとに見に行くので平均 125 ms 遅れていた。**速くもなった。**

### ③ 新しい上限（`measure-ceiling-output.log`）

| 同時待機 | メモリ増 | 通知の配達 p95 | 待機中の DB 接続 |
|---|---|---|---|
| 150 | 0.5 MB | 12 ms | 0 |
| **1000** | **2.5 MB** | **20 ms** | **0** |
| 2000 | 3.4 MB | 27 ms | 0 |
| 5000 | 11.0 MB | 77 ms | 0 |
| 10000 | 17.2 MB | 505 ms ← ここで崩れ始める | 0 |

保険の再確認だけが待機中に残る DB 負荷で、実測 **1000 人 = 86 クエリ/秒 /
2000 人 = 171 クエリ/秒**（飽和は約 2,100 クエリ/秒）。

**既定は 1 台 1000 本 = 2 台で 2000 人**にした。

| | 1 台 | 2 台 |
|---|---|---|
| GAP-198 時点 | 22 人 | 44 人 |
| GAP-201 後 | 150 人 | 300 人 |
| **GAP-202 後** | **1000 人** | **2000 人** |

## どこで動くか / 誰の費用か

サーバー側の作り方を変えただけ。**追加費用 0 円**。VM のサイズも DB のプランも
変えていない。利用者の PC 側（Bridge）は 1 行も変えていない。

## まだやっていないこと（正直に）

- **5000 でもまだ余裕はある**が、`uvicorn` と Fly のプロキシが同時 1000 本の HTTP を
  保持したときの挙動は**未実測**。そこに余白を残して 1000 にしている。
- **上限を超えたときはまだ「お断り」のまま**。順番待ちにする話は別 GAP。
  さらに、サーバーが返している日本語の混雑メッセージを**画面が捨てている**
  （`apps/web/app/chat/s_e01/_components/stream.ts` が本文を読まず
  `HTTP 503` にしている）ため、利用者には汎用エラーしか見えない。これも別 GAP。
- **Supabase の Supavisor（transaction pooler）を入れると LISTEN/NOTIFY が届かない**。
  そのため `ATELIER_DB_LISTEN_URL` で待ち受けだけ直結を指せるようにしてある。
  未指定なら通常の DB URL を使う。
